# Ultima VI (C64): reversing notes

What is known about the original C64 release of *Ultima VI: The False Prophet*, (c) Origin
Systems / Lord British, independent of the cart. How the cart uses it is in
`docs/developer/u6.md`.

Findings come from static disassembly (da65, py65's disassembler), VICE memmaps and
snapshots of the original game in play, a trace of every command the loaders sent during
a played session (2239 commands), and comparisons of played disk copies with the
originals. Where it matters each statement says how sure it is:

| Tag | Meaning |
|---|---|
| [dis] | read in the disassembly |
| [rt] | seen at run time in VICE (RAM, registers), on copies of the disks |
| [mm] | seen in VICE memmaps of play |
| [tr] | seen in the loader-command trace of a played session |
| [disk] | seen by comparing disk images |
| [inf] | inferred, not proven |

A negative finding ("no reference") is only as broad as the search it names.

Addresses are run-time addresses; the binary is named where it is not `game`.

Dungeon disks is raw sectors. D64 geometry: 21 sectors on tracks 1-17, 19 on 18-24, 18 on
25-30, 17 on 31-35.

[disk]. Every code overlay of the `$2C80` table, T19 S0-7, and T1/T2/T4/T5 S9-20 are
identical on both, so code loads from whichever is inserted. **The exception is T3 S9-20,
the Cast overlay: the two disks carry different builds of it** (2080 of 3072 bytes differ,
in 89 runs; the first differences are shifted call targets in otherwise identical code).
Casting on the surface runs 1A's, in a dungeon 1B's; whether they behave differently was
not examined [dis].

## 2. Boot: `U6LOAD` and the `$AE` trick

`U6LOAD`'s load address `$00AE` is the KERNAL's EAL/EAH, the pointer LOAD itself stores
through. The file loads into the pointer that is loading it: payload byte 0 (`$AE`) goes
to `$00AE`, byte 1 (`$02`) to `$00AF`, the KERNAL then increments the pointer to `$02B0`,
and the rest follows. Payload byte k (k >= 2) lands at `$02AE + k`; the entry is `$02B0`
(`SEI`, then `LDA #$34 / LDX #$03`, the copy source `$0334`). Disassembling from `$00AE`
or `$02AE` gives garbage.

The body copies the resident driver image (payload offset `$86`) to `$C000` and starts it
at `$C00C`.

### The resident boot driver, `$C000-$C336` (workspace to `$C3FF`)

| Entry | Target | Function |
|---|---|---|
| `$C000` | `$C045` | load and run INTRO |
| `$C003` | `$C036` | load and run CREATE |
| `$C006` | `$C054` | load and run GAME with its assets |
| `$C009` | `$C16B` | generic load: X/Y -> a command string |
| `$C00C` | | cold start; also the RESET vector |

| Address | Role |
|---|---|
| `$C074` | init: IRQ/NMI/RESET vectors, VIC cleared, CIA interrupts off, `$01` = `$35`, `CLI` (blackens the border only) |
| `$C0B6-$C12C` | the load descriptors |
| `$C12D` | IRQ (raster; plays music through `$9003`) |
| `$C14E` | self-modified `LDA #` operand: `$00` music on, `$FF` off |
| `$C164` | NMI |
| `$C16B` | the loader (X/Y stored into `$C247`/`$C248`) |
| `$C1AA-$C1AF` | the store loop, target operand self-modified at `$C1AD`/`$C1AE` |
| `$C292`, `$C2A1` | 2-bit receive from `$DD00` |
| `$C2E4` | drive-code upload, the driver's only KERNAL use (`$ED0C`, `$EDB9`, `$EDDD`, `$FFAE`) |

Callers: `OPENING` calls `$C003`; `CREATE` `$C000`, `$C006` and `$C009` (at `$06BC` and
`$06DD`); `INTRO` `$C003`; `GAME` `$C000`.

**Descriptors** (`$C0B6`): `%`, the name in ASCII, a terminator (`$00` = another entry
follows, `$FF` = last), the load address. The chains: `%THEME` -> `$9000`; `%ICHARS` ->
`$8000` + `%OPENING` -> `$0200`; `%ICHARS` + `%CREATE` -> `$0200`; `%INTRO` -> `$0200`;
`%GAME` -> `$0200` + `%COLORS` -> `$A000` + `%TILEFLAGS` -> `$A200` + `%CHARS` -> `$D000` +
`%POINTER` -> `$FF40`; `%TILES` -> `$6000`.

**Boot sequence** at `$C00C`: upload the drive code (`$C2E4`), init (`$C074`), load
`%THEME`, `JSR $9000`, music on. Then the opening (`ICHARS` + `OPENING`, `JMP $0200`) -- or,
if a key was pressed (detected at `$C143`, which self-modifies `$C024`, the operand of `LDA
#$00 / BNE $C036` at `$C023`), character creation. `$C054` (the `$C006` entry) loads the
`GAME` chain, `JSR $900C`, turns the music off (TILES overwrites the player at `$9000`),
loads `%TILES` and jumps to `$0200`.

### The drive code

Loaded from the Game disk, T18 S3, S6, S9, S12, into drive RAM `$0300-$06FF`; its loader
stub sits in the unused tail of that disk's BAM sector, which DOS holds at `$0700`. `$C2E4`
starts it with `M-E $07AB`; `GAME` never uploads again [dis].

## 3. The loaders and their protocol

There are **two copies of one fastloader**: the resident one above, and one inside `GAME`
at `$2989-$2B4D` (entry `$29BE`, also `$0263` in the jump table). Both bit-bang CIA 2 port
A, two bits per transfer. Both take X/Y as a pointer to a command string, read through a
self-modified `LDA $FFFF` (`$C246` / `$2AB0`); the marker table is `# ^ &` at `$C240` /
`$2AAA` with parameter counts `2 4 4`:

| First byte | Command | Sent | Then |
|---|---|---|---|
| `#` | disk-ID check, e.g. `#SU` | `#`, 2, two ID letters | status only |
| `^` | read part of a sector | `^`, 4, track, sector, offset, count (0 = 256) | 2-byte destination, data comes back |
| `&` | write a sector | `&`, 4, track, sector, 2 bytes, the source, 256 bytes | |
| anything else | load by name | the name up to a terminator: `$00` another entry follows, `$80`+ last | 2-byte destination; unless the name starts with `/`, the file's PRG header is received and dropped |
| `!` | (in the save overlay) a file's first track/sector, see 6 | | 2 bytes back |

Data coming back is escaped with `$AC`: `$AC $AC` a literal `$AC`, `$AC $FF` end of unit,
`$AC $F7` an error block follows (stored at `$D400` in `GAME`), any other `$AC xx` a pause
while the drive fetches the next sector. (No run-length decoding exists, despite the look
of it.) A chain is one call: the terminator is stored into the `LDA #` at `$C165` / `$2989`
and `$00` loops back.

**There is no disk parameter**: the drive reads whatever is inserted. The game picks a
disk by the `#xx` check: `$2813` chooses `SU` or `DU` by `$10` (the map level), `$2823`
builds `#` + an ID from `$289C` (`SU DU CA CB CC GA`, matching the BAM IDs) and prompts
"PLEASE INSERT ..." (names at `$28B0`) until it matches. X selects the disk as a byte offset
(0 Surface, 2 Dungeon, ...).

`GAME` keeps a standing parameter block at `$0203-$0209` (over the bytes after `JMP
$038F`): command, track, sector, offset, count, destination; it loads as `5E 00 00 00 00 00
D4`. `$27FA` clears offset and count and sends it (whole sector), `$2809` sends it as set.
All sector reads go through it:

| Site | Track | Sector | Offset / count | Destination |
|---|---|---|---|---|
| `$2320-$2355` | `$10` (dungeon level) | 4, then 0-3 | `$80` bytes, then whole | `$4380`, `$4400-$47FF` |
| `$238D-$23DD` | superchunk row + 1, wrapping 1-8 | 8, then the map's sectors | whole | `$D7xx`, `$D6xx` |
| `$26E3` | `$27F8,X` (26 or 30) + chunk >> 6 | (chunk >> 2) & 15 | (chunk & 3) x 64 / 64 | `$D700` |
| `$2C3F` | the `$2C80` table | | whole | the table's page |
| `$30E8` | 34 or 35 | value >> 4 | | |
| `$3E0E-$3E5C` | 1, 2, 4, 5 | 9-20 | whole | `$6800`, `$C000` |
| `$3EBD` | 6 | 9-20 | whole | `$5400-$5FFF` |

The only write anywhere is the save (6): `$0203` holds `^` except there, so every other
caller of `$27FA` is a read (searched: every store to `$0203` in the 14 files of the Game
disk, and the save overlay).

Each other overlay carries a `$DD00` routine near its entry. In `OPENING`, `CREATE` and
`INTRO` these are serial stubs; in `END` and in `GAME`'s init (`$03BD`) they are VIC bank
switching (`AND #$FC`), not serial code.

## 4. Banking

The game runs at `$01` = `$34` (all RAM) or `$35` (RAM and I/O) and never returns to `$37`
during play; `$36` only for the drive-code upload. The idiom: sit at `$34`, `INC $01` to
reach I/O, `DEC $01` back. The loaders go the other way (`DEC`/`INC`) to store under I/O
and ROM. HIRAM is always 0, so the KERNAL and BASIC are never visible in play; `GAME`
makes no KERNAL calls at all.

| Where | `$01` writes |
|---|---|
| `U6LOAD` | `$0400` `STY $01` (`$00`, the memory wipe), `$0417` `$37` then `JMP $FCE2`, `$04B2` `$35`, `$0619` `$36` |
| resident `$C000` | `$C0B2` `$35`; IRQ `$C132`/`$C137`/`$C15D` (save, `$35`, restore); `$C171` `$35`; `$C1AA`/`$C1AF` `DEC`/`INC`; `$C2E5` `$36` |
| `GAME` | `$0392` `$35`; `$1304` `$34`; `INC`/`DEC` pairs at `$13C4`, `$1706`, `$1B03`, `$1F6C`; IRQ `$1F2E-$1F4C`; loader `$298E`, `$29C8`, `$2A08`, `$2A34`, `$2A9B` |
| `OPENING`, `CREATE`, `INTRO`, `END` | `$0200`: `SEI / LDA #$35 / STA $01`; `CREATE` also its IRQ `$048E`/`$04CA` and `$0509`/`$050E` |

The IRQ handlers set `$35` with `LDA #$35 / STA $01`: a constant, which also clears `$01`
bit 3 (the cassette write line).

## 5. Memory during play

While `GAME` runs (after `$C006`). Boot phases and `END` use memory differently.

| Range | Contents |
|---|---|
| `$0000-$00FF` | zero page, used almost completely (below) |
| `$0100-$017F` | sprite multiplexer's sort table / scratch (overlay `$18` reads it, `$3C` writes it) |
| `$0180-$0182` | number entry; `$0190-$0192` decimal digits; `$0193/$0194` counters; `$0196`/`$0197` the key just scanned and its repeat delay (8) |
| `$01AB-$01FF` | stack (the main loop resets S to `$FF`); the deepest use seen in the memmaps of play is `$01AB` |
| `$0200-$437E` | `GAME` |
| `$4380-$43FF` | one bit per chunk of the window: which of two tile banks (tracks 26-29 or 30-33) holds its graphics |
| `$4400-$47FF` | chunk-index map, 32 x 32 |
| `$4800-$4BFF` | plane 1: map tile per cell, a 32 x 32 ring indexed by `$7E`/`$7F` |
| `$4C00-$4FFF` | plane 2: an object's tile over the cell (0 = none) |
| `$5000-$53FF` | plane 3: the object's byte 0 (`$FE`/`$FF` special) |
| `$5400-$5FFF` | **the save state** (7) |
| `$6000-$9FFF` | TILES: 512 tiles of 16 x 16 multicolour pixels, 32 bytes each; `$6800-$7FFF` doubles as the conversation buffer |
| `$A000-$A1FF` | COLORS, one byte per tile [inf] |
| `$A200-$A7FF` | TILEFLAGS, tables at page boundaries; `$A39F-$A3F9` reused as sprite/actor tables in play |
| `$A800-$BFFF` | **object pool**: 768 nodes of 8 bytes (6 of record, a 2-byte link) |
| `$C000-$CBFF` | code-overlay area (below) |
| `$CC00-$CFE7` | the bitmap's colour matrix (`$D018` = `$38`) |
| `$CFE8-$CFF7` | unused (never written since power-on in any session) |
| `$CFF8-$CFFF` | sprite pointers; sprite 0 always block `$FE` |
| `$D000-$D3FF` | CHARS, the font drawn into the bitmap (RAM under I/O) |
| `$D400-$D5FF` | overlay `$34`; the loader's error block at `$D400`; the save reads the BAM into `$D500` |
| `$D600-$D6FF` | sector buffer: chunk-map sectors at a window load; the save builds chunk-file sectors here |
| `$D700-$D7BF` | the 64 tile bytes of the chunk being fetched, then its object layers `$D740`/`$D780` |
| `$D7E4-$D7FE` | **key queue**: the IRQ appends at `$D7E4,X` (X = `$45`, at most 27) |
| `$D800-$DFFF` | sprite images, **double-buffered**: blocks `$60-$6F` and `$70-$7F` |
| `$E000-$FF3F` | multicolour bitmap, under the KERNAL |
| `$FF40-$FF7F` | POINTER, sprite block `$FD` |
| `$FF80-$FFBF` | sprite block `$FE`, sprite 0, written by `$0B0B` |
| `$FFC0`.. | text line buffer (`$FFC0,X`); `$FFF5`/`$FFF6` chunk-map load temporaries |
| `$FFFA-$FFFF` | NMI `$2062` (an `RTI`: RESTORE does nothing), RESET `$C00C`, IRQ `$1F26` |

The resident boot driver is gone in play (the overlays load over it), ICHARS was only there
during the opening and creation, and the music is overwritten by TILES (`GAME`'s IRQ never
calls `$9003`).

**The sprite halves.** `GAME` draws actors into one half of `$D800-$DFFF` while the other
is shown; `$27` bit 4 says which is on screen. A trace of 521,320 sprite-pointer stores
over a game start and a save found none into the shown half during a loader call [rt].

**The screen.** Cells written in play [mm]: the map view columns 2-19, rows 4-21 (9 x 9
tiles of 2 x 2 cells); the top bar columns 3-18, rows 1-2; date and wind on row 23,
columns 2-11 and 13-19; the party panel columns 22-38, rows 0-12; the message area columns
22-38, rows 14-23. Row 24 is not written in play.

## 6. The save

Only Surface and Dungeon are ever written; the other four disks never [disk]. The save
routine `$3E83` runs from Shift-S (`$2EDD`), **at every surface window shift** (`$22C5`:
the party's window coordinate `$72`/`$73` below `$14` or at least `$EC`; the window is then
recentred by 128 tiles) and **at every level change** (`$25A9`). So the disks are rewritten
continuously while the party walks, which is why the manual insists on copies.

`$3E83`: the anchor object-file name from `$243C` into `$0190`; overlay `$44` (T19 S17-18
to `$CA00`, in no file) does the chunk files; zero page `$02-$21` to `$5879`; actor 0 gets
actor 1's position and the current level; then `&` T6 S9-20 from `$5400`, after `#SU` (a
dungeon save prompts for the Surface disk, then `#DU` again) [dis].

**The chunk-file writer** (`$CA00-$CBD7`) picks four names: in a dungeon `D` + level letter
+ `A`-`D`; on the surface the 2 x 2 window whose bottom-right superchunk is the anchor (row
and column letters each the anchor's less one and itself, wrapping `A`-`H`: the world is an
8 x 8 torus of superchunks; second letter row, third column). For each:

1. collect the quadrant's records from the pool into `$C000`, each ANDed with `FF 7F 7F FF
   FF FF` (window to superchunk coordinates); records whose status has bit 5 set (other
   than `$FE`) are dropped; the end record follows;
2. `!NAME` until it succeeds: **the drive** finds the closed PRG entry, frees the file's
   chain in its copy of BAM bytes `$04-$43` (tracks 1-16 only), writes the BAM, and replies
   with the first track and sector;
3. `^ 18 0` -> `$D500`, the BAM;
4. write the chain: mark the current sector used, find the next free one -- **track 17 down
   to 1, sector 0 up**, first free bit -- as its link, fill 254 bytes, `&`; the last
   sector's link is `00`, last-byte index;
5. `& 18 0`, the BAM back.

The directory sector is never written, so a file keeps its first sector and its (possibly
stale) block count. A chain that was not ascending comes back ascending [rt, disk].

**Bug: track 17 leaks** [dis, disk]. The C64 allocates from track 17, but the drive frees
only tracks 1-16 (for track 17 it modifies drive RAM `$06AA-$06AD` instead, never written
back). A file with sectors on track 17 re-marks its first one, decrementing track 17's free
count on every save, and loses the others for good. A played Dungeon disk showed both (the
count at `$F8`). Nothing reads the counts, so the wrap does no harm by itself.

**Bug: a full disk** [dis, not run]. With no free sector on tracks 17-1 the scan tries
"track 0", whose bitmap is BAM bytes 1-3, in which two sectors look free: a drive error. If
that fails too, carry set is returned and not checked: the file is cut short. Never seen:
1A has 74 blocks free.

**`CREATE`** checks for 1A, reads T6 S12 once and writes T6 S9-20 from its template; it
writes no object file and no BAM. **A new character on a used disk keeps the used world**.

**Load**: Shift-L prints "LOAD Game ?" (`$2EE7`), asks Y/N (`$3E6C`) and at `$2EF9` branches
`BCS` -- but `$3E6C` returns carry set for Y, and the save prompt beside it tests `BCC`. So
Y does nothing and **N reloads the last save**, discarding everything since (verified in
VICE). Not in the manual. A load jumps to `$03FC`, which re-reads T6 S9-20, restores zero
page and reloads the window's object files.

What is not saved: temporary objects (status bit 5); the terrain (read-only); objects of
superchunks outside the window are on disk as the window last left them, so quitting
without saving loses changes only in the current window and state.

## 7. Data formats

### Object files `SAA`-`SHH`, `DAA`-`DED`

84 files: 64 surface superchunks (128 x 128 tiles each) and 20 dungeon quadrants (5 levels
of 2 x 2). PRG type but no load address: loaded with `/` to `$C000`, linked into the pool
with bit 7 of x and y ORed in by quadrant. **6-byte records** and an `$FF` end record (all
84 files a multiple of 6 [disk]):

| Byte | Meaning |
|---|---|
| 0 | status: `$00`, `$01`, `$02`, `$FE`, `$FF` end; bit 5 (not `$FE`) = temporary, not saved [rt] |
| 1, 2 | x, y inside the superchunk, 0-127 |
| 3 | object type, the tile drawn over the map |
| 4, 5 | not decoded |

Over the 6739 original records: status `$FE` 4458, `$00` 2054, `$01` 112, `$02` 31. The
factory files end in `FF FF FF ...`, saved ones in `FF 7F 7F FF FF FF`. Hypothesis, not
verified: like the PC's `objblk` (status, position, type and frame, quantity/quality),
with `$FE` a C64-specific class of fixed objects.

**The pool can run dry.** `$2548` (from the object creator `$32DD`) returns carry set when
`$4C`/`$4D` is zero; the count is reset to 764 only when the window's files are reloaded.
The worst 2 x 2 window holds 644 records (`CB`), leaving 120 for objects made in play. The
Orb of the Moons then answers "Not possible" whatever square is chosen [inf: fits the
code; `$4C`/`$4D` = 0 not confirmed in the monitor].

### The world map

1024 x 1024 tiles: 8 x 8 superchunks of 16 x 16 chunks of 8 x 8 tiles. The game holds a
window of 2 x 2 superchunks, 256 x 256 tiles (`$78`/`$79`). Surface: track = superchunk
row + 1, sector 8 the chunk-bank bits (32 bytes per superchunk), the chunk-map sectors the
16 x 16 chunk indices. Dungeon: T*level* S0-S3 the chunk indices, S4 bytes `$00-$7F` the
bank bits (the dungeon maps' chunks join up across their borders only with these). Chunk
tiles: 64 bytes each, on tracks 26-29 or 30-33 by the bank bit.

### The save state `$5400-$5FFF` (1A T6 S9-20, one page a sector)

| Range | Contents |
|---|---|
| `$5400-$54BF` | inventory status, 6 members x 32 slots, bit 7 readied |
| `$54C0-$557F` | inventory item type |
| `$5580-$563F`, `$5640-$56FF` | inventory third and fourth bytes [inf: quantity] |
| `$5700-$576D` | names, screen codes, `$00`-terminated: the Avatar (9 characters, blank in the factory state), then the 14 companions |
| `$576E-$577C` | slot -> actor number for each named character |
| `$577D-$578B` | offset of each name in `$5700` |
| `$578C`.. | stats, 23 slots each (0 the Avatar, 1-14 the companions, 15-22 not established): `$578C` STR, `$57A3` DEX, `$57BA` level (low nibble), `$57D1` INT, `$57E8` HP, `$57FF` max HP, `$5816` condition (`$01` protected, `$02` paralysed, `$04` asleep, `$08` poisoned, `$40` in the party), `$582D` (bit 1 invisible), `$5844` MP |
| `$585B-$5878` | experience, 16-bit per named character (cap 9999) |
| `$5879-$5898` | the copy of zero page `$02-$21` |
| `$5899-$58C7` | not decoded (`$589E`, `$589F` the rest's hours left among them) |
| `$58C8-$599C` | NPC flags, one byte per NPC (bit 0 "met"; the conversations' `flag(n, b)`); NPCs 203-210 are the spellbook's circles |
| `$599D`.. `$5E35`.. | the actor table, 196 entries per array: tile/figure [inf], status (`$5A61`.., `$5A62` = `$FF` runs overlay `$40`), x low/high, y low/high (`$5B25`, `$5BE9`, `$5CAD`, `$5D71`), level (`$5E35`) |
| `$5EF9-$5FAF` | not decoded |
| `$5FB0-$5FFF` | five 16-byte tables [inf: combat or creature slots] |

Max HP is stored, never computed (no store in `GAME`, the 18 small overlays, `CREATE`,
`INTRO`, `END` or `OPENING`; `(zp),y` and the scripts not checked). Levels come only from
the eight shrine conversations, which set max HP to 30 x level and raise attributes (cap
30); max MP is 2 x INT. Nothing checks consistency at load.

The factory save area on the Surface disk is `CREATE`'s template (at `$722B-$7DDA`) in
2992 of 3001 comparable bytes; the differing bytes sit at a 23-byte stride in the stats
[inf: a different build of the template]. The Dungeon disk's T6 area is essentially zeros
and never used.

### Conversations

`/Tnnn` is loaded to `$6800` by the Talk overlay (command string at `$CBF5` in the T4
image), and `$6800-$7FFF` (TILES) is reloaded from T1/T2 S9-20 afterwards. The scripts are
evaluated one byte at a time by T4, all 8-bit. An answer list is `ASK` (`$F7`), per answer
`KEYWORDS` (`$EF`) words `ANSWER` (`$F6`) statements, `ENDANSWERS` (`$EE`); `$B0` is a
16-bit `JUMP`; `*` is the catch-all keyword. Lower-case letters are `$01-$1A`, the rest
ASCII. T001 is the game's own debug and cheat menu (flags, stats, items), reached by
talking to yourself. Lord British (T005), Mariah (T033) and Selganor (T064) ask the
copy-protection questions.

## 8. Bugs in the original

Besides the two allocation bugs and the load prompt above:

- **The shrines' level check.** T4's `exp()` (opcode `E0`, `$C650`) adds to a character's
  16-bit experience and returns its **low byte**; the shrines (T191-T198 on 3A, a table in
  each file's last 8 bytes) compare it with the low bytes of 0, 100, 200 ... 6400. Levels
  come on the low byte alone, too early or too late. Only the shrines and T001 call
  `exp()` (all 202 conversations decoded).
- **Rest with a guard.** Rest is overlay `$20` (T24 S16-18); each pass of its loop
  (`$C901`) is 5 minutes and every actor's turn, and with a guard it stops when anyone not
  in the party is in sight. The alarm "I hear something!" is printed through `$0383`, the
  print that returns from the caller, so the `JMP $C923` after it never runs: the hours
  left (`$589F`) stay set and the party asleep. While `$589F` is set the game neither pins
  the controlled actor to the view centre (`$07DA`) nor stops drawing the campfire there
  (`$D72E`): the keys move the view and the fire (through walls), and once the Avatar is out
  of the actors in sight `$3DB6` returns X = `$FF` and the move test reads stale zero page.
  At the end of the hours the Avatar is moved to wherever the view is. Reproduced in VICE
  on the original disks. And the guard prompt (`$C8E1`) refuses the last party member: the
  answer less one is accepted only below `$15`.
- **A second tap of the same key is lost.** The IRQ queues a key when it differs from the
  last one seen (`$43`) or when the repeat count `$0197` runs out, and does nothing on a
  frame with no key, so a re-press is the old key held. Measured in VICE: 4 frames down, 3
  or 12 up, 4 down is one key. Only `GAME` has this queue (a byte search of the six disks).
- **Direction taps between two reads are lost.** The direction keys are not queued: `$47`
  is rebuilt every frame, `$0449` samples it once a pass (9 frames at least, a step 13-16).
  Return sets the fire bit (`$206D,9` = `$10`) and is also queued, but the confirms (`$2F45`,
  `$1D43`) read only the sampled fire bit, and a queued Return outside combat comes to
  nothing (`$2D50`).
- **"Press a key" after the title menu.** `OPENING`, `INTRO` and `END` share a routine
  (`$0C22`, `$09ED`, `$0AFE`) that reads keyboard column 4 (Space among others) without
  selecting a row; after the title menu's scan (`CREATE` `$0945`) port A's data register is
  `$FF`, no row, so only the joystick's fire button goes on.
- **The text box's raster split** in `OPENING`, `INTRO` and `END` switches `$D011`, `$D018`
  and `$DD00` from an IRQ two lines before the box's first character row after a fixed
  BIT/NOP delay tuned for 65-cycle NTSC lines; on PAL the stores could run past cycle 12 of
  the row, a badline, into the picture.
- **The flood's dark-neighbour special case is dead logic**: both of its paths mark the
  cell and skip the push when the cell is opaque (from the code).

## 9. Engine notes (from profiling)

Measured in VICE on the cart build, with the same game code: a plain step on the map is
~300k cycles, CPU-bound (the main loop's 9-frame pacing never binds). The view `$1631` is
74 % of it: the draw loop (a masked copy of 32 bytes per cell, 81 cells, 41 cycles a byte
pair; the mask by light level from `$93B0` + 16 x (5 - level) in TILES, level 4 all `$FF`,
level 0 all `$00`), the line-of-sight flood (each cell tests eight neighbours, ~690 times a
step), the actors (`$081B`, `$09F6`, both walking ~187 slots and calling the range test
`$0A41`). Interrupts take ~11 %, VIC's stolen cycles ~10 % on top. Every eighth step four
chunk fetches each walk the whole pool (~610 nodes): ~700k cycles.

The light map `$18E8`: level = the party's light `$26` + the cell's own (`$A600` bits 0-1,
or 0 with `$589E` set) less a distance from a table at 8 x |rows| + |columns|, clamped 0-4;
the table is never read past 45. The flood's first visit decides how a cell is marked
(`$18C7` looks at the cell it is seen from). A cell's lower half in the bitmap is 320
bytes after its upper (row tables `$1E3A`..).

## 10. RAM the game leaves alone

Almost none. From the memmaps of play sessions (every command key, combat, save, load, a
window shift; not conversations' content, spells, dungeons or the ending), a bitmap of every
absolute operand in `GAME` and every overlay of both disks, and a RAM dump compared with
VICE's power-on pattern:

- `$CFE8-$CFF7` (16 bytes): never written since power-on.
- `GAME`'s one-time init, `$038F-$03FB`, `$1302-$13D9`, `$2077-$208C` (347 bytes): each
  named only by the init's own calls, never run again.
- Page 1 `$0183-$018F` and `$0198-$01A8`: named by nothing, untouched; the stack got no
  lower than `$01BB` in the audit's sessions, but no bound was proved, and `$01A9` is
  touched by something.
- About 3 KiB of code no session ran (`$3E83`, `$22E0-$238C`, actor handlers ...): not
  dead -- `$37D4`, the one block with no pointer to it, is actor type `$81`'s handler,
  reached through split low/high tables at `$422F`/`$4242`.

Not free: the zero page (its unnamed bytes are inside the four actor arrays), the object
pool, the tile slots (255 of 256 terrain ids occur), the sprite images, the state, and
`$FFD9-$FFF4`: the line buffer `$FFC0,y` is checked against `$22` only at a word's end, so
a line runs to 34 characters plus the word that crosses it.
