# Ultima III: Exodus (C64): reversing notes

What the analysis of the original Commodore 64 release found: its disks, boot chain,
disk I/O, memory map, copy protection and save data, and the engine routines the cart
touches. This describes the game itself. How the cart changes it is in
`docs/developer/u3.md`. The fan version Ultima III Gold is in
`docs/reversing-notes/u3-gold.md`.

Ultima III: Exodus is (c) Origin Systems / Lord British. Addresses are C64 addresses in
the named unit. Track/sector is written `T05/S08`.

## The disks

Two disks: **disk A** (program) and **disk B**. The Ultima Trilogy calls disk B the
"PLAYER MASTER" (its BAM name). The 1984 release calls it the Scenario disk, BAM name
"ULTIMA III-SCEN.", ID `U3`. The game itself says INSERT SCENARIO DISK.

- **The CBM file system is almost unused.** Disk A's directory holds one real file,
  `ultima`, the boot PRG. Everything else on both disks is raw sectors outside the BAM,
  which still reports 660 of 664 blocks free. Disk B's directory track is overwritten
  with game data, so a directory listing of it shows garbage.
- **The game has its own catalog**, loaded to `$B000`: 94 entries of 8 bytes. +0..+3 the
  name (4 characters, bit 7 set), +4/+5 the start block (little endian), +6 the length in
  blocks, +7 the destination page. The table ends at `$B2EF`. `$B300-$B3FF` is a copy of
  `$BB00-$BBFF` (a mastering leftover, not catalog data).
- **Block numbers are linear from T1/S0 straight through the disk, track 18 included.**
  They are converted to track/sector with the sectors-per-track table in the DOS module
  at `$BAD6`.
- **Both disks share one block-number space.** Disk A holds the ten program files and
  disk B everything else, and their block ranges overlap by design: `DEMO` is block 144
  on disk A, `MAPI` blocks 144-159 on disk B. A block number means nothing without its
  disk. Disk A is needed only at boot.
- The catalog references 606 of the two disks' 1366 blocks. The highest block used is
  284 on disk A and 381 on disk B, and no two entries share a block.

## Boot

The boot PRG `ultima` loads from BASIC and runs with `SYS 2064` (`$0810`).

**Its load address is off by one.** The file records `$0800`, but the first data byte
lands at `$0801`, and `SYS 2064` only resolves with that base. A disassembly at `$0800`
shifts every table lookup by one byte.

1. It sets `$01` to `$36` (BASIC out), black border and background, clears the screen.
2. Its code at `$0825-$090F` paints a title screen of credits (ORIGIN SYSTEMS PROUDLY
   PRESENTS ... MUSIC COMPOSED BY KENNETH W. ARNOLD) straight into screen RAM and
   leaves it up while it loads.
3. It reads three raw chunks with its own `U1` block reader (KERNAL messages off):

   | Blocks (disk A) | Track/sector | To | What |
   |---|---|---|---|
   | 5-91 (87) | T1/S5 - T5/S7 | `$3000-$86FF` | `EXOD` |
   | 92-95 (4) | T5/S8 - S11 | `$B800-$BBFF` | the DOS module |
   | 100-103 (4) | T5/S16 - S19 | `$B000-$B3FF` | the catalog |

4. At `$0910` it consumes a pending key, then `JMP $8220` into EXOD.

EXOD's entry (`$8220`) loads SUBS and TEXT, and `$8239` runs its sequence at `$826C`:
the display set-up (`$852A` copies `$3000-$5FFF` to `$1000`, then `$8322`, the frames at
`$82C5`, `$B803`), `$827E` `LDY #5 / JSR $8545` (a timed delay), the "Exodus"
scramble-in (`$8343`), and waits, each through `$854E` (`JSR $B80C / CMP #$FF`). At a
wait, C (`$855E CMP #$C3`) runs `R COPY`, the disk copier. Any other key goes to `$856E`
(`PLA` x4 / `JMP $823F`), which issues `^D "R BOOT"`: load BOOT and jump to `$1000`.

BOOT loads SUBS, TEXT, SHPS, DEMO, ULT3, DDAT and MUSI, calls the copy-protection check
(below), starts the music (`JSR $9A00`), prints **INSERT SCENARIO DISK** (`$1055`, an
inline string after `JSR $46C3`) and waits for any key (`$1072-$1078`, polling `$B80C`),
then flushes the keyboard at `$1079`. From then on everything is read from disk B. BOOT's
demo view polls for a key at `$1169` (`JSR $B80C / CMP #$FF / BEQ $1117`). Its menu reads
a key at `$1278` (`JSR $4711`), and J (Journey onward) goes to `$12A9`.

**`COPY`** (disk A blocks 278-284, loads at `$0800`), "PLAYER DISK DUPLICATOR", asks for a
formatted disk and copies blocks 0-383 through `$1000` in two passes of 192 (`U1`/`B-P`/
`U2`), track 18 included. So a player disk it makes carries its master's BAM name.

## Disk I/O: an Apple II DOS 3.3 emulation

Game code never calls a loader. It **prints** an Apple DOS command as an inline string
after a call:

```
        jsr print_inline
        !byte $04                ; Ctrl-D
        !text "L MAPA"
        !byte $8D, $00           ; CR, terminator
```

`cout` (`$B986`, through the jump table at `$B815`) watches for `$84` (`^D` with bit 7),
buffers what follows until CR, looks the name up in the catalog and loads or saves it.
The first letter is the operation: `L` load, `S` save, anything else (`R`) load and jump
to `$<destination page>00`.

There are **44 call sites**: EXOD 4, ULT3 26, BOOT 14. Two names are changed at run time:
`L SHP@` (ULT3 `$66EF`) and `L CON@` (ULT3 `$7E9C`) have their last character overwritten
to pick `SHP0`-`SHP7` and `CONA`-`CONS`. The writes:

| Unit | Address | Command |
|---|---|---|
| ULT3 | `$64CD`, `$64D5`, `$64FB`, `$6503` | `S SOSA`, `S SOSM`, `S PLRS`, `S PRTY` |
| BOOT | `$17EF`, `$17F7`, `$17FF` | `S ROST`, `S PLRS`, `S PRTY` |
| BOOT | `$1D93` | `S ROST` |

ULT3 loads SOSA and SOSM at start (`$500B`, `$5013`), back on Sosaria (`$6DA4`, `$6DAC`)
and when leaving Ambrosia (`$7729`, `$7750`).

### The DOS module, `$B800-$BBFF`

The single choke point for disk, screen and keyboard. The analysis's commented
disassembly of it reassembles byte-identical to the original.

Jump table, the only interface the rest of the game uses:

| Entry | Target | Function |
|---|---|---|
| `$B800` | `$B8CE` | init: SID, save the KERNAL IRQ vector, flush the keyboard |
| `$B803` | `$B90D` | bitmap mode on, screen `$0400`, bitmap `$2000`, VIC bank 0 |
| `$B806` | `$B92F` | stub (`RTS`) |
| `$B809` | `$B93F` | wait for a key and consume it |
| `$B80C` | `$B952` | poll a key (`$FF` if none); does not consume |
| `$B80F` | `$B973` | flush the keyboard queue |
| `$B812` | `$B97A` | delay, duration in A |
| `$B815` | `$B986` | character out, with `^D` command interception |
| `$B818` | `$B930` | toggle SID volume bit 7 |
| `$B81B` | `$B973` | same as `$B80F` |
| `$B81E` | `$B895` | plot A at column `$79`, row `$7A` |

Internals:

| Address | Routine |
|---|---|
| `$B99E` | `^D` command parser; buffers at `$BAFA`, dispatches on CR |
| `$BA1D` | catalog lookup: linear scan of `$B000`, 4-character match |
| `$BA48` | `dos_transfer`, the load/save driver: block to track/sector, a status check and retry per block |
| `$BB0B` | read one block: `U1:2 0 t s`, then 256 x CHRIN into `($35),Y` |
| `$BB79` | write one block: 256 x CHROUT from `($35),Y`, then `U2:` |
| `$BB31` | send a command string; `"U1:2 0 "` at `$BB6C`, its digit at `$BB6D` patched `1`/`2` |
| `$BB4D` | binary to two decimal digits and a space (the track/sector arguments) |
| `$BB9B` | send `"B-P:2 0 "` |
| `$BBB2` | open channel 15, then channel 2 as `"#"` |
| `$BBE2` | close both, CLRCHN |
| `$BAD6` | sectors-per-track table, indexed by track 1-35 |
| `$BB00-$BB0A` | the parameter block: `$BB00` operation (1 load, 2 save), `$BB01`/`$BB02` destination, `$BB03`/`$BB04` start block, `$BB05` length, then the current track/sector |

The dispatcher copies +4/+5, +6 and +7 of the catalog entry straight into the parameter
block. `$35`/`$36` is the destination pointer (`$35` is always 0, `$36` the page, bumped
after each block).

Properties:

- Standard-speed **KERNAL serial only**: no fastloader, no custom GCR, no drive code.
  The game is about 400 bytes per second.
- Device 8 hardcoded (`$BBB4`, `$BBC5`); channel 2 for the buffer, 15 for commands.
- Every block is checked against the error channel and **retried indefinitely** until the
  status reads `00` (`$BAA9`, `$BAB2`).
- `catalog_find` has no "not found" path: an unknown name walks off the end of the table.
- The VIC is programmed in exactly one place, `$B90D`: `$D011 |= $20`, `$D018 = $18`,
  `$DD00` bits 0-1 = `%11`. A scan of ULT3, SUBS, BOOT, MUSI and DDRW for writes to
  `$D011`/`$D016`/`$D018`/`$D020`/`$D021`/`$DD00`/`$DD02` found none.

### Other copies of disk code

- **BOOT `$1DF4-$1EE4`**: a private KERNAL block reader used only by the copy-protection
  check (below). `$103F` is the only call into it from the rest of BOOT (a scan of BOOT's
  blocks 217-231 for `JSR`/`JMP`).
- **The boot PRG `$0801-$0B0B`**: discarded once SHPS loads over `$0800-$0FFF`.
- **SHP0 and SHP6, `$977F-$97BF`**: serial code that calls the DOS module's internals
  (`$BB20`, `$BB93`, `$BBD3`) and the KERNAL's serial routines. It is unreachable: the
  shop code before it ends at the `RTS` at `$977E`, and no absolute `JSR`/`JMP`/`JMP ()`
  into `$977F-$97FF` exists in any unit of the game (branches cannot reach it from
  outside the unit). It is residue, like OUTM's copy of DOS code.

## Copy protection

Disk A carries an error map: all 21 sectors of **track 6** are flagged "21 no sync"
(the image is 175531 bytes). BOOT calls `$1DF4` from `$103F`, after its `L MUSI` and
before `JSR $9A00` starts the music. The routine reads **track 6 sector 8** into `$F000`
with its private reader, then reads the error channel. If the status is `00` (the read
**succeeded**), it jumps to `$1E42`, an endless loop. The check requires the read to
fail. With no drive it passes only after the KERNAL times out.

The DOS module has no protection, so a scan of the load path alone finds none.

## Memory map

```

$0002-$00FF  zero page.  $02/$03 boot loader pointer and SUBS' map read, $22 the idle
             timeout counter, $23 the dungeon level, $33/$34 screen and catalog
             pointer, $35/$36 DOS destination, $4C torch light, $62 where the party
             is, $79/$7A plot x/y, $7E/$7F inline-string pointer, $C6 keyboard queue
             length, $F7/$F8 the party's position
$0100-$01FF  stack
$0200-$03FF  KERNAL work area.  $0277 keyboard buffer, $0314/$0315 IRQ vector,
             $032E/$032F saved copy of it
$0400-$07E7  text screen (the colour matrix of the bitmap)
$0800-$0FFF  SHPS (tiles)  |  COPY ($0800-$0EFF)
$1000-$1EFF  BOOT                                    -+
$1000-$1FFF  MAPx / SOSA                              +- one at a time
$1800-$1FFF  DDRW (dungeon drawing)                  -+
$2000-$3F3F  hires bitmap (VIC bank 0, $D018 = $18)
$3000-$86FF  EXOD (intro; overwritten by the game)
$4000-$40FF  PLRS (player records)
$4100-$4EFF  SUBS (shared subroutines; $4100-$42FF animation frames)
$4F00-$4FFF  MONx / SOSM (monster and people table of the current map)
$5000-$93FF  ULT3 (the engine)
$9400-$97FF  SHP0-7 / SHNE / OUTM / DNGM / END overlays
$9500-$99FF  ROST (roster; during character selection)
$9800-$98FF  TLKx (conversations)
$9900-$99FF  CONx / FNTN / TIME / BRND / SHRN
$9A00-$AFFF  MUSI (music and SID player)
$B000-$B2EF  catalog, 94 x 8 bytes
$B300-$B3FF  copy of $BB00-$BBFF (mastering leftover)
$B400-$B7FF  TEXT (font)
$B800-$BBFF  DOS / screen / keyboard module
$BC00-$BFFF  free
$C000-$C0FF  DEMO
$C100-$C4FF  DDAT (dungeon data)
$C500-$C9FF  free
$CA00-$CCFF  UPDT (map view update)
$CD00-$CDFF  PRTY (party state)
```

The units tile page-exactly (ULT3 ends at `$93FF` and the overlays start at `$9400`; SUBS
ends at `$4EFF` and MONx starts at `$4F00`), which cross-checks the catalog decode. "Free"
means no catalog unit loads there.

`ULT3 $922F-$93FF` is BASIC residue (monster-name strings), not code: the engine's code
ends at `$922E` (a table at `$921F-$922E` is referenced), and a scan of the original image
finds no absolute reference into it.

## `$00` and `$01`

Only **two** writes in the whole product, both in code that runs once:

| Address | Code | Effect |
|---|---|---|
| boot PRG `$0815` | `LDA $01 / AND #$FE / ORA #$40 / STA $01` | `$01` = `$36` |
| `COPY` `$0800` | the same | `$01` = `$36` |

`$36` is LORAM 0 (RAM at `$A000-$BFFF`), HIRAM 1 (KERNAL in), CHAREN 1 (I/O in). Bit 6
is unconnected on the C64. **The game proper never touches `$00` or `$01`**: checked by
tracing reachable code and by scanning both raw images for every encoding of
`STA`/`STX`/`STY`/`LDA`/`INC`/`DEC` `$00`/`$01`. The other matches are inside map and
conversation data, plus two further copies of the boot code on disk A (T1/S1, the
`ultima` PRG itself, and T17/S0, an unreferenced spare). `$01` stays `$36` for the whole
run, the motor bit set.

## Saving

**What play writes**: only disk B, five units:

| Unit | Disk B blocks | Holds |
|---|---|---|
| `SOSA` | 296-311 (16) | the map of Sosaria |
| `SOSM` | 312 | Sosaria's monster table |
| `ROST` | 327-331 (5) | the roster |
| `PLRS` | 332 | the four party members' records |
| `PRTY` | 333 | the party state |

(From the list of `^D` call sites above.)

**When the original writes.** Seven triggers, from ULT3:

| Trigger | Where | Writes |
|---|---|---|
| Q, "Quit & save" (surface only) | `$647F` | SOSA, SOSM, PLRS, PRTY |
| entering a town, castle or dungeon | `$5925` -> `$64AA` | all four |
| back on Sosaria | `$6DA1` loads SOSA/SOSM, `$6DB9` saves | all four (`$64BD`) |
| the whirlpool to Ambrosia | `$764C` | all four (`$64BD`) |
| leaving Ambrosia | `$7726`/`$774D` load, `$777B` saves | PLRS, PRTY (`$64E1`) |
| a character dies | `$7076` -> `$70B4` | `$64BD` or `$64E1` |
| the whole party dies | `$70AD` ("ALL PLAYERS OUT!", then `JMP $70B0` forever) | as above |

So every town visit is a save point, and a death is written to disk at once.

**Player records.** PLRS holds four 64-byte records: +0 the name (bit 7 set, NUL
terminated), +`$0F` torches, +`$11` the status letter, +`$1A` hit points and +`$1C`
their maximum (BCD, high byte first). PRTY +1 is the party's size (0: no party formed).

**The pristine state.** On an unplayed disk B, ROST and PLRS are all zero, PRTY is zero but
+4 = `$08` and +5 = `$FF`, and SOSM is zero but +`$FC` = `$02`. SOSA is the 64 x 64 map
without monsters or transports. ULT3 loads SOSA and writes it back at every save, and
nothing resets it. Forming a party writes only ROST, PLRS and PRTY. The original's model
is to copy the Player Master with `COPY` before playing. **No copy of SOSA exists
anywhere else** on either disk: its 64-byte rows and 16-byte chunks were searched against
every other catalog unit and both whole images, and `MAPA`-`MAPL`/`MAPZ` differ from it
in 2301-3810 of 4096 bytes. Of the disk B dumps
compared, the one taken as the reference is very likely pristine (an empty roster, no
monsters). An empty roster alone says nothing about SOSA: two played dumps have the
roster zeroed and the world still played.

**What play writes into SOSA, and what records the tile underneath** (ULT3; the five
writers below were traced, not every store into the map):

| Write | Code | The tile underneath |
|---|---|---|
| a monster (SOSM entry n: tile +n, x +`$40`+n, y +`$60`+n) | | SOSM +`$20`+n |
| a chest where a monster dies | `$525D`: `$24` + ((under-tile >> 2) & 3); water under it: water, no chest | the chest's low two bits; opening it (`$5AFA`) writes `(v & 3) << 2`, or `$20` for 0 |
| the moon gate (`$88`) | `$6EBA`: grass (`$04`) on all eight gate squares (`$77C5` x, `$77CD` y), then `$88` on the phase's (`$6E88` - `$B0`) | grass; the pristine map has the gate on entry 4, (15, 29) |
| the whirlpool (`$30`) | `$74C3`: moves by SOSM +`$FE`/+`$FF` onto water (or a frigate, `$2C`), writes water behind it (`$74FC`) | water; its square is SOSM +`$FC`/+`$FD` |
| a parked craft (frigate `$2C`, horse `$28`) | X-it (`$6951`): `LDA $0E / ASL / STA ($7E),Y` on a square below `$05`; Board writes water (`$52D0`) or grass (`$52B2`) where it took the craft | by the craft: a frigate sails only on water and the whirlpool (`$71AD`), so it parks on water; a horse cannot stand on water, so it parks on grass |

Putting these back returns Ultima III Gold's SOSA (10 squares) to the pristine map exactly. A chest
on mountains is `$24`, as is one on a floor: what was under it is lost. Gold's trainer keys
S and H jump into Board's write, so on Gold they leave water or grass wherever the party
stood, with no record.

## Engine notes

Findings about ULT3, SUBS and UPDT, used by the cart's changes. Scopes are as stated.

**Keyboard.** The KERNAL's IRQ fills the queue (`$0277`, length `$C6`). `$B80C` (`$B952`)
reads `$0276,X` with X = `$C6`: the **last** key queued, without removing it. ULT3's
command loops (`$50A9` the surface, `$6F25` "which player?", `$72D8`, `$7FFD` combat,
`$8B6D` the dungeon, `$8F25`) and SUBS' key wait (`$4E9C`, its poll at `$4EB4`) each do
`JSR $B80C / CMP #$FF / BEQ (wait) / JSR $B80F` (the flush). So of keys typed ahead only
the last one counts, which makes the game feel unresponsive. `$8198` polls without a
flush. ULT3 also flushes before its prompts.

**The idle loops redraw continuously.** The command loop (`$509D` -> `$46F3` -> SUBS
`$4A68`) runs all of UPDT on every key poll, and the key wait behind every prompt
(`$72C0`) runs the blit alone (`JSR $CA03` -> `$CB01`). So the redraw time is both the
animation frame time and the worst-case delay before a key is noticed. About 20 more sites
call UPDT after actions. A redraw takes about 191-201k cycles (about 200 ms on PAL),
measured in a 6502 simulator over SOSA at three party positions. The line-of-sight pass
before the blit is 34-44k of that.

**A move on the surface.** A direction key (`$50AC`; Gold's dispatcher sends `@` to
`$6DAD`, `/ ; :` to `$93B2-$93C7`) prints the direction's name with a newline, which
scrolls the message window (SUBS `$4770`), and checks the square (`$70E1`). On a free one
the footstep plays (`$710A-$7135`), the party moves, and the turn goes on at `$6D38`: the
turn's bookkeeping (`$72EC`: food at `$73D1`, poison), the party's panel (`$71D3`), the
wind (`$6E44`), then `$780B`: the monsters appear (`$783A`) and move (`$78AF`) -- on a
horse (`$0E` in `$14-$17`) only every other turn -- and back to the prompt (`$507E`). The view is
not drawn in the turn: the idle loop's `$CA00` draws it before the next poll. `$72EC`
ends with `JSR $71D3`, and all three of its callers (`$6DC0`, `$7F72`, `$8DD0`) call
`$71D3` again right after it, so the panel is drawn twice every turn.

**The view's line of sight.** UPDT (`$CA09`) copies the 11 x 11 squares around the party
from the map into `$9900` (each byte shifted right and masked with `$7E`; off the map's
edge `$0F`, or wrapped when it is negative), the party's own tile at `$993C`. Then
(`$CA99-$CB00`) for each square from index 120 down to 0 it walks toward the party, x and
y each a step nearer (`$CBE8`, `$CBF3`), and marks the square `$48` (dark) if a square on
the way holds `$06`, `$08`, `$46` or `$48`. A square's walk goes on as its first step's
does, so the order the squares are taken in makes no difference to the result. The blit
(`$CB01`) then draws every square.

**The message window** is text rows 17-23, columns 24-39. A newline (`$FF` in a string,
`$475B`) scrolls it with SUBS' `$4770`: rows 18-23 copied up a bitmap line at a time, the
screen RAM (the colours) every eighth line, then 16 spaces printed into row 23 through the
glyph printer (`$48C5`), which also sets each one's colour through the DOS module's
`$B81E` (`$B895`, the colour from `$B851`).

**Sound.** The effects (`$470E` -> SUBS `$4D3D`, A = `$FF` down to `$F6`) are the Apple's
speaker: each toggles bit 7 of `$D418` through the DOS module's `$B818` (`$B930`, the state
in `$B93E`; voice 3 set up by `$B8CE` to give the toggle a level), with delay loops
between, and blocks until it is done. `$4D3D` plays nothing while `$20` is non-zero. The
footstep is effect `$F6` (`$4E7C`: eight toggles, each after `$D012 + $D41B` `DEX` loops,
about 5k cycles), a fixed loop (`$710F`, X = 255 by Y = 32, 41k cycles), `$F6` again,
and on a horse (`$0E` = `$14`) another loop and a third `$F6`. MUSI's IRQ handler (`$9A75`, put
into `$0314` by `$9A00`, the KERNAL's in `$032E`) runs the player (`$9A86`: Shift-CLR
(`$93`) toggles the music, `$9A74`), which writes `$D418` = `$0F` at every IRQ while the
music is on, then goes on to the KERNAL's.

**Tile and font layout.** The C64 port keeps an Apple-like layout. SHPS (64 tiles of 16 x
16) is 16 rows of 128 bytes: row r, tile t, byte b at `$0800 + r*$80 + t*2 + b`. TEXT is
8 rows of 128 bytes (`$B400 + r*$80 + c`). SUBS' 16 animation frames at `$4100-$42FF`
are `$4100 + i*32 + r*2 + b`. The blitter walks the view one bitmap row at a time with
self-modified single-byte copies. **Readers of this layout** (a byte-pattern scan of every
code unit for absolute addresses into `$0800-$0FFF`/`$B400-$B7FF` and `LDA #$08/$0C/$B4-$B7`
pointer set-ups): UPDT's blitter (`$CB01-$CBE7`), SUBS' glyph printer (`$48CE-`) and
animations, BOOT's title-menu blitter and animations (`$1369-$14F1`), and one copy of the
animation code in DDRW at `$1CB2-$1CFF`. That copy has no callers from DDRW or ULT3 and
uses BOOT's variables at `$1400`: it is a stray copy of BOOT's page `$1400`, not live
code. A byte-pattern scan can miss computed pointers.

**`$62`, where the party is**: 0 on Sosaria, positive in a town or castle, negative in
Ambrosia and in combat (`$80` in combat). Dungeons have their own dispatcher.

**Food.** `$73D1` `LDA #$10 / JSR $7463`: 0.10 food per living member per turn. It is the
food routine's only caller.

**Idle turns.** Three keyboard timeouts pass a turn: surface and towns `$5096` (`DEC $22 /
BEQ $50E9`, "Pass"), combat `$7FF4` (`DEC $22 / BNE $7FFD / LDA #$A0 / JMP $8007`, a
space), the dungeon `$8B66` (`DEC $22 / BNE / JMP $8BF5`, "PASS").

**Torches.** Ignite ("WHOSE TORCH-", `$5F63`) takes the character's torches, record byte
`$0F` through `($7E),Y`, with `SED / SEC / SBC #$01 / STA ($7E),Y`, then lights (`$4C` =
`$FF`).

**"Which player?"** is `JSR $6F04`, from 23 call sites.

**Other** (O, "CMD:", where EVOCARE is) checks words by their last letter and length only;
"NO EFFECT!" is printed from `$61DA` (`JSR $46C3`, the inline print).

**Fights the party did not start**: a monster stepping onto the party (the monsters'
turn at `$78AF`, X = the monster, `$78D5 JMP $5249`, which is Attack's own entry; on the
surface, in towns and in Ambrosia), and a dungeon's random encounter (`$8DF4`: on an empty
square a roll against the level; `BMI $8E01`, where `LDA $23 / CLC / ADC #$02` picks the
encounter; the other way continues at `$8B2B`). Found from the `L CON@` load at `$7E9C`
and its callers.

**Peering at a gem.** ULT3 loads `OUTM` on the surface (`^D "L OUTM"` at `$642F`) or `DNGM`
in a dungeon (`$8DB6`) to `$9400` and calls it (`JSR $9400`). OUTM draws the 64 x 64 map as 2 x 2
hires pixels a tile, white dither patterns on black, a pixel left of the view's middle,
and blinks the party until a key. DNGM draws the level's 16 x 16 squares as glyphs in
cells 4-19 of the view, a `*` blinking on the party, then the dungeon view is redrawn
(DDRW `$1800`). The overlay window `$9400-$97FF` is shared: SHP0, SHP2, SHP3 and SHP6
fill all four pages.

**The weapon shop** (SHP3, `$9400`) buys one item per purchase: `$9502` `ADC #1`.

**SUBS entry points** used by overlays: `$46C3` print the inline string after the
`JSR`; `$46CC` clear the view; `$46D5` a glyph at (`$79`, `$7A`); `$46DE`, `$46EA`
number input; `$4708` the tile at (`$02`, `$03`); `$4711` read a key. `$4300`/`$43C0`
are the bitmap address tables of the view's lines.

## Analysis pitfalls

- **Inline strings stop a tracer.** Subroutines take inline data after the `JSR` (the
  `PLA`/`PLA` trick, e.g. EXOD `$824B`), so a recursive-descent disassembly runs into
  text and stops. Seed traces from many entry points, or skip inline strings.
- **Linear byte-pattern scans mostly hit data.** A search for `85 01` and the like
  across the images hits map and conversation data far more often than code. Every
  candidate needs its context disassembled.
- **Say which disk.** A block number without its disk is ambiguous.
