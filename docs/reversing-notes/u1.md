# Ultima I (C64): disk I/O, memory map, data and save formats

Ultima I is (c) Origin Systems / Lord British. These notes describe the original C64
game on its one disk, independent of the cart. How the cart replaces the disk code is in
`docs/developer/u1.md`.

All addresses are **runtime** addresses. The `$2000` load address in almost every file's
PRG header is vestigial: the loader always calls `SETLFS` with secondary address 0, so
the KERNAL discards the file's own header and loads to the address the loader supplies.

Addresses, tables, call sites and the `$00`/`$01` usage below were read directly out of
the binaries and cross-checked. Where something is inferred rather than read, it says so;
the last section collects the caveats.

## Boot chain

```
u1 ($02D7)     LOAD "HELLO" with SA=0 to $8000                    -> JMP $8000
HELLO ($8000)  SEI; $01=$36; mask both CIAs
               NMI    $0318/19 -> $CE00 (a single RTI)
               CHROUT $0326/27 -> $1FFE (CLC/RTS: suppresses KERNAL messages)
               copy $8400-$8BFF -> $C000          (the disk driver relocates itself)
               prompt for the drive type -> $B000; OPEN 15,8,15,"I0"
               load index $0E ("LO" -> $0800); save index $00 ("DD")
                                                                  -> JMP $0C00
LO ($0C00)     VIC: $D011=$37, $D016=$08, $D018=$18
               load index $05 ("OU" -> its cache at $E000, via $C486)
               load index $0C ("IN" -> $6800, via $C480)          -> JMP $6800
```

Interrupts are masked at boot (`SEI`, and `$7F` to `$DC0D`/`$DD0D`) and never re-enabled
by the game. NMI is neutralised by the `RTI` planted at `$CE00`, so RESTORE does
nothing. The only `CLI` is inside the fastloader at `$C13E`. HELLO copies eight pages to
`$C000`, but its file only reaches `$89FB`: the last 516 bytes of that copy are whatever
RAM held. The driver proper is `$C000-$C5FB`.

The drive-type prompt (HELLO `$8188`, "Please enter which type of disk drive you will be
using") accepts `1` or `2` and stores the answer at `$81B9`; the byte goes to `$B000` and
is saved as `DD`. If it is not `2`, HELLO installs the fastloader by pointing the ILOAD
vector `$0330/$0331` at `$C042`.

## The disk driver

Every disk-related routine is in **one block of about 1.5 KiB**. It ships at
`$8400-$89FB` inside `HELLO` and runs at **`$C000-$C5FB`** (a delta of `$3C00`). No
other module contains disk code; they only `JSR` into this block.

| Address | Purpose |
|---|---|
| `$C000` / `$C003` | fastloader on / off: patches the `$0330` ILOAD vector, prints "SIZZLE ON/OFF" |
| `$C042` | the fastloader's ILOAD replacement; falls back to `$F4A5` when verifying or when the name starts with `$` |
| `$C148` | advance the destination pointer `$AE/$AF` by Y |
| `$C155` | M-W uploader: 32-byte chunks to drive address `$0146` |
| `$C195` | `LISTEN $BA` + `SECOND #$6F` (the command channel) |
| `$C19F` | `"M-W"` + address (`$C1A2/$C1A3`, self-modified) + count |
| `$C1A5` | `"M-E"` + `$0146` |
| `$C1AA` / `$C1BA` | serial bit-pattern tables, patched with the live `$DD00` line state |
| `$C1DA` | fast send: page -> `$C600`, then bit-banged out; waits on `BIT $DD00 / BVS` |
| `$C22C-$C26B` | 64-byte 1541 bootstrap, written to `$0146` with M-W and started with M-E |
| `$C26C` | fast receive of a block; raster-synced through `$D012` and `$D011 AND #$07` |
| `$C2B2-$C4B1` | the 512-byte main 1541 routine, pushed over the fast channel |
| **`$C480`** | **load file by index X** (with the OU special case) |
| **`$C483`** | **save file by save index X** (scratches `"S:xx"`, then KERNAL `SAVE`) |
| **`$C486`** | **plain load by index X**, no special case |
| `$C489` | "save next": `LDX $C4F8`, adds 2, then saves |
| `$C48E` | the save implementation |
| `$C4F9` | the OU special case: if X = 5, bank the KERNAL out (`$01 AND #$FD`) and copy 24 pages from `$E000` to `$8C9E` instead of touching the disk; returns C clear |
| `$C52C` | the load implementation |
| `$C564` | read the drive's error channel; C set on failure (first byte not `'0'`) |
| `$C593-$C5FB` | the name and address tables (below) |
| `$C600-$C6FF` | the fastload receive buffer: `$C600` status, `$C601` count, `$C602/03` address |

`$C4F8` holds the current character's number (0-3), so `$C489` saves that character's
`P` file (inferred from the arithmetic: save index 2-5 are `P0`-`P3`).

The fast loader is the game's own 2-bit protocol with drive code uploaded to the 1541.
Answering `2` at the drive prompt leaves the stock KERNAL load in place.

### Every call site in the game (13)

```
HELLO  $80A0 JSR $C480      LO  $0C93 JSR $C486      TW  $8CDA JSR $C480
       $8113 JSR $C480          $0C98 JSR $C480          $8CDF JSR $C480
       $8118 JSR $C483
GE     $8CA0 JSR $C480      CA  $8CDC JSR $C480      OU  $965B JSR $C489
       $8D77 JSR $C480          $8CE1 JSR $C480
       $8EE0 JSR $C483
       $9349 JSR $C483
       $9353 JSR $C483
```

(OU's call is at file offset `$09BD`; see "Overlay bases" for why the runtime address
is `$965B`.) Nothing else in the game calls the KERNAL for I/O. The `$88xx` KERNAL calls
a raw scan of `HELLO` shows are the pre-relocation image of `$C4xx`, the same bytes.

## File tables at `$C593`

- `"S:"` prefix for the scratch at `$C593`; the name buffer for `SETNAM` at `$C595/$C596`
  (two characters)
- names: `$C597 + 2i`
- load addresses: `$C5C3 + 2i`
- save start: `$C5E3 + 2j`, save end: `$C5EF + 2j` (j = i - 16)

The save-name table at `$C5B7` is the main name table from index 16 on, so save and load
indices share one numbering: `LDX #$01` before a save means `RO`, not `MA`.

| i | Name | Loads to | Content |
|---|---|---|---|
| 0 | TC | `$4000` | data: the ten town and castle layouts (to `$5DEC`) |
| 1 | MA | `$C700` | data: the settlements' glyph set, 1 KiB |
| 2 | PL | `$6400` | a player record; not on the disk |
| 3 | FI | `$6420` | data: sprites / figures |
| 4 | GE | `$8C9E` | overlay: character creation (and the world map, below) |
| 5 | OU | `$E000` | overlay (outdoors), cached; see below |
| 6 | DN | `$8C9E` | overlay (dungeons) |
| 7 | TW | `$8C9E` | overlay (towns) |
| 8 | CA | `$8C9E` | overlay (castles) |
| 9 | SP | `$8C9E` | overlay (space) |
| 10 | TM | `$8C9E` | overlay (time machine) |
| 11 | ST | `$0C00` | the resident game kernel |
| 12 | IN | `$6800` | the intro |
| 13 | MI | `$7400` | starts with `JMP $8C9E` |
| 14 | LO | `$0800` | title and loader, entry `$0C00` |
| 15 | PR | `$12C0` | on the copy-protection track |
| 16 | DD | `$B000` | saved `$B000-$B000` (1 byte: the drive type) |
| 17 | RO | `$B000` | saved `$B000-$B03F` (64 bytes: the roster) |
| 18-21 | P0-P3 | `$81E2` | saved `$81E2-$83AB` (458 bytes each: a character) |

The overlay purposes (DN dungeon, TW town, and so on) are inferred from load order, size
and entry behaviour, not from strings in the binaries. MA and TC were identified by
following the code that uses them and checking the screen in an emulator.

## Overlay bases

The bases were confirmed by counting how many of a module's internal `JSR`/`JMP abs`
targets land inside `[base, base + length)` for each candidate base:

```
module  len     $8C9E       $2000      $E000
OU      5292    120/527     28/527     3/527     -> $8C9E
DN     10090    225/580      9/580     3/580     -> $8C9E
SP      9109    203/521     13/521     2/521     -> $8C9E
TM      8296    197/537     17/537     8/537     -> $8C9E
TW      8637    195/926     61/926     8/926     -> $8C9E
CA      5646    110/604     39/604     8/604     -> $8C9E
GE      5674     36/366     38/366     1/366     -> $8C9E (ambiguous by fit;
                                                   decided by its entry code)
ST      4999     78/141 @ $0C00                  -> $0C00
IN      7386     58/106 @ $6800                  -> $6800
MI      6350    159/448 @ $7400                  -> $7400
TC / FI          mostly data, a low fit either way -> data
```

GE is assigned to `$8C9E` on the strength of its coherent entry code (`LDX #$11 / JSR
$C480`, load the roster) and its sane `$01` sites.

**OU has two addresses.** It is assembled for `$8C9E`, not `$E000`. LO loads it once to
`$E000` (RAM under the KERNAL) through `$C486`, and `$C4F9` copies 24 pages from there
into the overlay slot whenever the game asks for index 5. An address taken from a scan
of OU based at `$E000` is `$535E` too high.

`MI` (`$7400-$8CCD`) overlaps the first 48 bytes of the overlay slot, and its first
instruction is `JMP $8C9E`. Its dispatcher at `$8C9E` runs `SEI`, resets the stack, loads
ST (index `$0B`) to `$0C00`, then attempts PR (index `$0F`) to `$12C0`. The exact
interplay between MI and the overlays in that slot was not traced.

## Copy protection: track 6 and `PR`

The reference `.d64` is **175531 bytes, not 174848**: it carries a 683-byte error map
after the data area, and the map is load bearing.

- **All 21 sectors of track 6** are flagged `$02`, DOS error 20, "header block not
  found". The track is unreadable by normal DOS.
- **Track 6 is fully allocated in the BAM** (0 of 21 free), so DOS never writes there.
- **`PR`'s directory entry points at track 6, sector 5**, claiming 2 blocks.
- `MI` at `$8CA9` does `LDX #$0F / JSR $C480`, loading `PR` to `$12C0`, and **ignores
  the returned carry**. The next instruction is `JSR $1655`.

`$12C0-$13BD` in the shipped `ST` is a **254-byte monotonically ascending table**, not
code. 254 bytes is exactly what a 2-block `PR` would deliver. So `PR` and that table
occupy the same window, and what the game ends up with depends on whether the load
succeeds. A whole-disk copy that *formats* track 6 turns the failing read into a
succeeding one and overwrites the table with whatever the copier wrote there.

**What the image cannot settle:** whether track 6 originally held data that only the
game's own uploaded 1541 code could read (the driver can push arbitrary drive code, so
a non-standard format is possible), or whether it was left blank so that the load always
fails and the shipped table stands. A `.d64` represents both the same way. Deciding it
needs a flux-level dump or a trace of the uploaded drive code. On an original disk as
dumped, the load fails and the table in `ST` is the one in use.

`PL` (index 2) has a table entry but no file on the disk.

## Save formats

The writable files are `DD`, `RO` and `P0`-`P3`, and they are the only writes the game
makes:

- `DD` -- written by HELLO on every boot (`$8118`).
- `RO` -- written by GE (`$8EE0`, when a character is terminated, and `$9349`).
- `P0`-`P3` -- written by GE (`$9353`, at creation) and by OU through `$C489`.

### Roster (`RO`, 64 bytes at `$B000`)

Four 16-byte records, one per seat, indexed as `P0`-`P3`:

```
+00  $FF      the seat is in use (inferred from the terminate code)
+01  $00 $00
+03  name, 13 bytes, NUL-padded
```

An empty roster is 64 zero bytes.

### Character (`P0`-`P3`, 458 bytes at `$81E2-$83AB`)

Read from scratched saves and the game's own code; little-endian 16-bit fields:

| Offset | Field |
|---|---|
| `+$0C` / `+$0D` / `+$0E` | readied spell / weapon / armour (MI's Ready, `$8801`/`$8810`/`$881F`; Ztats marks them with a dot) |
| `+$31` + vehicle | vehicle counts (`$8213` + vehicle number; the horse is 1, so `+$32`) |
| `+$4A` | sex (0 male, 1 female) |
| `+$4B` (`$822D`) | character name, NUL-padded |
| `+$59` | hit points |
| `+$5B`-`+$65` | the six attributes |
| `+$67` | coins, in copper pence (1234 = 12 gold, 3 silver, 4 copper) |
| `+$69` | race |
| `+$6B` | class |
| `+$78` | food |
| `+$7A` | experience |
| `+$82`, `+$83` | a random seed (below) |

`+$82/+$83` differs per save. It is not a checksum: GE stores two random bytes there at
creation (`$25BA`/`$25C0`: `JSR $1670 / STA $8264`, `STA $8265`), and SP copies them to
`$FC`/`$FD` as it starts. No other absolute reference to `$8264`/`$8265` is in any file
on the disk (a static scan of every file), so nothing checks them.

The field layout from `+$59` on follows the notes of C64UltimaEditor (zoggins' save editor
for Ultima I-IV); all of these fields were checked against the game's Ztats screens, and
those the screens do not show against the code.

### The reference disk's saves

The reference disk **has been played and then blanked**. In the live directory there is
no `P0`-`P3`, and `RO` is 64 zero bytes, so the game sees no saved game. Scratched
entries survive with their blocks freed and not overwritten: a roster, three of the four
characters (`P1`-`P3`, each a full 458-byte payload with the header `$81E2`) and an
earlier `DD` (`$01`; the live one is `$02`). `P0` is absent: no directory entry, live or
scratched, and a sweep of the whole disk for the `$E2 $81` header finds only the three.
These are useful test data: restoring the directory type byte to `$82` and re-allocating
the blocks in the BAM makes them loadable again.

**The blanking was not done by the game.** The live `RO` carries the load address
`$2000`, but the save table writes `RO` from `$B000`, so a roster the game wrote would
carry `$B000`, as the scratched `RO` and the live `DD` do. Across the Ultima I images
examined (13), every data file other than the saves is identical by content, except
two bytes of `TC` in one cracked version.

## The game's data

### The world

**The world map is in GE** (character creation), at file offset `$959`. GE puts it at
`$D000`; OU copies those 13 pages to `$B000` when the party goes outdoors (OU `$8C9E`) and
back (`$9279`). There are four offsets, one per continent (the continent is `$81E4 & 3`),
each to run-length data: count in the top five bits, tile in the low three, stored x 2
(OU `$9840`), decoded into a 64 x 64 map at `$6400`. Tile kinds: 0 water, 1 grass,
2 forest, 3 mountains, 4 castle, 5 landmark, 6 town, 7 dungeon.

MI holds the 84 places: `$7C18` the y coordinate with the continent in bits 6-7, `$7C6C`
x, names from `$7CC0` (the last letter of each with bit 7 set). Each place lands on a
square of its own kind. Dungeons are generated in play.

### Tiles and the view

**ST's first 2 KiB are the outdoor tiles, not code.** The view renderer (ST `$1C8A`) draws
19 x 9 tiles around the party. Tile v = (map byte & `$7E`) / 2; monsters are `$20-$58`,
alternating by a table at `$B700`. It copies 32 bytes a tile from `$0C00 + 32v` (through
the pointers at `$14C0`,v / `$1480`,v): the first 16 the upper two cells, the next 16
the lower two, and puts the colour `$1500`,v in both cells' screen RAM. ST animates four
tiles in place (`$1DB5`): the water (`$1B06`: cells swapped, rows rotated) and byte pairs
of the castle's flag, the town's and tile 12.

The renderer runs on every key poll: ST `$1E50` (`$167C`, which OU's key wait `$8DD0`
calls up to 128 times before a turn passes) draws the view before it looks at the key
queue, and OU calls it directly too (`$166A`, six sites). Each draw is all 171 cells into
the hidden bitmap (~100k cycles), a key read at each tile row, then the flip (`$1DB2
JSR $1700`), which waits for the raster to pass line 255 (`$1C81`) and plays out every
queued sound effect (`$171A`) before it returns; the animation steps after it (`$1DB5`,
then on into the key read at `$1E08`). Outdoors a draw is six frames on a PAL machine, so
the water and the flags step every six frames (VICE), and the monsters' frames, picked
anew at every draw (`$178E`, one on per monster, into the table at `$B700`), change as
often. So a key
is acted on only after the draw under way ends, and a step is seen only once the next
poll has drawn it.

### Towns and castles

TW and CA load TC (to `$4000`) and MA (to `$C700`). **TC holds the ten settlement
layouts**: layout n is found through TC's pointers, `$4000 + 2n` for the two castles and
`$4004 + 2n` for the eight towns, and copied to `$CB00` (TW `$8CF5`, CA `$8CF7`: three
pages, `LDA abs,X` self-modified / `STA $CB00,X`). The place's number in its continent
picks n (castles 0-1, towns 13-20 less 13), so each layout serves one place per
continent. A layout is 18 rows of 38 glyphs (printed through MI `$83D7`, TW `$A51A`),
then 16 people: `$CDAC` type (bit 7: none), `$CDBC` x, `$CDCC` y.

**MA is a glyph set**: TW swaps it in over the text font at `$0800` while it draws a
settlement (TW `$A553`). Glyph g is `$0800 + 8g`, hires, its colour `$1530`,g (TW's
colour table at `$A887`, CA's at `$A22B`, swapped in with it). The same routine swaps
both back before the people are drawn, so a person of type t is glyph `$AD98`,t (CA
`$A21D`,t) of the text font (the first KiB of LO), in ST's own colours; the player is
glyph `$7B`.

### Text

Ultima I has no Talk command: kings and shops answer Transact, the pub's keeper a drink.
The text is inline strings (printed through `JSR $848E` / `$848A`) in TW, CA, OU, TM, SP
and DN, and in MI's tables. The kings' quests are chosen by castle (CA `$8CB7`); the eight
rumours are in TW (`$ADEA`).

### Outdoors: commands, lands, vehicles

OU's command loop (`$8CFB`) prints the prompt, waits for a key (`$8DD0`: 128 polls, then
a turn passes) and hands it to MI's `$85FD`, which looks it up among the 25 keys at
`$81C9` (`@ / ; :` north, south, east, west, space Pass, then `A B C D E F G H I K N O Q
R S T U V X Z`): the index picks OU's routine from the table at `$9E29`, called at
`$8D42`. A key not there prints "Huh?" and returns C set. Either way the monsters move
next (`$9A2F`).

- **The party**: `$20`/`$21` x and y, `$81E4` the land (0-3; `$81E5` the land in bits
  6-7). `$81E8`/`$81E9` keep x and y while a town, castle or dungeon is played.
- **The lands' edges** (`$97F6`, after every step): a land is 64 x 64 with ten squares
  of sea beyond. x past 73 is the next land (x = -10), x below -10 the previous (x = 72);
  y past 73 is the land two back (y = -5), y below -10 the land two on (y = 67); the land
  number wraps at 4. Then `$983D`: `$9A10` takes the monsters off the object list,
  `$9840` decodes the land's map at `$6400` and puts the land's objects on it (each over
  the square it saves), and `$9916` counts the vehicles again.
- **Objects** (monsters and vehicles left outdoors), in the character record: the count
  at `$826B`, then per object x (`$826C`,i), y with the land in bits 6-7 (`$82BC`,i), its
  tile (`$830C`,i) and the tile under it (`$835C`,i). A vehicle is tile `$08`-`$0F`, a
  monster `$20`-`$59` (the map byte / 2, `$9D50`).
- **Vehicles**: `$81F1` the one the party is in -- 0 on foot, 1 horse, 2 cart, 3 raft, 4
  frigate, 5 aircar, 6 shuttle, 10 time machine (7-9 are the space ships; the names are
  MI's table at `$7930`). Board (`$9053`) takes the vehicle under the party off the map
  (`$9CD8`), sets `$81F1`, the party's tile (`$9E0B`) and the view, and says "Mount" and
  the name for a horse or a cart, the name for the others (`$90B2`); a shuttle launches at
  once (SP), the time machine needs the four gems (`$81EA`-`$81ED`). With nothing to
  board, "nothing to Board!" (`$9082`). X-it (`$9677`) puts the vehicle on the map on
  water, grass or forest (`$9CA6`), else "Thou canst not leave it here!". `$8213`,v, the
  counts Ztats lists, are counted again from the objects and `$81F1` whenever a land is
  entered (`$9916`); on death the vehicle the party was in is lost, and every weapon, and
  nothing stays readied (`$8D60`).
- **Text**: the message window is the four lines under the view, 30 columns, the first
  of each line the prompt's (`$2E`-`$33`: left, width, top, bottom, column, row). A
  command's name is printed after the prompt, and its message usually goes to column 1
  of the same line (`$83F6`), over the name.

### Thieves

- **Iolo the bard** (TW `$A40C`) and **the jester** (CA `$9D39`) step each turn. When the
  party is the square they would step on, they steal (TW `$A457`, CA `$9D88`): one of
  every weapon the player carries but the readied one (`DEC $81F8,X` for X = 15..1; `$4C`
  counts the kinds). Whether the player is told is a separate roll: CA prints "The jester
  stole something!" if a random byte is below 128 + wisdom (`$8245`); TW compares the
  random byte with `$4C`, the number of kinds taken (`$A47A CMP $4C`, where CA has `$9DAB
  CMP $4D`), so "Iolo stole something!" shows at most 15 times in 256. The code is
  otherwise the same, so the bard's is very likely a slip (inferred).
- **A thief in a dungeon**: a monster's attack that lands picks a special attack by
  `$A86B` + `$A874` (`$9DD3`; jumps at `$9E81`-`$9E8A`): `$17` steals, `$1E` destroys the
  worn armour ("Armour destroyed!", `$9EFC`), `$25` halves the food ("A gremlin stole some
  food!", `$9F27`), `$2A` "Mental attack!" (`$9E8A`); the rest hit (`$9DF6`). The
  stealing (`$9EAF`) takes one of the first weapon the player carries but the readied
  one, "Thief stole a ..."; with none, it hits. (Which monsters these are is from the
  messages; what `$A86B` and `$A874` hold was not traced.)

### Keyboard

The game reads the keyboard itself, with interrupts off: ST `$1ED5` reads the joystick in
port 2 (its directions are the keys `@ / ; :`, its fire the key at `$1632`, which OU sets
to A, `$8CC6`), else calls
the KERNAL's `SCNKEY` and `GETIN` (`$1EEF`); the cursor keys become the direction keys, a
key held down is taken once (a direction repeats). `$1E08` puts it in the game's own
queue (`$4E-$55`, count `$56`), and `$1E3E`/`$1E50` take it from there with bit 7 clear:
F7 (`$88`) arrives as `$08`.

A key held down is new at every read (`$1F7A` puts `$FF` in the KERNAL's last key, `$C5`),
so a release, seen by any read, ends a repeat, and the next press is taken at once. A
direction held repeats by CIA 1's time of day, which every key taken resets (`$1F6F`):
after five tenths, then after two (`$1637`; `$1F46`). The KERNAL leaves the clock's input
at 60 Hz, so on a PAL machine a tenth is 0.12 s: the repeats come 0.6 s and then 0.24 s
apart (VICE), each when the next key read sees it due.

Outdoors a turn passes after 128 polls without a key (OU `$8DD0`). Each poll draws the
view and flips on the frame (above), six frames: 15.32 s on a PAL machine (VICE). DN's,
TW's and CA's waits (`$1679` -> `$1E44`) draw nothing.

## Memory map

```
$0000-$00FF  zero page
$0100-$01FF  stack
$0200-$03FF  KERNAL workspace
             $02D7  boot stub (u1)
             $0318  NMI    -> $CE00 (RTI)
             $0326  CHROUT -> $1FFE (CLC/RTS)
             $0330  ILOAD  -> $C042 (fastloader) or $F4A5 (KERNAL)
$0400-$07E7  screen 0
$0800-$15DA  LO (title and loader), entry $0C00; later overwritten by ST
             $0800-$0BFF  the text font (also swapped with MA in settlements)
$0C00-$1F86  ST, the resident game kernel; overlays call into it ($1632, $1655, ...)
             $0C00-$13FF  the 64 outdoor tiles, 32 bytes each (data)
             $12C0-$13BD  the table PR would overwrite
             $1500        the tiles' colours
             $1E28        the VIC double-buffer table
```

### Graphics: double-buffered across VIC banks

The game runs in hires bitmap mode (`$D011 = $37`). Table at ST `$1E28`, page flip at
ST `$1700` (toggles on `$5C`):

| Frame | `$DD00` | VIC bank | `$D018` | Screen | Bitmap |
|---|---|---|---|---|---|
| 0 | `$97` | `$0000` | `$18` | `$0400` | `$2000` |
| 1 | `$96` | `$4000` | `$80` | `$6000` | `$4000` |

HELLO's own boot screen differs: `$D018 = $17`, screen `$0400`, character set `$1800`.

ST's drawing routines, through its jump table (`$163A-$16A2`). `$5C` selects the bitmap
drawn into (0: `$2000`/`$0400`, `$60`: `$4000`/`$6000`), `$5D` is `$60` while both are in
use (0 with one, as after a death, MI `$8BFF`):

| Entry | Routine | Draws |
|---|---|---|
| `$163A` | `$178F` | the screen's set-up: SID, VIC, both screens' colours `$10` |
| `$1646` | `$1723` | the bitmap shown copied over the other, all 32 pages, and its screen |
| `$1649` | `$1910` | the window scrolled a row: each row from the bitmap at `$2000` into it and the one `$5D` away; the last row cleared, cursor at its start, then a key read (`$1E08`) |
| `$164C`, `$164F` | `$199E`, `$19A6` | the cursor's row cleared, whole or from the cursor on |
| `$1652` | `$1A48` | the window cleared |
| `$1661` | `$16AD` | the view's area of the hidden bitmap cleared, its colours `$10` |
| `$1664` | `$1700` | the flip |

| `$166A` | `$1C8A` | the view |
| `$168B`-`$1694` | `$1773`, `$17ED`, `$1866`, `$186A` | a point's colour, a point, lines (the dungeons' walls), into the hidden bitmap |

The windows (`$2E` left, `$2F` width, `$30` top, `$31` bottom, `$32`/`$33` the cursor):
`$165B` the message window (columns 0-29, rows 20-23), `$1658` the status (31-40, rows
20-23), `$165E` the view's (1-38, rows 1-18), `$1655` the whole screen. The scroll and the
row clears work in pages of 256 bytes; for a window wider than 32 columns the scroll's
second page reads the first page's source again (its `INC`s at `$198B` raise the
destinations only), so such a scroll would copy wrong bytes into columns 32-39 (read out
of the code; not seen on screen).

## Writes to `$00` and `$01`

### `$00` (the DDR): never written by C64 code

The only `LDA #imm / STA $00` in the game is at HELLO `$87A6` (`LDA #$B0`), inside the
1541 drive-code blob (`$C2B2-$C4B1` after relocation), where `$00`/`$01` are the drive's
job-queue registers, not the C64's port. A raw byte scan also flags many `$06 00`,
`$C6 00`, `$E6 00` sequences in the overlays; those are data, not instructions.

### `$01`: exactly nine sites

| Site | Value | Purpose |
|---|---|---|
| HELLO `$8001` | `#$36` | boot: BASIC out, KERNAL and I/O in, the game's steady state |
| driver `$C4FD` | `AND #$FD` -> `$34` | KERNAL out, to read the OU cache at `$E000` |
| driver `$C524` | `ORA #$02` -> `$36` | restore |
| GE `$8DDF` | `#$30` | all RAM |
| GE `$8DFA` | `#$36` | restore |
| OU `$8C9E` | `#$30` | all RAM; copies 13 pages `$D000` -> `$B000` |
| OU `$8CC2` | `#$36` | restore |
| OU `$926D` | `#$30` | all RAM |
| OU `$9291` | `#$36` | restore |

`#$30` is all RAM: no ROM **and no I/O**. These windows are safe only because interrupts
are masked for the whole run. No site clears bit 5 (the cassette motor).

## Pitfalls when studying the binaries

- **PRG headers lie.** Nearly every module's header says `$2000`; none loads there. Use
  the load-address table at `$C5C3`.
- **OU has two addresses** (stored at `$E000`, run at `$8C9E`).
- **HELLO contains the driver twice over**: `$8400-$89FB` is the pre-relocation image of
  `$C000-$C5FB`, so a naive scan double-counts every KERNAL call in it.
- **The `.d64`'s error map matters.** Read the data area without it and `PR` comes out
  silently empty, with no sign that copy protection exists. VICE's `c1541` fails on this
  image's zero-length `PR`.
- **Save and load indices share one numbering** but index different tables: a save's X
  is the file index minus 16.
- **Byte scans over graphics data produce noise**: `$06 00`, `$C6 00`, `$E6 00` decode as
  `ASL`/`DEC`/`INC $00`. Look for `LDA #imm / STA $01`-shaped patterns instead.
- **Memory that looks idle may not be.** `$C700-$CAFF` and `$CB00-$CDFF` are written only
  when a town or castle is entered, so a watch through the intro and the outdoors alone
  sees them unused.

## Confidence and caveats

- Addresses, tables, call sites and the `$00`/`$01` usage are read out of the binaries
  and cross-checked.
- The overlay purposes are inferred from load order, size and entry behaviour; MA, TC,
  the world in GE and ST's tiles were established from the code and checked against the
  game's screen in an emulator.
- GE's base is the one overlay whose fit is ambiguous; it rests on its entry code.
- The interaction between MI and the overlay slot it overlaps was not traced.
- What track 6 held on the original media is open (see "Copy protection").
