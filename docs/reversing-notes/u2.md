# Ultima II on the C64: reversing notes

Ultima II: The Revenge of the Enchantress (c) Origin Systems / Lord British. These notes
describe the original C64 game, independent of the cart: its disks, boot chain, memory
map, disk layer, save format and copy protection. They come from static analysis of the
two sides of the Origin (Ultima Trilogy) disk, plus later checks recorded below. How the
cart replaces the disk layer is in `docs/developer/u2.md`.

Convention: addresses read out of a disassembly are facts; the *purpose* of a routine is
marked as inferred where it was not traced.

## The disks

| Side | BAM name | Contents |
|---|---|---|
| A, "Program + Galactic" | `GALACTIC DISK` | all the code, and the planets' maps |
| B, "Player Master" | `PLAYER DISK` | data only: Earth's maps, the player record, the save templates |

Side B's `SHAPES` and `MONSTERS` are byte-identical to side A's.

- **Side A carries a 683-byte error map** (the image is 175531 bytes, not 174848). Exactly
  one sector is flagged: **track 18, sector 18, error 5** (data block checksum error, DOS
  error 23). That is the copy protection, below. Side B has no error map.
- The player record has no directory entry: it is raw track 35, sector 16 on side B.

### Editions

Sierra's 1984 release is another edition. Compared by content:

- Side B is byte-identical in both.
- On side A every file matches except two. `ULTIMA` differs only in 44 bytes at file
  offset `+$39FF`, where Sierra's end text has an extra line and the Trilogy's has spaces.
  `INTRO` is not a file on Sierra's side A: it sits inside the 64-block, BASIC-started
  `ULTIMA II` at offset `+$2E4D`, and it is a **different build**: 772 of its 4096 bytes
  differ, mostly in `$C600-$CCFF`, and the code from `$C600` up sits up to `$220` lower.
  So every `INTRO` address in these notes moves on Sierra's edition (`$CED6` is `$CCB6`,
  `$C9C0` is `$C85C`, `$CE89` is `$CC69`, `$CED3` is `$CCB3`). What the changes do has
  not been examined. Sierra's Player disk is named `U II-PLAYER DISK` in its BAM.

Everything below is the Trilogy's side A.

## Boot chain, and lying PRG headers

**PRG header load addresses are meaningless here.** The loader calls `SETLFS` with
secondary address 0, so `LOAD` relocates to the address passed in X/Y and ignores the
file's header. Analysing a file at its header address gives plausible-looking, wholly
wrong disassembly.

| File | Header says | Loads at |
|---|---|---|
| `ULT` | `$02DA` | `$02DA` (the only honest one) |
| `INTRO` | `$6000` | `$C000` |
| `SUBS` | `$6000` | `$4000` |
| `ULTIMA` | `$2000` | `$5000` |
| `STARS` | `$2000` | `$9000` |
| `DNGNDRAW` | `$6000` | `$9680` |

The chain:

1. BASIC `RUN` loads `ULT` at `$02DA`: it blanks the screen (`$D011 = 0`), and
   KERNAL-loads `INTRO` to `$C000` (`SETLFS 15,8,0`), then `JMP $C000`.
2. `INTRO` (`$C000-$CFFF`): `SETMSG(0)`, clear screen, KERNAL-loads `SUBS` to `$4000`
   (the name is at `$C601`). Its own work starts at `$C025`. From there on it uses the
   `SUBS` API for every load: `SHAPES` -> `$0800` (`$C06E`), `DNGNDRAW` -> `$9680`
   (`$C07A`), `STARS` -> `$9000` (`$C088`).
3. The title sequence starts at `$C093`. Its menu offers `<P>` (play, `$CEBC`) and `<C>`
   (create a character). `$CEC2` loads `ULTIMA` to `$5000`; `$CED3` is `JMP $5000`.
4. `ULTIMA` (`$5000-$8A8F`, about 15 KB) is the main program. `INTRO` stays resident at
   `$C000-$CFFF` during play.

| Range | Contents |
|---|---|

| `$0002-$00FF` | Zero page. `$02/$03` player X/Y; `$23/$24` map cursor; `$2F/$30` text cursor; `$38` pending key (bit 7 set while one waits); `$2D/$2E` frame counter; `$4D` blank-screen flag; also `$0A/$0B`, `$0E`, `$2B/$2C`, `$3D/$3E`, `$FB-$FF` |
| `$0100-$01FF` | Stack |
| `$0400-$07FF` | Screen (VIC bank 0) |
| `$0800-$0FFF` | `SHAPES` / `MONSTERS`: the 2 KiB tile character set |
| `$1000-$1FFF` | `MAP xx`: 4 KiB, 64 x 64 tiles, 64 bytes per row. The VIC in bank 0 sees character ROM here, so the map is invisible to it -- deliberately |
| `$2000-$2FFF` | `$2000-$21FF` is game state (`$7BA5` fills it with `$FF` as a new game starts); `$2200-$2FFF` not traced |
| `$3000-$30FF` | `MOB xx` |
| `$4000-$4FFF` | `SUBS`: jump table, raster IRQ, text, sound, disk I/O |
| `$5000-$8A8F` | `ULTIMA` |
| `$8A90-$8DFF` | gap (not traced) |
| `$8E00-$8EFF` | the player record (T35/S16) |
| `$8F00-$8FFF` | `MON xx`: 32 people and monsters, one field per 32 bytes: `+$00` X, `+$20` Y, `+$60` tile (map byte), `+$A0` talk byte (`$81` and up: string n of `TLK xx`, read at `$8230`; smaller values inferred to be movement) |
| `$9000-$9671` | `STARS` |
| `$9680-$9BFF` | `DNGNDRAW` |
| `$9C80-$9D7F` | `TLK xx` (dialogue) |
| `$A000-$B0FF` | map cache in the RAM under BASIC ROM (below) |
| `$B100-$BFFF` | unused: nothing in the game writes above `$B0FF` there |
| `$C000-$CFFF` | `INTRO`, resident (its data ends at `$CFFD`) |
| `$D000-$DFFF` | I/O. The RAM below is never reachable to the game (`$01` is only ever `$36`) and nothing loads there |
| `$E000-$FFFF` | KERNAL, used for LOAD/SAVE and serial I/O |

### `$00` and `$01`

**Exactly four writes, at two adjacent sites, both in `ULTIMA`.** Nothing in `INTRO`,
`SUBS`, `STARS` or `DNGNDRAW` writes `$00` or `$01`.

- `$6809` (restore from the cache): `$00 = $2F`, `$01 = $36`, then copies
  `$A000-$AFFF` -> `$1000-$1FFF` (the map) and `$B000-$B0FF` -> `$8F00-$8FFF` (the
  monsters), and ends `CLI / RTS` with `$01` left at `$36`.
- `$685F` (stash into the cache): the same two writes, then the copies the other way.

`$36` is BASIC ROM out, KERNAL and I/O in. **`$01` is never put back to `$37`**: from its
first map-cache copy on, the game runs with BASIC banked out. Both loops stop at `$B0`,
so the cache is exactly `$A000-$B0FF`. The cache tag at `$6806-$6808` holds the map's two
name digits (`$8E13/$8E14`) and the planet (`$8E37`), so revisiting a map skips the disk.

False positives in a byte scan: `STX $00`/`STY $00` in `INTRO` at `$C691-$C8D4` and
`ASL $01` in `SUBS`/`STARS` are data tables (runs of `$84`/`$86`/`$88`/`$00`), checked by
dumping the bytes.

### Display

A two-way raster split, entirely in `SUBS` (`$4715-$47C5`), from a static table at
`$47C6-$47CF` that `ULTIMA` never writes:

| Address | Value | Meaning |
|---|---|---|
| `$47C6` | `$30` | split 1, raster line 48 |
| `$47C7` | `$D6` | split 2, raster line 214 |
| `$47C8/$47C9` | `$17` | `$D011`: display on, 24 rows, text mode |
| `$47CA` | `$12` | `$D018`: screen `$0400`, characters `$0800` (the tiles) |
| `$47CB` | `$15` | `$D018`: screen `$0400`, characters `$1000` (character ROM) |
| `$47CC/$47CD` | `$08`, `$08` | `$D016` |
| `$47CE/$47CF` | `$0D`, `$0B` | `$D021` |

Rows 0-19 use the tile set at `$0800`, rows 20-23 the ROM font. Nothing writes `$DD00`, so
the VIC stays in bank 0. When `$4D` is not zero the IRQ forces `$D011 = 0`. The IRQ
increments the frame counter `$2D/$2E` at `$47A9`. Nothing in the game calls CINT or
writes MODE (`$0291`; every file scanned), so Shift+C= flips the KERNAL's character set
until the next split rewrites `$D018`.

## `SUBS`: the OS layer

`SUBS` opens with a **59-entry `JMP` table at `$4000-$40B0`**. `ULTIMA` contains no
direct `$FFxx` KERNAL references at all: it reaches the disk only through four of these
vectors.

### Inline parameters, a house pattern

Three subsystems pop the caller's return address, read parameters from the code stream
after the `JSR`, and push a corrected address back: the disk calls (a name and
addresses), the string printer `$4006` (the text itself), and the SID block writer
`$40A2`. A disassembly that treats the bytes after one of these `JSR`s as code shows
garbage.

```
        JSR $408D            ; LOAD
        .byte "MAP 00",0     ; NUL-terminated name
        .word $1000          ; destination
        ; execution resumes here

        JSR $4090            ; SAVE
        .byte "MOB 00",0
        .word $3000          ; start
        .word $3100          ; end
```

### Disk entries and their helpers

| Vector | Target | Function |
|---|---|---|
| `$408D` | `$4B1C` | LOAD a named file |
| `$4090` | `$4B55` | SAVE a named file (sends the `S0:` scratch first) |
| `$40AB` | `$4E6A` | raw `U1`/`U2` block read/write |
| `$40AE` | `$4F2D` | OPEN 15,8,15 (command channel) |

| Address | Function |
|---|---|
| `$4BF0` | pull the return address -> `$2B/$2C` (locates the inline parameters) |
| `$4C05` | length of the inline name -> `$0E` |
| `$4C11` | SETNAM with length `$0E`, pointer `$2B/$2C` |
| `$4C1C` | add the parameter length to the return address, return past the inline data |
| `$4C32` | restore the raster IRQ state (`$D019`/`$D01A`/`$D012`/`$D011`) after disk access |
| `$4C47` | print "ONE MOMENT PLEASE!" |
| `$4F01` | send `B-P:2 0` |
| `$4F3E` | OPEN 2,8,2,"#" (direct-access buffer) |
| `$4F5C` | read the error channel -> `$FD`, CLOSE 2, CLOSE 15, CLRCHN |

A failed load prints "LOAD ERROR! PRESS A KEY TO TRY AGAIN." and loops, which doubles as
a disk-swap prompt. Several command strings are stored backwards: `S0:` at `$4BB5`,
`U1:2 0 ` at `$4ED2` (the digit at `$4ED7` is patched to `1` or `2`), `B-P:2 0 ` at
`$4F54`; `$4ED9` is a `0123` digit table indexed by `$FD`.

The block call's parameters are in zero page: `$FB` track, `$FC` sector, `$FD` operation
(1 = `U1` read, 2 = `U2` write; on return `$4F5C` leaves the error channel's first digit
there), `$FE/$FF` the buffer.

**The disk code is not one contiguous block.** Eleven jump-table entries point into the
range between the disk routines: ten sound effects in `$4CBC-$4E68` (`$40A2` -> `$4CBC`,
`$40A5` -> `$4D04`, `$4018` -> `$4D1D`, `$402A` -> `$4D45`, `$4030` -> `$4D83`, `$4033`
-> `$4DB4`, `$4021` -> `$4DD9`, `$4024` -> `$4DFC`, `$401E` -> `$4E1F`, `$4027` ->
`$4E42`) and the RNG (`$4048` -> `$4F79`). The code that only serves the four disk
vectors is `$4B1C-$4CBB` (416 bytes) and `$4E6A-$4F78` (271 bytes).

Sound: `$40A2` -> `$4CBC` is a SID block writer with inline parameters. It self-modifies
the `STA $FFFF,X` operand at `$4CD5/$4CD6`; the parameters are the target register (a
word) and seven data bytes: the loop stores Y = 3 to 9 and leaves at `CPY #$09` with the
carry set, which `ADC #$08` at `$4CDC` picks up to step past all nine (run in py65: the
click's two blocks write `$D415-$D41B` and `$D40E-$D414`). The ten
effect vectors (`$4018`, `$401E`, `$4021`, `$4024`, `$4027`, `$402A`, `$402D`, `$4030`,
`$4033`, `$40A5`) are built from such blocks plus `$409F` (`$46D4`, a busy-wait delay,
A = duration), ending by gating the voice off. That they are sound effects is inferred
from register usage; which effect each plays was not determined. `$401B` -> `$43BF` also
touches the SID; `$43BA` spins on `$D41C` (voice 3's envelope output).

is seeded from the frame counter `$2D/$2E` and self-modifying by design (`$4FA2-$4FA7`
is its state).

**The file names are self-modifying.** The map loader writes the map's digits straight
into the inline parameter bytes: `$67C2`/`$67C5`/`$67C8` write `$67E0`, `$67EC`,
`$6800`; `$67D0`/`$67D3`/`$67D6` write `$67E1`, `$67ED`, `$6801`; `$6847` and `$684F`
write `$6859`, `$685A`; `$6898` and `$689E` write the cache tag `$6806/$6807`
(initially `$FF $FF`). The digits come from `$8E13`/`$8E14`.

The `MOBX00`/`MONX00` -> `MOB 00`/`MON 00` pair in `INTRO` is new-game initialisation: it
copies pristine templates onto the player disk.

### What the game writes

- `$68AE` skips the whole `MOB`/`MON` save while `$8E37` is not zero, so the game only
  writes `MOB` and `MON` files on the Player disk, when the party leaves a map on Earth.
- `$67F1` skips the `MOB` load unless `$8E14` and `$8E37` are both zero.
- The files written in play are `MOB 00`-`MOB 40`, `MON 00`, `MON 10`-`MON 40` and
  `MON 03` (through the time door), plus the record: twelve units of 256 bytes.
- Each `MOB nn`/`MON nn` on a fresh disk is a byte-for-byte copy of its `MOBXnn`/
  `MONXnn` template on the same disk. `MOBX` files are all `$FF`, `MONX10`-`MONX40` all
  `$00`; only `MONX00` holds real data (a 160-byte table). Across 29 Player Master dumps,
  including played ones, the templates were identical in every one: the game never
  writes them.

## The saved game is not a file

The player record is read and written with raw `U1`/`U2` block commands on **track 35,
sector 16** of the Player disk, with no directory entry:

```
        LDA #$01 / STA $FD   ; 1 = U1 (read), 2 = U2 (write)
        LDA #$23 / STA $FB   ; track 35
        LDA #$10 / STA $FC   ; sector 16
        LDA #$00 / STA $FE
        LDA #$8E / STA $FF   ; buffer $8E00
        JSR $40AB
```

Call sites: `ULTIMA` `$690D` (buffer `$8E00`), `ULTIMA` `$7B42` (buffer `$1000`), and
`INTRO` `$CEE8`, `$CFE4`, `$CFFC` (character creation and write-back). Because the
sector is written with raw `U2`, **it is invisible to the BAM**: T35/S16 shows as free
whether or not a save exists.

### The record (`$8E00-$8EFF`)

| Offset | Meaning |
|---|---|
| `$00` | first character of the player's name; **zero = no character on this disk** |
| `$13`, `$14` | the current map, the two digits of `MAP xy`/`MON xy`/`TLK xy` (used by the loader at `$67C2`; the name built at `$689B`). `$13` is the period on Earth (0 the Time of Legends, 1 9,000,000 B.C., 2 300 B.C., 3 1990 A.D., 4 2112 A.D., from the time-door sign's text at `$776F`) or the planet (in `STARS`' order, 1 Mercury ... 9 X); `$14` the place: 0 the surface, 1-3 towns and castles, 4-5 towers and dungeons |
| `$15-$1A` | the six attributes |
| `$1B/$1C` | hit points |
| `$1D/$1E/$1F` | food: hundreds, units, hundredths |
| `$20/$21` | experience |
| `$22/$23` | coins |
| `$2E` | torches |
| `$2F` | keys |
| `$30` | tools |
| `$37` | the planet: 0 on Earth, 1-9 on a planet |
| `$38-$3A` | the time doors' state |
| `$40+X` | weapons |
| `$60+X` | armour |
| `$80+X` | spells |
| `$A0+X` | items; `$A5` helms, `$AF` tri-lithium |
| `$FF` | must be **`$00`**; not zero = "this is not a player disk" |

The player position is not in the record's map digits: it is `$02/$03`. Every number in
the record is BCD.

`$CFCC` (read) and `$CFD0` (write) both return `$8EFF` in A. `INTRO`'s dispatcher:

```
$C9F5   JSR $CFCC        ; read T35/S16 -> $8E00, A = $8EFF
$C9F8   BNE $C9C0        ; not 0 -> "INSERT PLAYER DISK AND PRESS <F1>"
$C9FA   LDA $8E00
$C9FD   BNE $CA02        ; a name -> "THIS DISK HAS A PLAYER NAMED ..."
$C9FF   JMP $CABC        ; else -> character creation
```

At "THIS DISK HAS A PLAYER NAMED ...", any key but the one to continue reaches `$CAB9`,
`JMP $C9B4`, back to the insert-player-disk prompt, so that another disk can go in.

`$CFBD` erases: it fills `$8E00-$8EFF` with `$00` and writes it back. An all-zero sector
is a blank but valid player disk.

State of the shipped images: side B's T35/S16 is all `$00` (no character: the game boots
into character creation); side A's is `$00` except `$F8-$FF` = `$FF`, deliberately not a
player disk, which is what makes the game ask for the Player disk if side A is left in
the drive.

### Which disk: `$8E37`

Twelve names exist on both sides with different contents: `MAP 10`, `MAP 15`, `MAP 20`,
`MAP 30`, `MAP 32`, `MAP 40`, `MAP 41`, `MAP 45`, `MON 32`, `MON 41`, `TLK 32`,
`TLK 41`. The selector is `$8E37`, the planet number. `STARS` sets it (`STX $8E37` at
`$9518` and `$9538`, X = the planet) and on landing copies it into `$8E13` (`$966B`),
the first digit of the map name. `$7B42` proves the mapping: it reads T35/S16 into
`$1000` -- deliberately not into `$8E00` -- and compares the marker with `$8E37`:

```
$7B42   JSR $40AB        ; raw read T35/S16 -> $1000
$7B45   LDA $10FF        ; the "not a player disk" marker
$7B48   BNE $7B51        ; set: the Galactic disk is in
$7B4A   CMP $8E37        ; A = 0: the Player disk is in; on Earth?
$7B4D   BEQ $7BA5        ;   yes: fine
$7B4F   BNE $7B56        ;   no: "WRONG DISK!!"
$7B51   LDA $8E37
$7B54   BNE $7BA5        ; Galactic disk and on a planet: fine
```

So `$8E37 = 0` means the Player disk, anything else the Galactic disk.

### The disk prompts

Four, all "print, wait for F1 or a key, carry on":

| Address | File | Prompt |

## Copy protection: track 18, sector 18

The check is in `INTRO`:

```
$CED6   LDA #$12 / STA $FB      ; track 18
                   STA $FC      ; sector 18 (same value)
        LDA #$01 / STA $FD      ; U1 = read
        LDA #$00 / STA $FE
        LDA #$8E / STA $FF      ; buffer $8E00
        JSR $40AB               ; expected to FAIL
        LDA $FD                 ; the error channel's first digit
        RTS
```

called from the boot path:

```
$C031   JSR $CED6
$C034   CMP #$32                ; ASCII '2': a "2x" read error
$C036   BEQ $C06E               ; protection OK: load SHAPES, carry on
$C03B   JSR $4006 ...           ; "I/O ERROR #69. PRESS <F1> ..."
```

The logic is inverted from the obvious reading: **the read must fail.** On an original
the drive answers `23,READ ERROR,18,18` and `$FD` holds `'2'`. A sector copy reproduces
the data but not the error, the drive answers `00,OK`, and the check fails. "I/O ERROR
#69" is a protection failure dressed as an I/O fault. It is the only place the drive's
status is used as data rather than for retries.

## Overflow: counts that wrap at 99 and 9999

The C64's `ULTIMA` has the overflow known from the Apple II version. Every add to the
record is `SED / ADC / STA` with the carry out of the top digit dropped: 99 + 1 is 0,
9999 + 5 is 0004. None is checked first. The adds, by what they change:

- coins and experience: a kill (two code paths: `$712F`/`$7159`, `$7239`/`$7261`), a
  chest's gold (`$7925`);
- food (`$8E1D`): the shop's 100 (`$5DB8`), Steal (`$8177`);
- a weapon, armour, spell (+5) or item: shops (`$64AA`, `$639A`, `$5F30`, `$603A`),
  Steal (`$81C4`, `$819D`), one picked up from the tile under the party (`$7889`,
  `$78BB`), a person paid and pleased (`$7F3A`), a dungeon's chest (`$70A4`, `$70F0`);
- keys (+2), tools, torches (+1 to 4), helms, tri-lithium: a dungeon's chest, the
  surface's (`$795A`);
- an attribute (+4 times the payment in `$28`): a person paid (`$7F6A`, four `ADC $28`
  in a row from `$7F6C`, each carry added into the next).

**Hit points are the exception and cannot wrap on the C64**: their one add, the king's
(`$8426`), gives +300, +200, +100 or nothing depending on how high they already are,
and nothing from 9900 on. The rest of the record's writes are subtractions, which the
game checks, or plain stores. `STARS` only takes tri-lithium away; `DNGNDRAW` writes
nothing in the record.

Scope of that scan: every `$F8` byte in `ULTIMA` (56; a linear disassembly decodes 42 as
`SED`, each of the other 14 was disassembled from that byte, and 3 more are real `SED`s
-- all 45 read), and every write into `$8E15-$8EBF` in `ULTIMA`, `INTRO`, `SUBS`, `STARS`
and `DNGNDRAW`.

Other details found along the way: Ignite (`$798A`) in a dungeon with torches left does
`SED / SEC / LDA $8E2E / SBC #$01 / STA $8E2E` and then lights (`$27 = 150`); the food
costs are BCD subtractions from `$8E1D-$8E1F` for a pass (`$5163`, 0.10), a dungeon turn
(`$5948`) and a move (`$6B11`, `$6B94`, 0.19 each); the idle timeouts are the overworld
round counter (`$5151`), the dungeon countdown (`$6D11`) and the direction prompt
(`$692B`). Board on foot with nothing to board prints " WHAT?" (`$72CD`); a non-letter
key that is no command in the surface and town command loop goes to "ILLEGAL COMMAND!"
(`$5233` `JMP $6702`).

## A move and its footstep

The surface's and the towns' command loop (`ULTIMA` `$50F1-$5233`) takes a direction
(`@ / : ;`, `$C0 $AF $BA $BB` with bit 7), changes `$02` or `$03`, prints the direction's
name and calls `$69F1` with the tile in that direction (`$15-$18`, from the last view
drawn). First (`$69F3-$6AD5`): a town left at its edge, 5 hit points for one class of
tile (`$26` = 2, not identified), a force field (`$2E`: "FIELD CAUSES 1000 DAMAGE!" unless
the ring, `$8EA0`) and paralysis (`$3A`: "--PARALIZED!", no move). Then the transport,
`$13`, picks the move (`$6AD6`):

| `$13` | | Move |
|---|---|---|
| `$28` | rocket | `$6B6B`: refused |
| `$26` | plane | `$6B75`: the horse's food and walk (`JSR $6B94`), then the plane's own tests |
| `$24` | frigate | `$6B87`: water only; no sound, no food |
| `$22` | horse | `$6AF1`: a click, the pause, `$6B94`: food 0.19, then `$6BB4` `JSR $6B01`, the walk |
| other | on foot | `$6B01`: a click, the pause, a click, food 0.19 (`$6B11`) |

The click is effect `$4021` (`SUBS` `$4DD9`): two `$40A2` blocks (filter off and volume
14; voice 3 a noise at `$3000` with the gate on, attack and decay 1), the delay `$409F`
with A = `$80` (21.3k cycles, 21.6 ms) and the gate off. The pause is a fixed loop
(`$6B04`, `$6AF4`: X = 255 by Y = 32, 42.5k cycles). So on foot a move's sound is two
clicks 66 ms apart, on a horse three, a plane's two; a horse and a plane use food twice.
Every effect blocks like this one, and nothing but the effects (and the SID clear
`$401B`) writes voice 3. Each voice-3 block sets the sustain and release (`$D414`, its
seventh byte): the click `$00`, the others `$F4`-`$FB`.

The IRQ's key goes into `$38` (`SUBS` `$4765`); `SUBS` sets `$028A = $80` (`$4704`), so a
held key repeats, the first time 16 scans after the press, then every four.

## Reproducing the analysis

Extract files with VICE's `c1541`, strip the two-byte PRG header, and disassemble at the
**real** load address from the table above (never the header's). `da65` works but prints
no addresses; a small disassembler with addresses and KERNAL-call annotations, and a
decoder for the inline `JSR $408D`/`$4090` parameters (which is what established the
memory map), were used alongside it.
