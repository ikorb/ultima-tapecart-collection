# Akalabeth (C64): the 2016 conversion, Genesis Project's release

**Akalabeth: World of Doom** on the C64 is Andrea Schincaglia's conversion of Richard
Garriott's Apple II original (1980), from 2016: code and conversion Andrea Schincaglia,
idea and testing Antonello Molella, graphics David Vigh. These notes describe Genesis
Project's release of it ("Akalabeth - World of Doom +4 /GP", 2016-08-04, "compiling and
trainers: Wertstahl, linking: L.A.Style"), the one the cart is built from. They come from
unpacking its main file, reading the runtime's dispatcher, and tracing the program in
VICE; what is inferred rather than read or traced says so.

Addresses are C64 addresses; program addresses are where the program runs, from $0801.

## The disk

The disk is named "accept no limits". Its directory starts with nine DEL entries whose
names are the logo of the directory listing; they point at the main file's sectors and
hold nothing of their own. Then:

| File | Blocks | Loads to | What |
|---|---|---|---|
| `AKALABETH+4  /GP` | 83 | $0801 | the intro, the game, packed: `SYS 2061` |
| `AKA2BITMAP`, `AKA3BITMAP`, `AKA5BITMAP` | 33 each | $A000 | three pictures' bitmaps (8192 bytes) |
| `AKA2VIDEOMEM`, ... | 4 each | $8C00 | their screen RAM (1000 bytes) |
| `AKA2COLORMEM`, ... | 4 each | $D800 | their colour RAM (1000 bytes) |
| `LIB` | 9 | $C000-$C8A6 | the graphics routines the program calls (`SYS 49152`+) |

## The main file

`SYS 2061` starts a decruncher, which runs from $0100 and unpacks, in about 1.9 million
instructions, an intro (Genesis Project's, from $3000) and the game, which it leaves at
$4000 as the game is in RAM from $0801. The decruncher hands over to the intro at $3000.
When `$DC01` bit 4 goes low there ($3B00: space, among others), the intro calls IOINIT,
RESTOR and CINT, copies a routine to $0400 and runs it: with `$01` = $34 it moves
$4000-$FEFF to $0801-$C6FF and jumps to $081C.

In VICE, the intro leaves BASIC's temporary string stack pointer `$16` at $08 (the intro
uses $14-$17), and the program stops at its start with `?FORMULA TOO COMPLEX ERROR IN
30440`; `$16` = $19 at the hand-over ($0421, the routine's `JMP $081C`) and it runs.
Whether this happens on a real C64 was not tried.

## The program: a compiled BASIC program

$0801 holds a BASIC line, `SYS 2076`; $081C is a runtime's entry (`JMP $0C92`). The
compiler is not identified. The program ends at $7A2E:

| Range | What |
|---|---|
| $081C-about $2100 | the runtime: a p-code interpreter; it calls BASIC's ROM for arithmetic, strings, conversions, SYS's arguments and errors (which it reports with the BASIC line numbers) |
| about $2100-$784B | the p-code and its constants |
| $784C-$7A2E | the scalar variables' table, names compiled in; BASIC's pointers are set from the runtime's at $1F93 (VARTAB $784C, ARYTAB $7A2F; $0CB1 sets them and clears the values) |
| $7A2F- | arrays (DIMmed as it runs) and strings, up to MEMSIZ ($A000) |

What the bytes of the moved image hold above $7A2E is not used: they are not the same in
VICE and in an unpack on the host, and the program runs without them.

The variables are the Apple original's: `TE(21,21)` the map (`TE(X,Y)`, X fastest: 1 a
mountain, 3 a town, 4 a dungeon; 2 a tree and 5 Lord British's castle, inferred from how
they are drawn), `TX`/`TY` the party's square, `IN` the dungeon level (0 outdoors),
`PW(0)` food, `C(0)` hit points and `C(5)` gold (the rest of `C` the other attributes),
`LN` the lucky number. Each was read in VICE against what the screen showed.

### The p-code, as far as it was read

The runtime keeps its p-code pointer in $39/$3A and fetches with `LDA ($39),Y` at $0ECF.
The byte decides (read from the dispatcher, $0ECF-$0F4E):

| Byte | What |
|---|---|
| $0E-$7F | an operation or statement: its handler from the tables at $087A (low bytes) and $0817 (high bytes), indexed by the byte |
| $80-$BF, $E6-$FF | through $0F4E, which keeps the byte in $3B as the next thing to do and first does or pushes what was there; the numbers ($A6-$A8) are read from there ($10B8-$10F3) |
| $C0-$DF | a variable, by the table at $082B |
| $E0-$E5 | through $0F36: string variables (inferred: `FL$` is `$E0` where the program assigns it) |

Among the operations, read from their handlers:

- **$3A, `:`**: the empty statement. Its handler ($0ECB) only steps the pointer on: no
  value, no state.
- **$19 hi lo**: GOTO. **$1A hi lo**: GOSUB, pushing the return address and $8D. The
  target is an address in the p-code, high byte first.
- **$1D**: RETURN when a GOSUB's $8D is on the stack ($1D30); otherwise the frame is a
  FOR's, and it is NEXT (inferred).
- **$17**: POKE ($1832); **$18**: SYS ($1856), which hands `TXTPTR` to the ROM's SYS, so
  anything after the address is parsed by BASIC (`SYS 57812 FL$,U,1`).
- **$A6 n**: a one-byte number; **$A7 hi lo**: a two-byte number; **$A8** and five
  bytes: a number in BASIC's floating point format (`A8 90 40 39 00 00` is 49209).
- **$E7 n** and n bytes: a string (inferred from the program's text).

A statement's handler ends through $0EAC, which clears the pending operation ($3B) and
steps on. So a run of `:` can replace whole statements; one that starts inside a
statement leaves an operation pending, and the program fails later (for one, a RETURN
then finds a number on the stack instead of $8D: `?RETURN WITHOUT GOSUB`).

## The loads

The program loads through one routine, at $6261: `SYS 57812 FL$,U,1: ... SYS 65493`
(the ROM's parameter parsing of LOAD, then the KERNAL's LOAD; `U` the drive). Ten GOSUBs
call it, each after `FL$` is set:

- **$692A-$6932**: `LIB`, after `PRINT "LOADING..."` ($691D), as the title is about to
  be drawn: the title sequence, which the program runs once, at its start.
- **$6AE0-$6BE0**: the three pictures, in the instructions (answer Y at "INSTRUCTIONS
  (Y/N)" -- the Y goes to $6AB0, a "(PRESS SPACE TO CONTINUE)" on the title). After
  that key (`GOSUB $62CB` at $6AD5: POKE 198,0: WAIT 198,1), `POKE 53265,11` ($6AD8, the
  screen off), then from $6AE0 `SYS 49209` and a FOR loop (inferred), then per picture
  `GOSUB $6283` (bitmap mode: POKEs to `$DD00`, `$D016`, `$D018`, `$D011`), its colour
  RAM and screen loaded, `SYS 49170`, its bitmap loaded, `SYS 49173`, `SYS 49209` --
  `AKA2`, `AKA5`, `AKA3`, in that order. Then, at $6BE1, `GOSUB $62A8` (the text screen
  back) and `SYS 58692` (the KERNAL's clear screen), and the first page of text ("MANY,
  MANY, MANY YEARS AGO"). What the three `LIB` calls do was not read.

The KERNAL's LOAD is called from one place, the routine's `SYS 65493` (its only
occurrence in the program, as `SYS 57812`'s is). In VICE, with a breakpoint on SETNAM
and LOAD, nothing else loaded through the play: towns, a dungeon, death and the
resurrection (which goes back to "TYPE THY LUCKY NUMBER"); Lord British's castle was not
visited. The program saves nothing.

## The trainer

`GOSUB $76E6` at $20A2, at the program's start, runs Genesis Project's trainer ($76E6-
$784A, the end of the p-code): upper case, a clear screen, "Fixed and trained by
Wertstahl", then `POKE 1023,0: POKE 1022,0: POKE 1021,0: POKE 1020,0` and four questions,
each Y a `POKE n,100`:

| Address | Question | Where the game reads `PEEK(n)` (the constant's place in the p-code) |
|---|---|---|
| 1023 ($03FF) | Unlimited food? | $4F2F, $4FC3, $5B9C: where a move or a turn uses food |
| 1022 ($03FE) | Unlimited gold? | $67D9, $6833: the shop's "CAN NOT AFFORD" test and its charge |
| 1021 ($03FD) | Invincible? | $5B55: a monster's attack |
| 1020 ($03FC) | Always hit, always kill? | $553E, $5591: the player's attack |

Food and gold were seen to work in VICE; the other two are read from where their tests
are. "Fixed" is not explained in the release; what it fixed was not looked for.
