# Ultima V (C64): reversing notes

Ultima V: Warriors of Destiny is (c) 1988 Origin Systems, Inc. / Lord British. These
notes describe the original C64 release as it is on its eight disks, independent of the
cart. They come from parsing the disk images, extracting every file, recursive-descent
disassembly, exhaustive byte-pattern scans across all 236 files, and runs of the original
in VICE on copies of the images. Findings that are inferences rather than checks say so.

A general caution for anyone repeating this work: byte-pattern scans over U5's files give
many false positives. Graphics and text are full of sequences that decode as plausible
opcodes; a raw scan for `STA $01` finds 57 hits, of which 6 are real code. Confirm every
hit by disassembling from real entry points. Recursive descent from a file's load address
covers overlays poorly, because they are entered through dispatchers; low coverage means
"needs better entry points", not "mostly data".

N is the game's own disk number (`$6C09`'s argument); the BAM ID character the game
checks is `$40 + N`.

- All files: 772 284 bytes; 148 of the 236 unique by content (411 600 bytes).
- **Every disk except 1A also carries a private raw-sector area**: blocks the BAM marks
  allocated that belong to no directory entry, on tracks 19-35 (2A, 2B), 24-35 (3A, 3B,
  4A, 4B) and 23-35 (1B): 1507 blocks, 376.8 KiB, 337.8 KiB unique (only 30 blocks are
  shared between disks). This is what the raw block reads fetch (below): the overworld
  and Underworld maps, town maps and dungeon records. Counting files only understates
  the game by nearly half.
- Disk 1A's image is 175 531 bytes: a D64 with an error map in which all 21 sectors of
  track 6 are flagged "no sync" (unformatted). The other seven are plain 174 848-byte
  images.

## Boot

**C64.** `LOAD"*",8,1` loads `meow`, the first directory entry, at `$032C` over the
KERNAL vector table; its CLALL vector points at its own payload, which does `RESTOR`,
loads `XYZZY` and jumps to `$2000`.

`xyzzy`:

1. Tests for a C128: `LDA #$4C / CMP $C024 / BNE` (`$2042`). On a C128 booted from 1A,
   `$C000-$CFFF` is the screen editor ROM and `$C024` is a `JMP` (`$4C`, checked in
   VICE's C128 ROM image). On a C64 it is RAM. On the C128 branch it sets `$C8` = `$80`
   ("a C128"), `$79` = `$80` (music on), the NMI vector to `$0395`, `$00` = `$00`,
   `$9D`, `$D8`, `$D011`. Before the test it writes `RTS` to `$0126` and `$0129`, the
   music API, so on a C64 every music call returns at once.
2. `$01` = `$06` (BASIC out, KERNAL and I/O in).
3. The drive-type prompt (1541/1571, or Enhancer 2000/MSD), stored in `dconfig`; held
   space at boot brings the prompt back.
4. Sends `UJ` (drive reset), loads `u5siz.o` to `$7700`, and installs the fastloader
   (`JSR $7700`) unless `dconfig` is 2, which leaves plain KERNAL I/O.
5. C128: loads `m` to `$7200`, `JSR $720F` (copy to bank 1, start the player), then
   `subs.128` over `$7700`. C64: `$FFFE/$FFFF` = `$0380`, the IRQ handler it copies.
6. Loads `temp.subs` to `$6C00`, then `JSR $6C24 "ST*"` (`startup`) and `JMP $8000`.
   With J held (`$2109` `LDA $C5`, compared with `$22`) it takes `qs`, the quick start
   into Journey Onward, instead.

**C128.** Disk 1A has a C128 boot sector at track 1 sector 0 (`CBM`, no extra sectors,
file `XYZZY`, `JMP $2000`), so a C128 loads `xyzzy` and runs it in C128 mode. That, not
anything on the disks, is what makes the `$C024` test succeed.

**A weakness of the `$C024` test.** On a C64 `$C024` is RAM and a reset keeps it. If a
program left `$4C` there, `xyzzy` takes the C128 path on a C64: it blanks the screen and
skips the `$FFFE/$FFFF` store, and the first interrupt in all-RAM banking jumps through
whatever is in RAM there. Reproduced in VICE by poking `$4C` at `$C024` before booting
(the machine jams through `$FFFF`). Ultima VI writes `$C024` with each large overlay it
loads at `$C000`; none of its original overlays has `$4C` there (all sectors of its six
disks scanned), so which program can leave that value is not known.

The resident block is `$4C00-$7B56`. `temp.subs` is permanently resident despite its
name.

**`$7B57-$7FFF` is not free.** `u5siz.o` ends at `$7B56`; above it, a scan of absolute
loads and stores across all 236 files finds accesses throughout: `m` and `startup`
around `$7B90-$7BE6`, `main.out` `$7CAE`, `create` `$7C6D`/`$7CF6`, `main.twn` writing
`$7D00,X`/`,Y` from twelve sites (`$9B13` stores eight `$FF` empty-slot markers at
`$7D00-$7D70`, 16 bytes apart), `main.combat` `$7DA6`, `talk.*` `$7DF3`, the sector
buffers from `$7E00`. The RAM under the I/O is also used: data placed at `$D000` is
overwritten during the intro.

### The IRQ handler at `$0380`

Saves the registers and `$FF00`, `JSR $6C03` (I/O and KERNAL in), `JSR $FF9F` (SCNKEY),
`LDA $DC0D` (acknowledge CIA 1), `JSR $6C06` (all RAM), restores and `RTI` at `$039E`,
which is also the NMI target. It returns to all-RAM, which confirms all-RAM as the run
state. The keyboard is scanned by the KERNAL routine from this interrupt, so the game
depends on interrupts being enabled.

In play the KERNAL is banked out and the game uses its own RAM copies of the routines
under the ROM; the KERNAL's GETIN at `$F142` is not reached after the early attract.

## Banking: `$00` and `$01`

Two routines in `temp.subs`, reached through `$6C03` and `$6C06`:

- `$7684`: `$01` = `$06` (I/O and KERNAL in), `$FF00` = `$0E` (the C128 MMU; RAM on a
  C64), `CLI`.
- `$768F`: `$01` = `$00` (all RAM), `$FF00` = `$3F`.

Each machine ignores the other's write. The six real `$01` writers in the game (from the
57-hit byte scan, each confirmed by disassembly): `temp.subs` `$7686` and `$7691`,
`xyzzy` `$2064`, `scratch` `$2046`, `update.himem` `$1F48`, `intro.view` `$9F37` (the
`STA` addresses; all but the all-RAM one store `$06`). DDR writers: `xyzzy` `$2055` and
`scratch` `$2039` (`$00` = `$00`, on the C128 branch only) and `u5siz.o`/`subs.128`
`$7A0C` (`$B0`). On a C64 the DDR stays `$2F`.

Both `$01` values clear bit 5, the cassette motor line.

## The `$6C00` jump table

All disk access goes through a 17-entry table at `$6C00` in `temp.subs`. Only seven
slots touch the drive; the other ten are engine services. Call-site counts are raw
byte-pattern matches across all disks, so upper bounds.

| Slot | Target | Function | Sites |
|---|---|---|---|
| `$6C00` | `$6EAE` | **disk**: raw block read (`U1`) | 27 |
| `$6C03` | `$7684` | I/O and KERNAL in | 20 |
| `$6C06` | `$768F` | all RAM | 53 |
| `$6C09` | `$6D47` | **disk**: ensure disk N | 94 |
| `$6C0C` | `$6F4E` | targeting cursor (8-way, sprite 0) | 24 |
| `$6C0F` | `$712E` | redraw all objects | 7 |
| `$6C12` | `$72E3` | pixel -> tile coordinates | 29 |
| `$6C15` | `$72AC` | set one bitmap pixel | 28 |
| `$6C18` | `$73F4` | blit a 16 x 16 map shape | 129 |
| `$6C1B` | `$7472` | the moongate step: nothing unless the tile under the party is `$DC` (`$7475`); travelling, it saves `TLIST` through `$6C2D` | 7 |
| `$6C1E` | `$7545` | party status: can anyone act? | 47 |
| `$6C21` | `$757B` | party HP regeneration (BCD) | 16 |
| `$6C24` | `$6C49` | **disk**: LOAD by inline name | 336 |
| `$6C27` | `$75E5` | "which character?" prompt | 52 |
| `$6C2A` | `$6CAA` | **disk**: check disk ID | 11 |
| `$6C2D` | `$6DE0` | **disk**: command (scratch) + SAVE, inline | 66 |
| `$6C30` | `$6E7B` | **disk**: read a 512-byte record | 10 |

A one-byte variable at `$6C33` holds the current device (8 or 9). A second, 7-entry
table follows at `$6C34-$6C48`: `$6C40` play song, `$6C43` volume toggle, `$6C46`
restart the song, and four bank/clock helpers (`$7699`, `$76A5`, `$769B`, `$76A7`); none
touch the drive.

### The disk slots

**`$6C24`, LOAD by name.** `LDX #post / JSR $6C24 / "NAME",0`. `SETLFS 8,dev,1` (the
file's own load address), the name from the inline string, `JSR $0126`, `LOAD` (retried
for ever on error), `CLOSE`, `JSR $0129`. Then X = 0 returns after the string, 1 does
`JMP $8000` (a mode root), 2 `JMP $A700` (an overlay). Callers test the carry: `startup`
`$8A14` is `LDX #0 / JSR $6C24 / "HTXT",0 / BCS` back to the load.

**`$6C00`, raw block read.** A = buffer page, X = sector, Y = track. Opens a `#` buffer
channel and sends `U1 5 0 tt ss` (template at `$6F3D`) on the command channel, then
reads 256 bytes with CHRIN, bracketed by `$0126`/`$0129`. There is no `U2` (block write)
anywhere: the only store to the command byte (`$6F42`), at `$6EB1`, writes `'1'`.

**`$6C30`, 512-byte record.** `$6E7B` turns a record number into a track and sector and
calls `$6EAE` twice directly (from `$6E9E` and `$6EAA`, not through the table), into
`$7E00` and `$7F00`.

Who reads raw blocks: `main.twn` (16 `$6C00` sites and 4 `$6C30`), `t` (5 `$6C30`),
`main.out`, `main.dng`, `startup` and `dng.precom` (one each); most compute track and
sector from game state. Two read fixed places: `p` `$A8C5` (track 19 or 30, sector 0,
into `$BC00`) and `transfer` `$81FA` (track 14 sector 0, into `$BD00`, from an Ultima IV
disk). A town map is four consecutive sectors into `$4400-$47FF` (`main.twn`
`$98FA-$991B`: track `$20 + n/4`, sector `(n*4) & $0F`, tracks 32-35); the overworld
reads one sector per 16 x 16 chunk (tracks 20-35 of 2A/2B, 256 x 256 tiles); a dungeon
level is one 512-byte record.

**`$6C09`, ensure disk N** (`$6D47`): stores N, adds `$40`, calls `$6C2A`, and prompts
and retries on a mismatch. **`$6C2A`, check disk ID** (`$6CAA`): reads track 18 sector 0
into `$7F00` through `$6C00` and compares `$7FA2`, the first BAM ID byte. With two
drives (`$C8` bit 0) it tries the other device first. Both signal "the right disk" with
**carry clear**; their callers retry on carry set. The prompt with the seven disk names
lives in the same routine (`$6CAA-$6DDF`).

**`$6C2D`, scratch + SAVE** (`$6DE0`): `JSR $6C2D / "S:NAME",0 / !word start / !word
length`. The whole string goes to the command channel (scratch), then `SETNAM` on the
name plus 2 (without `S:`) and `SAVE` of start..start+length. The game's only
`JSR $FFD8` is at `$6E59`; `$6E5C` retries on carry. The routine consumes the inline
block and returns after it.

The original disk code occupies `$6C49-$6CA9` (load), `$6CAA-$6DDF` (check ID, ensure
disk, prompt), `$6DE0-$6E7A` (save) and `$6EAE-$6F4C` (block read); a static scan of
all 236 files finds no absolute reference into those ranges from outside them that is
real code (the hits are misaligned bytes, text and map data). `$6F4D` is a variable of
the targeting cursor at `$6F4E`.

### The ten service slots

- `$6C0C` -> `$6F4E`, the "in which direction?" picker: A selects one of 8 handlers
  through the table at `$6F6C`; fills `$BE00-$BEE5` with `$FF`; sprite 0 (colour 9) is
  the cursor.
- `$6C0F` -> `$712E`: walks the object arrays down in steps of 13, drawing each from
  `$BE00,X`/`$BF00,X`.
- `$6C12` -> `$72E3`: X = object index; returns X = (`$BE00,X` - 7) / 16, Y likewise.
- `$6C15` -> `$72AC`: row base from `$1400`/`$14C0`, bit from `$72A4`; the store is an
  OR written as `(~m & k) ^ m`.
- `$6C18` -> `$73F4`: X indexes `$4A40`/`$4A60`; clears a 2 x 2 screen cell and copies
  32 bytes of shape from `$42C0`.
- `$6C1E` -> `$7545`: over the 6 party records, A = 0 if anyone is G(ood) or P(oisoned),
  1 if only S(leeping), `$FF` if none.
- `$6C21` -> `$757B`: BCD add to current HP (`+$08/$09`), clamped to the maximum
  (`+$0A/$0B`), for everyone not D(ead). A table at `$118F` scanned for `$2D` here has an
  unconfirmed purpose.
- `$6C27` -> `$75E5`: one able member is chosen silently, else a prompt; echoes the name
  from `$1000`.

Helper `$76F3` multiplies by 16, the record stride.

## The fastloader (`u5siz.o`)

Installed only when `dconfig` is 1. `$7700` points the KERNAL LOAD vector (`$0330`) at
`$770B`, so every `JSR $FFD5` becomes a fast load; VERIFY and `$` loads fall back to the
KERNAL. The name is copied into a buffer inside the drive code (`$7AD4`, 17 bytes,
`$A0`-padded); 512 bytes of drive code go to the 1541's `$0500-$06FF` in 16 `M-W`
chunks of 32, started with `M-E`. The drive searches track 18 itself, with `*` and `?`
wildcards. The transfer is 2-bit over `$DD00`, synchronised against `$D012` and
`$D015` (badline timing depends on sprites), 256 bytes a block into `$7F00,Y`.
`enter.play` adds sprite-off/on hooks around loads for this timing (below).

## The saved game

### What the game writes

From saves made with the original on copies of the disks (character creation, then saves
at the start, in the overworld and in a town), diffed against the pristine images:

| Disk | Files | Load | Size |
|---|---|---|---|
| 2A | `ROSTER` | `$1000` | 1025 shipped, 1024 written |
| 2A | `PRTY.DATA` | `$BC00` | 48 |
| 2A | `LIST`, `SLIST`, `TLIST` | `$4A00` | 512 each |
| **2B** | **`TLIST`** | `$4A00` | 512 |

So the save disk is not only 2A. About 3.1 KiB in all. Track 18 and an occasional extra
block also differ after a save: DOS side effects of scratch-then-save, not game writes.

### The validity test

`enter.play` (Journey Onward) loads the set and tests one byte:

```
$8153  LDX #$00 / JSR $6C24 / "ROS*",0     ; the roster to $1000
$815D  LDA $1000 / BNE $8165                ; roster byte 0
$8162  JMP $833A                            ; "No active game!", then the Program disk
```

On the shipped 2A, roster byte 0 is `$00`, so there is no saved game and the game says
"No active game!". `blank.roster` (1A, 2B) has a name there. In circulating dumps of 2A
the byte is non-zero when the disk has been played, so it is an exact "played" check.

### The roster

16 name slots of 8 bytes at `$1000-$107F`: PETSCII with bit 7 set on every character but
the last, then `$00` padding. Then 16-byte character records from `$1080`; the first 6 are
the party:

| Offset | Field |
|---|---|
| `+$00` | `$00` = in the party |
| `+$03` | status: `$C7` G, `$D0` P, `$D3` S, `$C4` D |
| `+$07` | magic points (BCD) |
| `+$08/$09` | current HP, 16-bit BCD |
| `+$0A/$0B` | maximum HP, 16-bit BCD |

Party items are BCD counts in the roster file: `$1184` keys, `$1185` gems, `$1186`
torches, `$1240`+ mixed spells. `+$07` and the item addresses come from the code that
uses them (Jimmy, View, Ignite, Cast), not only from save diffs.

### The object lists

`LIST`, `SLIST`, `TLIST` and `BLANK.ULIST` share one format, loaded at `$4A00`: 32 object
slots as 16 parallel 32-byte columns; `+$00`/`+$20` the tile (two animation frames),
`+$40` X, `+$60` Y (the `$4A40`/`$4A60` rows the blitter reads); slot 0 is the party.
(The layout is from the dumps and those reads, not a full decode.)

- `LIST` is the current map's objects.
- `TLIST` on each world disk is that world's list while the party is away from its
  surface. It is saved when the party leaves the surface: into a location (`temp.subs`
  `$74CC`), across to the other world (`main.out` `$977A`, which then loads the other
  disk's) and by Gate Travel (`c` `$B8BA`, after "To phase:" at `$B86D`). It is loaded only on the way back
  (`temp.subs` `$752B`, `main.twn` `$8659`, `main.dng` `$88A2`, `main.out` `$9798`, `c`
  `$B916`).
- A save copies `TLIST` to `SLIST` (`main.out` `$8FD8`, `main.twn` `$91B1`), and
  `enter.play` copies `SLIST` back to `TLIST` (`$812E-$8146`) before its roster test.
- `create` empties `LIST` and `SLIST` (`$8266-$828E`), writes 2B's `TLIST` from
  `BLANK.ULIST` (`$819D-$81BC`), loads `BLANK.ROSTER` and `BLANK.PARTY`, saves, and
  loads `STARTUP`, which plays the title and returns to the menu: **every game, a new
  one too, starts through Journey Onward**.

So 2A's shipped `TLIST` is never interpreted before it is overwritten. This was found by
reading every `TLIST` load and save site on the eight disks, and confirmed in VICE with
2A's `TLIST` filled with a marker value: creation, Journey Onward and leaving the
starting hut never read it. The other load sites follow a save on the way in (statically;
not run).

### What is on the shipped 2A

The save files hold non-default bytes behind the zeroed validity byte: `ROSTER` differs
from `blank.roster` in 13 bytes (slot 0's name zeroed but for stale bytes after it, a
few record bytes) and is one byte longer; `PRTY.DATA` differs from `blank.prty` in 22 of
48 bytes; `LIST`, `TLIST` and `SLIST` differ from `blank.ulist` in 80%, 13% and 10% of
their bytes (2A's `TLIST` holds the party and four objects). 2A is also the only disk
with scratched directory entries (`broster`, `wroster`, which no file names) and
scattered allocation (`c`, `u` and `main.out` written into the space they freed). The
game writes none of those files.

These read as mastering residue rather than a played game, but that is an inference: a
started-then-cleared game cannot be ruled out from the image alone. Character creation
does not rewrite 2A's `TLIST`, so it stays as shipped until the party first leaves a
surface. `PRTY.DATA` is zero page `$02-$31`: a save copies it there (`main.out` `$8FAD`: `LDX
#$2F / LDA $02,X / STA $BC00,X`). So `$BC2B/$BC2C` are `$2D/$2E`, the overworld X and Y
(0-255; seen in VICE: a teleport to (58, 43), then a save, left 58 and 43 there), and
`$BC00-$BC03` are `$02-$05`, the party's place in the 32 x 32 window and the window's
top-left chunk, which `main.out` works out again from `$2D/$2E` (`$9801`).

## Copy protection

None that is checked. Track 6 of 1A is unformatted and allocated to no file; a search of
every `JSR $6C00` call site with its preceding `LDY #track` finds tracks 1, 14, 19 and 30
read directly, never 6. It defeats whole-disk copiers only.

## Transfer From Ultima IV

`transfer` (1A, from the main menu) asks for the Ultima IV Britannia disk, checks it
with `$6C2A` A = `$30` (Ultima IV's BAM IDs are "01".."04"), wants "U4 DISK C" in the BAM
name the check leaves at `$7F00` (it tests three of those bytes, at `$7F90`, `$7F91` and
`$7F98`), and reads track 14 sectors 0-1 (Ultima IV blocks 273-274, its party) into
`$BD00`. It also loads `BLANK.ROSTER` and `BLANK.PRTY`, and ends by loading `STARTUP`.

## The main menu

`startup` (1A) builds the menu; `$84ED` prints the "Number of drives" line and `$85C5`
holds the cursor limit (6 entries). The menu's keys `$C1-$CF` (A-O) play songs 1-15:
`$85A2` is `AND #$0F / TAX / JSR $6C40` (silent on a C64). The menu times out:
`$9176` counts `$9152` down and then drops the return addresses and jumps back to the
attract loop. The attract sequence reloads `startup` every cycle.

Input: `$4C4E` -> `$5BDF` reads the joystick port `$DC00` when `$4CAE` is zero and calls
GETIN only when it is not (text entry at `$685C` sets it). In play the party moves by
joystick; commands come from the keyboard queue. Key codes carry bit 7 (`$5C26`
`ORA #$80`).

`qs` probes for a second drive with a bare `LISTEN 9 / SECOND $6F / UNLSN` and `$90`,
setting `$C8` bit 0. `startup`'s drive check at `$8417` sends LISTEN to devices 8 and 9
through U5's RAM copy of the KERNAL between a mute and an unmute; the KERNAL's serial
routines use CIA 1 timer B as a one-shot IEC timeout (`$ED94`, `$EE22`: `LDA #$19 /
STA $DC0F`), which stops a timer the C128 music runs on.

## Journey Onward's load hooks (C64)

`enter.play` installs disk-load hooks at `$0126-$0146` on a C64 whose LOAD vector is the
KERNAL's (`$0331` = `$F4`) and whose `$E486` is not `$46`: `$0126` turns sprites off,
`$0129` back on, for the fastloader's timing. Its gate at `$802A` is `LDA $C8 / BMI`
(skipped on a C128). On a C128 those addresses are the music's mute and unmute.

## C128 mode and the music

Booted on a C128, the game runs in C128 mode and uses RAM bank 1 for music and an
overlay cache.

### The music

`m` (1A only, `$7200`, 47 blocks): the player at `$7200-$7C9F` and 15 songs from `$7CA0`
(a skip byte, the song count 15, then 15 big-endian offsets relative to `$7CA0`). The
init (`$7349`) relocates the offsets into `$722B-$7248`; song 0 has no entry and means
silence. `muff` is byte-identical to the song data and referenced by nothing on any disk
(its name occurs once, in 1A's directory).

On the C128 branch `xyzzy` loads `m` into bank 0, and `JSR $720F` runs `$7BC4` (copies
`$7BDB-$7C2B` to `$0123-$0173` and `$7C2C-$7C9D` to `$0220-$0291`), `$0269` (copies
pages `$72-$A0` from bank 0 to bank 1 a byte at a time through `$FF00` = `$3F`/`$7F`)
and `$0123` (init). The bank-0 copy is then loaded over; the player lives on in bank 1.
This relies on the MMU's `$D506` at `$04`, 1 KiB of common RAM, where every routine that
writes `$FF00` lives (`$798F` raises it to 4 KiB around a KERNAL call and back).

| `$FF00` | Meaning |
|---|---|
| `$0E` | bank 0, RAM to `$BFFF`, I/O, KERNAL: for KERNAL disk calls |
| `$3F` | bank 0, all RAM: the C128's `$01` = `$00` |
| `$7E` | bank 1, all RAM + I/O: the music (SID visible) |
| `$7F` | bank 1, all RAM: the copy loop, the overlay cache |
| `$4E` | bank 1, RAM to `$BFFF`, I/O, KERNAL: to call SCNKEY |

Common-RAM API: `$0123` init (swap zero page, player init, timer, vectors), `$0126`
mute (gate the voices off, `$7219` = `$FF`), `$0129` unmute (re-arm the timer), `$0220`
the IRQ handler (hardware entry), `$0229` the same from `$0314`, `$0269` the one-shot
copy. Init programs **CIA 1 timer B** as the music interrupt (`$DC0D` = `$82`, `$DC0F` =
`$01`, no raster IRQ) and writes `$FFFE/$FFFF` = `$0220` in both banks. The handler ticks
the player (`$7203` -> `$73BC`), then scans the keyboard through `$798F` (SCNKEY, with
`$0A20-$0A30` saved): the keyboard rides on the music interrupt. The tick reloads the
timer from `$7225/$7226` (per-song rate, default `$429A`). `$73DA` swaps zero page
`$50-$5A` with `$9FF0-$9FFA` around the player.

Song selection, all in common RAM: `$03CC` requested (bit 7 a flag), `$03CD` selected,
`$03CE` playing; `$79` bit 7 "Volume On". `$6C40` (`$76B8`, gated on `$C8` bit 7) jumps to
`subs.128`'s `$7703`: `$03CD` = `$03CC` = X, then wait until `$03CE` = X. `$6C43`
(`$76C6`) toggles the volume. `$6C46` (`$76BF`, not gated) re-requests `$03CD`. Songs at
call sites (from the numbers, not from listening): 0 silence (most mode changes), 1 the
title and `main.combat` `$86FB`, 2 `shrine`, 3 the overworld (`main.out` `$8041`), 4
combat, 5 towns and `shrine`, `$0A` dungeons, `$0E`/`$0F` the ending. During the title
`startup` `$91D2` steps through all fifteen. The gates (`LDA $C8 / BPL`) are in
`temp.subs` (`$76B8`, `$76C6`), `startup` `$91D3`, `main.combat` `$86F5`, `u` (`$B4FC`,
`$B640`), `w` (`$A781`, `$A963`) and `end` (`$AC81`).

`temp.subs` mutes around its load, save and command paths (`$6C7E`/`$6C8D`, `$6DE0`,
`$6E5E`, `$6EC9`/`$6F15`), and so does the sound-effect routine at `$7B00` (a tone on
voice 1), so the C64 has sound effects but no music.

### `subs.128`, the overlay cache

`subs.128` has the same size and load address as `u5siz.o` (659 bytes differ); its drive
code is residue. It is not a fastloader but a cache, called directly by about 20
C128-only sites:

| Entry | Function |
|---|---|
| `$7700` | fetch overlay A to `$A700`: from bank 1 if one of the eleven cached (C E I M P R S T U V Z), else load it by name |
| `$7703` | play song X |
| `$7706` | restart the selected song (`$03CD` -> `$03CC`) |
| `$7709` | swap the mode root `$8000-$ACFF` with bank 1 `$A000-$CCFF`; once called with X/Y other than `$12/$34`, it patches itself to swap `$8000-$A6FF` with `$A000-$C6FF`, puts `$A700` back (a page from the VDC, and six from bank 1 if `$8001` reads `$E9 $81`) and `JMP $8000`; nothing patches it back |
| `$770C` | Journey Onward's preload: load Q, put its first page in the VDC at `$3E00`, load the eleven and stash each in bank 1 (reaches the VDC before its first `$6C03`, so its caller must have I/O in) |
| `$770F` | exchange `$C000-$FCFF` (a map) with the VDC's 16 KiB `$0000-$3CFF`; A tags the map, the old tag comes back |
| `$7712` | exchange the C128 KERNAL's `$0A00-$0A28` with a buffer |

Bank 1 is reached through the KERNAL's FETCH/STASH trampolines (`$02A2`/`$02AF`), one
call per byte. Overlay U is cached at `$CD00-$DFFF`, under the I/O. In bank 1 the cache
uses `$0400-$6FFF`, `$A000-$DFFF` and `$F000-$FEFF`, the music `$7200-$9FFF`; nothing of
the game's uses `$E000-$EFFF` there. No file writes `$D030` (2 MHz).

`startup` copies `$C000-$CFFF` over `$F000-$FFFF`, which puts the C64 path's IRQ vector
(`$0380`) into bank 0's `$FFFE`; that handler is MMU-safe and runs on a C128 until the
next unmute writes `$0220` back. On a C128 the J test is `LDA $D5` at `$20F8`, the C64's
`LDA $C5` at `$2109`. The attract sequence does not take keys from the C128 KERNAL's queue
in VICE, from the original disk either.

## Where a step goes

Measured in VICE on the original routines (cycles not exact), sound off: a step in
Britannia about 295k cycles (0.30 s; 352k with sound), a town step about 516k (0.52 s,
418-699k, the party poisoned). The game waits inside `JSR $4C15` (`main.out` `$810A`, `main.twn` `$8263`).

- **The view update, `$4C1B`, ~198k** in both: the cell draw (`update.himem` `$1D80`,
  from `main.subs` `$50DE`) 77k, all 121 cells every step, 32 bitmap bytes by `(zp),Y`
  plus colours; the line of sight (`$4D5D`) 57k, a flood from the centre over eight
  neighbour offsets (`$4E39`) with a row table rebuilt at `$7F00` each call; tile
  animation (`$572B`) 36k, 32-byte tiles at `$DA80`, `$DB00`, `$DD80`, `$D000`/`$D040`,
  `$DF40`/`$DF80` cycled a byte at a time through `JSR $57AC`/`$57B4`; the view buffer
  (`$4D06`, tiles at `$4880`, opacity at `$4980`) 21k.
- **The text window's scroll, `$5A90`, 33.7k, twice a step**: 12 rows of 128 bitmap
  bytes with a `CPY #$10` per byte. Its top row `$72` is always `$58` (the only stores:
  `startup` `$8A45`, `qs` `$8071`). The row tables are one row down from the plain layout:
  bitmap line n at `$2000 + 320 * (n/8 + 1) + n%8`, screen row k at `$0400 + 40 * (k+1)`.
- **The walking sound** (effect 7, `main.out` `$82E4` -> `$6112`, skipped when `$78`
  bit 7 is clear) 54k, 42k of it a fixed pause between two clicks.
- **Towns: the townspeople, `main.twn` `$9BB2`, 154k**: `$A35C` rebuilds a 32 x 32
  walkability map at `$BC00` every turn through `JSR $9F85` per byte (54k), and the
  neighbour search `$A37E`/`$A3FF` (~530 tests, 70k). The party panel (`$672B`) is
  redrawn when hit points change (a poisoned party: 55k a step).

Other readers of `$7F00` (`main.twn` `$997A`, `main.dng` `$9450`) fill it from a record
first. `main.subs` `$515E-$5183` is a lit-square helper; `$51F9`'s apparent branch into it
is row-table data. In `main.twn`, `$A345` is a live entry (`LDY $A1F9`). The tail after
`main.twn` was taken for a variable, `$A500`, but no instruction in the 236 files
addresses it: each of the 108 places whose bytes read as one (an absolute opcode, `$00`,
`$A5`) is a name's closing NUL followed by `LDA zp` (searched over every file; a computed
address is not excluded). Whether the tail is free was not checked further.

## Other details

- **Debug display**: C= + 1 in play shows the karma, the coordinates and more.
- Torches: lighting one is `SED / LDA $1186 / [CLC | SEC] / SBC #$01 / STA $1186 /
  CLD` at five places (`main.out` on 2A and 2B, 2B's `startup`, `main.twn`, `main.dng`);
  the `CLC` form subtracts two in BCD. The shops (`s`) are the only other writers of
  `$1186`.
- Keys break only when Jimmy fails ("Key broke!"; `s`, `cmd.dng` twice, `main.combat`,
  `main.twn`); View uses a gem (`main.dng`, `main.out` 2A/2B, 2B's `startup`,
  `main.twn`); Cast (`c` on 1B-4B, `oc` on 2B/3A/4A/4B, the same code four bytes on)
  checks the mixture at `$A7AC` (`LDA $1240,Y`), uses it, stores the cost into an
  `SBC #` operand at `$A7DA` and refuses on a borrow, then checks the circle against the
  caster's level.
- Food: `main.subs` `$5F9B` runs every turn; on an hour change it prints "Starving!" and
  hurts everyone without food, or at 06, 12 and 18 o'clock takes a ration per living
  member (`$5FE4-$6026`).
- Version residue: the drive code inside `u5siz.o` contains the string `STAR TROOPER`
  (`$7AE5`).
