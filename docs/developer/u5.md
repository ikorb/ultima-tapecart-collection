# Ultima V on the cart: how it works

The C64 game, unchanged but for its disk routines and a set of checked patches, loaded
from flash. Sources: `ultima/games/u5/build.py` (extract, patch, lay out; `parts()`),
`ultima/games/u5/u5drv.s` (the driver, two builds: C64 and `U5_C128`), `asm/init_u5.s`
(the init stub), the speed patches `u5anim.s`, `u5scroll.s`, `u5los.s`, `u5draw.s`,
`u5buf.s`, `u5walk.s`, the Action Replay music `armusic.py`, `armusic.s`, `armhook.s`
(and the same music from the Ultima VI EasyFlash, `armusic.s` with `EF_MUSIC`, `efhook.s`,
`ultima/ef/efu5.s`), and C128 mode `c128.inc`, `c128far.s`, `c128fast.s`, `sub128.s`, `launch128.s`. What the
original does is in `docs/reversing-notes/u5.md`; this file is about the cart version.

Disk keys: `u5-1a` (Program), `u5-1b` (Dungeon), `u5-2a` (Britannia), `u5-2b`
(Underworld), `u5-3a` (Towne), `u5-3b` (Dwelling), `u5-4a` (Castle), `u5-4b` (Keep).
The game numbers its disks 1-8 in the order 1A, 2A, 3A, 3B, 4A, 4B, 1B, 2B (`TAGS`):
disk N's BAM ID character is `$40 + N`.

## Shape

Every disk access goes through the 17-entry jump table at `$6C00` in `temp.subs`
(resident despite its name). Seven slots touch the drive; the other ten are engine
services and are left alone. All seven are handled:

| Slot | Original | On the cart |
|---|---|---|
| `$6C00` raw block read (A page, X sector, Y track) | `$6EAE` | `u5_block` |
| `$6C09` ensure disk N | `$6D47` | `u5_setdisk` |
| `$6C24` LOAD by inline name | `$6C49` | `u5_load` |
| `$6C2A` check disk ID (A = `$40 + N`) | `$6CAA` | `u5_checkid` |
| `$6C2D` scratch + SAVE, inline block | `$6DE0` | `u5_save` |
| `$6C30` 512-byte record | `$6E7B` | kept: it calls `$6EAE` twice directly; those two operands (`$6E9E`, `$6EAA`) point at `u5_block` (`RECORD_CALLS`) |
| `$6C1B` the moongate step | `$7472` | kept: it calls `$6C2D` (`TLIST`) |

`install_driver` checks that each vector is still the original `JMP` before it is
repointed. About 350 call sites in the overlays need no change.

**Three return contracts matter.** `$6C2A` and `$6C09` say "the right disk is in" with
the carry **clear**; their callers prompt and retry for ever on carry set, and `SBC #$40`
leaves it set, so `u5_setdisk` ends with `CLC`. `$6C24` returns carry clear on success:
`startup` `$8A14` does `BCS` back to the load, so a carry set there is an endless reload
behind a blank screen. A name not in the directory returns carry set and leaves memory
alone.

`$6C24`'s X is the post-action: 0 return after the inline string, 1 `JMP $8000` (a mode
root), 2 `JMP $A700` (an overlay). `u5_load` pulls the return address to find the
string, streams the name to the cart as it measures it, and pushes the continuation
back for the RTS.

## The cart does the name lookup

Nothing about U5's 236 files is in C64 memory. The tapecart's `DIR_SETPARAMS` (`$40`)
points the cart at a directory in flash, and `DIR_LOOKUP` (`$41`) matches a fixed-length
name against it and returns the entry's data bytes. Entries are 21 bytes:

- the name, 13 bytes: the disk number (1-8), then the file name padded with zeros to
  12. The key has to be the pair: `m` and `startup` are different programs on different
  disks.
- the data, 8 bytes: 24-bit flash address, length, load address, flags (`F_WRITE` = a
  save slot, `F_ZX` = a zx02 stream whose length is the stream's). The first seven land
  straight in tclib's `tc_addr`..`tc_dest`, which are contiguous.

The directory is set once, by the init stub; the cart keeps the parameters.

**Wildcards are resolved at build time.** `DIR_LOOKUP` matches bytes, and the game's
inline names include patterns (`D*`, `G*`, `CM*`, `ST*` ...). The disks' directories are
fixed, so what a pattern finds on a disk is known: `inline_patterns()` walks every
`JSR $6C24` inline string, collects the literal patterns, `resolve()` matches each
against each disk's directory in CBM DOS order (first match; `*` the rest, `?` one
character), and an extra entry keyed by the pattern itself points at that file. Names a
call site self-modifies (`TALK.XX`) are exact at run time and need nothing. The notes
count 236 files plus 38 aliases for 21 patterns, 274 entries (the build prints the
current counts).

The cart scans linearly, about 44 cycles an entry on hardware: a lookup takes 6.6 ms at
best and 18.5 ms at worst, against roughly 470 ms to transfer a 4 KiB file at 1 bit. That
is why the aliases are the patterns the code uses, not every prefix (which would be
about 2000 entries). The two directory commands are confirmed on real hardware.

## Memory

| Range | What |
|---|---|
| `$0200-$0276` | the init stub (`asm/init_u5.s`), once at launch; must end before `$0277` |
| `$2000` | `xyzzy`, patched, a boot segment |
| `$6C00-$76F8` | `temp.subs`, patched: vectors, four holes, motor and music gates |
| `$7700-$7AFF` | the resident driver, over `u5siz.o`'s fastloader (1024 bytes) |
| `$7B00-$7B56` | **the sound-effect routine: live**, byte-identical in `u5siz.o` and `subs.128` |
| `$7B57-$7FFF` | **the game's scratch area: not free** |
| `$A47A-$A5C7` | in overworld play: the launcher's X (`u5powers.s`, 334 bytes), appended to 2A's `MAIN.OUT` (2B: `$A470-$A5BD`) |

The fastloader never runs: `xyzzy`'s install is jumped over (below), and the file keeps
its original length (`u5siz.o` is overlaid, not replaced), so reloading it can never
reach the scratch area. The build fails if the resident part reaches `$7B00`.

**Nothing above `$7B56` is free.** An exhaustive scan of absolute loads and stores in all
236 files finds accesses throughout `$7B58-$7FFF`: `m` and `startup` around
`$7B90-$7BE6`, `main.out` `$7CAE`, `create` `$7C6D`/`$7CF6`, `main.twn` writing
`$7D00,X`/`,Y` from twelve sites, `main.combat` `$7DA6`, `talk.*` `$7DF3`, the sector
buffers from `$7E00`. In particular `main.twn` `$9B13` stores eight `$FF` empty-slot
markers at `$7D00-$7D70`, 16 bytes apart; driver code there gets those bytes punched
into it. The RAM under the I/O is not free either: a copy placed at `$D000` is
overwritten during the intro.

### The holes in `temp.subs`

What does not fit `$7700-$7AFF` goes into the original disk routines whose only entries
were the jump-table slots the driver has taken over (`HOLES`):

| Hole | Original | Holds (C64 build) |
|---|---|---|
| A `$6C49-$6CA9` | LOAD by name | `u5_slotread`, `u5_hdrsetup` |
| D `$6CAA-$6DDF` | check ID, ensure disk, the insert-disk prompt and its disk names | the zx02 decoder (`asm/zx02s.s`), the streamed patch applier (`asm/patch.s`), `pt_opts`, the AR read trampolines `u5_arget`/`u5_armap`/`u5_arout` |
| C `$6DE0-$6E7A` | scratch + SAVE | `u5_write`, the journal's second part |
| B `$6EAE-$6F4C` | raw block read | `u5_savefar`, the per-disk run and block-map tables, the save and block paths' variables |

The C128 build puts `u5_c128_ld` and its `u5_exit` in hole D and `u5_dirinit` in hole C
instead. Left untouched around them: the second jump table `$6C34-$6C48`, the device
byte `$6C33`, the record routine `$6E7B-$6EAD`, and `$6F4D`, a variable of the targeting
cursor at `$6F4E`.

The holes were checked two ways: VICE's memmap shows no access to them from boot through
the intro, Journey Onward, a town, the exit and the overworld (and hole D over 120 steps
of play with a fight); and every absolute JSR/JMP/LDA/STA into those ranges across all
236 files either comes from inside the dead routines or is misaligned bytes, text or map
data. `build.py` writes the pieces into `temp.subs` itself, so a reload of it keeps them.
`assemble_driver()` slices the four pieces out of acme's blob and fails if any byte
lies outside them, which is what catches a piece that grew past its end; each piece
also has an `!error` guard in `u5drv.s`. Every piece is within a few bytes of full.

The resident part holds tclib (`TC_NO_CMDMODE`, `TC_NO_FAST`, `TC_INIT_ELSEWHERE`,
`TC_PICK`), `u5_checkid`/`u5_setdisk`, `u5_load`, `u5_lookup`, `u5_fetch`,
`u5_enter`/`u5_exit`, `u5_save`, `u5_block`, `tc_host_pick` and `u5_jwrite` with the
journal's first part (`JR_PART = 1`). `tc_init` and the directory setup are not in the
C64 driver: they run once, from the init stub (`TC_INIT_ELSEWHERE`, `asm/tcinit.s`
assembled against the driver's symbols by `ultima/flash/tcsyms.py`); `build.py` fails
if they reappear.

## Boot

The menu loads four segments (`parts()`, the descriptor): `xyzzy` at `$2000`,
`temp.subs` at `$6C00`, `u5siz.o` with the driver at `$7700`, all three raw, and the
init stub at `$0200`. The stub:

- `SEI`, `$00` = `$2F`, `$01` = `$26` (BASIC out, KERNAL and I/O in, motor bit set);
- `$C6` = 0, dropping the key that chose the game (`xyzzy` reads `$C5`);
- `$C0` = 1 before the first `CLI` (the KERNAL IRQ starts the motor otherwise);
- `tc_init`, then `DIR_SETPARAMS` with the directory's page, entry count, name and
  data lengths;
- `JMP $2000`.

`xyzzy` patches (`XYZZY_PATCHES`): `$208D` becomes `JMP $20D5` over the drive prompt,
the `UJ` drive reset, the `u5siz.o` load and the fastloader install; `$210C` becomes
`JMP $211A` over the KERNAL load of `temp.subs`. What remains is the machine setup, the
`$0380` IRQ handler copy and `JSR $6C24 "ST*"`, which loads `startup` through the driver.
With the Action Replay music the `$208D` jump goes to the hook at `$2090` instead, which
ends in `JMP $20D5` (below).

**The `$C024` test.** `xyzzy` `$2042` (`LDA #$4C / CMP $C024`) takes the C128 path when
it finds a `JMP` there, the C128 editor ROM's byte. On a C64 that address is RAM and a
reset keeps it: with `$4C` left there by an earlier program, `xyzzy` sets `$C8` = `$80`,
blanks the screen and skips the C64 path's `$FFFE/$FFFF` = `$0380` store, and the first
interrupt in all-RAM banking goes through whatever is under the KERNAL. The menu stores
`$00` at `$C024` before loading any game's segments (`asm/menu.s`;
`test_collection.test_the_menu_clears_u5s_c128_probe`). A disk boot of the original has
the same weakness.

## Motor safety

U5 runs at `$01` = `$00` and banks in with `$01` = `$06`; both clear bit 5, which starts
the tape motor and drops the cart out of command mode. Six immediate operands become
`$20`/`$26` (`MOTOR`, each checked for its original byte):

| File | Operand | Original | Cart |
|---|---|---|---|
| `temp.subs` | `$7685` | `$06` | `$26` (I/O and KERNAL in) |
| `temp.subs` | `$7690` | `$00` | `$20` (all RAM, the steady state) |
| `xyzzy` | `$2063` | `$06` | `$26` |
| `scratch` | `$2045` | `$06` | `$26` |
| `update.himem` | `$1F47` | `$06` | `$26` |
| `intro.view` | `$9F36` | `$06` | `$26` |

The list comes from a scan of all 236 files that separated the six real `$01` writers
from 51 false positives in graphics data. A new patch that writes `$01` must keep bit 5
set.

## The I flag

`tc_enter` does `SEI` and `tc_leave` does not undo it. U5 plays with interrupts enabled
and its keyboard comes from the KERNAL's IRQ scan, so a driver call that returns with I
set leaves the game running, drawing, and deaf: character creation's first lore screen
never advances. Every driver entry goes through `u5_enter` (saves the flags) and
`u5_exit` (a `CLI` when the caller had I clear). `u5_exit` clobbers A and the flags, so
it runs before a return value is set up. Any symptom of the kind "the game is alive but
takes no key" or "a timed sequence stopped" is this first.

## Storage in flash

`parts()` lays out, from `regions.data_base("u5")`:

- **One stream blob**, deduplicated by content: every file the game loads by name, as a
  zx02 stream where that is smaller (`zx.crunch`; it returns `None` below 16 bytes,
  which the `zx02` tool cannot take), else raw, and every raw-sector block (below).
- **The save slots** at the top of flash (below).
- `xyzzy`, `temp.subs` and `u5siz.o`, raw and placed last (they carry the driver and
  its filled-in tables); the menu's boot segments and their directory entries share
  them.
- **The patch table** for the launcher's options, streamed by `pt_apply`.
- **The directory**, reserved before the driver file is placed (`Layout.reserve`):
  the driver needs its address, and its size depends on nothing placed after it.
  `u5_dirpage`/`u5_dircount` are filled in afterwards; placeholders of `$FF` are
  asserted before every fill.
- The Action Replay's songs and stage image, and the C128 launcher, its segments and
  its descriptor page.

### Raw sectors

The `$6C00`/`$6C30` callers (27 and 10 call sites, most computing track and sector from
game state) read a private data area that is in no file: blocks the BAM marks allocated
that no directory entry owns, on tracks 19-35 (2A, 2B), 24-35 (3A, 3B, 4A, 4B) and 23-35
(1B); 1507 blocks, 376.8 KiB, 337.8 KiB unique. `sector_runs()` finds, per disk, the
first such block (track 18 and 1A's unformatted track 6 excluded) and stores the run
from it to the end of the disk, which costs about 42 KiB over the orphan blocks alone
and makes the mapping two numbers per disk.

`u5_block` computes the linear block from track and sector (21, 19, 18, 17 sectors per
zone, summed in a loop rather than a 70-byte table), subtracts the disk's first block
(`u5_rfirst_lo/hi`; `$FFFF` for a disk without a run, so every block is "below"), and
reads the block's 4-byte entry in that disk's **block map** (`u5_rmap_lo/mid/hi`): the
24-bit address of its stream and its length, 0 for a page stored raw. Then it fetches
the stream into the caller's page. There is no upper bound to check, since every run
reaches the last block (`parts()` asserts it). A block below the run returns with the
buffer untouched.

A read returns with C clear, as the original's does when the drive found the sector: six
callers test it (`transfer` `$81F4` goes back to its prompt on C set; `main.out`, `p`,
2B's `startup`, `dng.precom`, and `main.dng` after `$6C30`, retry the read). The fetch
itself leaves C as it ends -- clear after a zx02 stream, set after a raw page
(`tc_getbyte`'s stop bit) -- so `u5_block` clears it. Raw pages are the U4 party's two
blocks and some 140 blocks of 3A-4B's town maps, which only `main.twn` reads, without the
test.

### Transfers

Everything goes through `u5_fetch`: a zx02 stream through `tc_stream_open`,
`zx_unpack` (`asm/zx02s.s`, which saves and restores four zero-page bytes from `$FB`,
safe because interrupts are off during the transfer) and `tc_stream_close`, or a raw
`tc_read`. All transfers run in all-RAM banking, so a unit may land under I/O or ROM,
and the display is never blanked (`TC_NO_FAST`: no `tc_blank`). On a plain C64 they are
1-bit; tclib's `TC_PICK` asks `tc_host_pick`, which goes 2-bit only when an Action
Replay's music is there (`$C8` bit 6; started from the Ultima VI EasyFlash, the
EasyFlash's, below) or, in the C128 build, through bank 1.

Named loads and saves call `$0126`/`$0129` around the transfer (mute and unmute the
music; `RTS` stubs that `xyzzy` writes when there is no music).

## Saves

The game writes six files (`WRITABLE`): `ROSTER`, `PRTY.DATA`, `LIST`, `SLIST`, `TLIST`
on disk 2A, and `TLIST` on 2B. Each is a slot of one 4 KiB erase block from
`regions.save_base("u5")` (`$1D7000`), in directory order: a header page (`$A5 $5A`, then
the 16-bit length), the data from `+$100`. The length lives with the data because the
game does not write back what it read (`ROSTER` is 1025 bytes on the disk and saved as
1024). The region's last block is the journal (`regions.journal("u5")`, `$1DD000`); the
region is 28 KiB.

- **Load**: the directory entry has `F_WRITE`; `u5_slotread` reads the header and points
  the transfer one page in. No magic = load error (carry set), which for `ROSTER` is the
  game's own "No active game!" path.
- **Save** (`$6C2D`, `jsr $6C2D / "S:NAME",0 / !word start / !word length`): the
  original scratches with the whole name and saves under the name plus 2. `u5_savefar`
  reads the block, looks up the name without `S:`, and when the entry has `F_WRITE`
  writes the slot through the journal (`u5_jwrite`: `jr_begin`, `u5_write` into the
  journal, `jr_commit`, `u5_write` in place, `jr_end`; `asm/journal.s`). `u5_write`
  erases the block, writes the data, then the header last. A save of a file with no slot
  is dropped (the game only saves the six). A save always returns carry clear.
- **C128 build**: `u5_write` straight into the slot, no journal (no room). A journal the
  C64 build left is finished by the first stage at the next C64 power-on.
- The first stage finishes or discards a journal at power-on (`docs/developer/saves.md`).

### The base state

The cart's base (what a fresh image holds and what Reset writes back) is generated, not
copied from the 2A image the player supplies: `ultima/disks/manifest.py` `SEEDS` makes 2A's five files
zero-filled with their load addresses and lengths (`ROSTER` `$1000`/1025, `PRTY.DATA`
`$BC00`/48, the lists `$4A00`/512), and 2B's `TLIST` a copy of 2B's `BLANK.ULIST`. The
master's 2A carries leftover bytes in those files ("the master's residue"); roster byte
0 is `$00` in both, so the game says "No active game!" either way. That is the one
difference `ultima/disks/verify.py` expects between a build from the reference disks
and one from the stand-ins.

Why the empty state is enough (from the code, every `TLIST` load and save site on the
eight disks read in context): `create` loads `BLANK.ROSTER`, `BLANK.PARTY` and
`BLANK.ULIST`, saves `TLIST` (2B, from `BLANK.ULIST`), `ROSTER`, `PRTY.DATA`, `LIST` and
`SLIST` (it empties `LIST` and `SLIST` at `$8266-$828E`), then loads `STARTUP`; every
game starts through Journey Onward, where `enter.play` copies `SLIST` to `TLIST`
(`$812E-$8146`) before anything reads it. 2A's `TLIST` is that world's object list while
the party is away from the surface: saved when it leaves (`temp.subs` `$74CC`,
`main.out` `$977A`, Gate Travel in `c` `$B8BA`), loaded only on the way back (`temp.subs` `$752B`,
`main.twn` `$8659`, `main.dng` `$88A2`, `main.out` `$9798`, `c` `$B916`). Confirmed in
VICE with 2A's `TLIST` slot filled with `$EE`: creation, Journey Onward and leaving the
hut never read those bytes. The other load sites follow a save on the way in (checked
statically, not run).

For debugging, `U5_SAVE_FROM=<dir>` seeds the slots from `u5-2a.d64`/`u5-2b.d64` in
that directory (`seed_saves_from`); such an image's banner says "DEBUG, do not flash: U5
seed" in red (`ultima/build.py` `DEBUG_SWITCHES`). `U5_NO_FAST=1` builds without the
speed patches ("slow" in the banner), for before/after measurements.

### The launcher's side

`p["page"]` gives the page `U5_ROSTER` (the roster slot, for names and hit points) and
the C128 launcher's flash address, length and block count. `p["xfer"]`: two disks,
"Britannia (2A)" with the five files and "Underworld (2B)" with `TLIST`, recognised by
their BAM names, written scratch-then-save as the game does; lengths `ROSTER`
1024 (1025 accepted), `PRTY.DATA` 48, `LIST`/`SLIST` 512, `TLIST` 256 or 512.
`p["journey"]`: `xyzzy` `$2109` `LDA $C5` becomes `LDA #$22`, the "J held" test, poked
by the menu before the init stub runs.

## Patches

All patches check the bytes they replace and stop the build otherwise.

- **Motor** (above).
- **`xyzzy`** (Boot, above).
- **Main menu** (`MENU_PATCHES`, 1A's `startup`): `$84ED` `JMP $850B` over the "Number
  of drives" line to the highlight call after it; `$85C5` cursor limit `$06` -> `$05`.
  The menu's keys `$C1-$CF` (A-O) are not drive digits: `$85A2` is `AND #$0F / TAX /
  JSR $6C40`, play song 1-15, and stay.
- **`transfer`** (`TRANSFER_TEXT`): its first two prompt lines (`$8170`, `$8197`) say
  the party comes from the Ultima IV save, same lengths and start columns.
- **Music gates** (`MUSIC_GATES`): every `LDA $C8 / BPL` ("a C128") guarding the songs
  becomes `BIT $C8 / BVC` (bit 6, "music is there", set by the C128 music setup and by
  the AR init): `temp.subs` `$76B8` (play) and `$76C6` (volume), `startup` `$91D3` (the
  title's walk through the score), `main.combat` `$86F5`, `u` `$B4FC`/`$B640`, `w`
  `$A781`/`$A963`, `end` `$AC81`. Only bits 0 and 7 of `$C8` are used elsewhere.
- **C64 gate** (`C64_GATES`): `enter.play` `$802A` `LDA $C8 / BMI` becomes
  `BIT $C8 / BVS`. On a C64 whose LOAD vector is the KERNAL's, Journey Onward installs
  disk-load hooks at `$0126-$0146` (sprites off and on around a load, for the
  fastloader's timing), over the music glue's API; with the gate they are skipped
  wherever the music is, and a plain C64 still gets them.
- **`temp.subs` music entries** (C64 build): `$76BC` `JMP $7703` (`subs.128`'s play on
  a C128) goes to the AR glue's `aplay`; `$76BF` (restart, not gated in the original)
  gets the same `$C8` bit 6 test and jumps to `arestart`.
- **C128 paths** (`XYZZY_C128_PATCHES`, `QS_C128_PATCHES`), on the one `xyzzy` and `qs`
  both machines load: `xyzzy` `$2055` `STA $00` -> `NOP NOP` (keep the DDR); `$20D9`
  `JSR $7715 / JMP $20F8` instead of LOAD `m` / `JSR $720F` / LOAD `SUB*`; `qs` `$8091`
  `JMP $80A1` over the reload of `subs.128`.
- **Speed patches** (below).
- **The launcher's options** (below).

## The launcher's options

`OPTION_PATCHES`, signature-checked RAM patches (`ultima/launcher/patches.py`,
`asm/patch.s`). U5's table does not fit in the driver, so it is in flash
(`PT_STREAM`): after every named load (not after raw sector reads), when an option is
on, `pt_apply` streams the table through tclib and applies each entry as it passes,
only where every original byte is in place. `pt_where` (flash address and length) is
filled in by `build.py`. `patches.check` proves each signature appears nowhere else the
game loads over that address (`option_units()` names the intended files).

- **FOOD** (bit 0): `main.subs` `$5FE4`, the ration taken at 06, 12 and 18 o'clock (and
  "Starving!" without food), jumped over to `$6027`, which keeps the hour's bookkeeping.
  Camping (`p`, `dng.precom`) and food-eating monsters still take food. U5 has no idle
  pass.
- **TORCH** (bit 4): the torch decrement's `STA $1186` becomes `BIT $1186` at five
  sites (`TORCH_SITES`): `MAIN.OUT` on 2A `$8D32` and 2B `$8D28`, 2B's `STARTUP`
  `$8D25`, `MAIN.TWN` `$8C7F` (3A-4B), `MAIN.DNG` `$8B53` (1B). The `LDA $1186 / BEQ`
  before still wants a torch. (The sites with `CLC / SBC #$01` take two in BCD, an
  original quirk kept with the option off.)
- **ITEMS** (bit 5): keys (`KEY_SITES`, Jimmy's "Key broke!" decrement in `S`, `CMD.DNG`
  twice, `MAIN.COMBAT`, `MAIN.TWN`: `STA $1184` -> `BIT`); gems (`GEM_SITES`, View in
  `MAIN.DNG`, `MAIN.OUT` 2A/2B, 2B's `STARTUP`, `MAIN.TWN`: `STA $1185` -> `BIT`); Cast
  (`CAST_SITES`, `C` at `$A7AC`/`$A7DA` on 1B-4B, `OC` four bytes on, on 2B/3A/4A/4B):
  the mixture's `LDA $1240,Y` becomes a `JMP` past its check and use, and the cost's store

## Music on a C64, from an Action Replay

An Action Replay 4.2/5/6 has 8 KiB of RAM: at ROML while mapped in (a store there
reaches the C64's RAM too) and its last page at `$DF00`, where a store does not.

- **The player, relocated** (`armusic.py`): `m` (1A, `$7200`) holds the player and 15
  songs. A recursive-descent walk (`ultima/sim/dis6502.py`) from the entries and the
  16-word jump table at `$762B` maps every operand or refuses it. Code and read-only
  tables go into the AR's RAM after a jump table at `$8000`; the writable state
  (`$7219-$7302` and the table the init fills at `$7BAE-$7BC3`) into the `$DF00`
  window; the 11 zero-page bytes the player swaps (`$9FF0-$9FFA`) to `$0100`. One address
  is built from two immediates (`IMM_PAIRS`, the instrument table: `ADC #$B8 ... ADC
  #$79`); `NOT_ADDRESSES` lists immediates that look like one and are not. The init's two
  C128 KERNAL-vector stores go. At a song's end (`NEXT_SONG`, `$7887`) the player jumps
  to `ar_next`: the same song restarts at once, another starts on the next tick (20 ms
  later), so the glue can load it first.
- **Songs on demand**: every song is position independent (tested by playing each from
  another address), the largest is 1100 bytes. They are loaded from the cart into the
  AR's RAM after the player; when one does not fit, all but the playing one are dropped.
  Each byte is stored with ROML mapped (reaching both RAMs), then the C64's byte is put
  back with the AR off: the game's mode roots live under the AR's RAM.
- **Never mapped outside the glue**: Ultima V never sets LORAM, so ROML appears only
  where the glue sets `$01 | %111`, and the AR's RAM is switched on (`$DE00` = `$20`)
  only inside it. `$DE00` is never read.
- **Glue in low RAM** (`AR_PIECES`): `$0100-$0122` (the player's zero page, variables),
  `$0123-$0173` (the music API where the C128 has it: `$0126` mute, `$0129` unmute,
  `ar_call`, both IRQ paths), `$0200-$0276` (the song loader), `$0335-$037F` (play and
  restart). The tick hooks both IRQ paths: the game's `$0380` handler and the KERNAL's
  `$0314` (the handler's `$6C03` does a `CLI` with the KERNAL in, so a pending interrupt
  goes through the KERNAL's path). Timer B on CIA 1 ticks the player at the rate each
  song sets.
- **Found by `xyzzy`** (`armhook.s` at `$2090`, in the skipped drive-prompt block, `$01`
  = `$26`): AR RAM on and `$01` = `$27`, a byte written to `$DFFF` must read back at
  `$9FFF`, through ROML, for `$A5` and then `$5A`: the AR's last page shows at both. RAM
  at `$DF00` alone is not enough: an EasyFlash has 256 bytes there, whatever its mode,
  and taken for an AR's it would leave the glue running from the C64's RAM at `$8000`,
  where the game's mode roots load; an EasyFlash's `$9FFF` is the C64's RAM (or ROM), one
  value through both stores. `$01` goes back to `$26` either way. Then the stage
  image (`armusic.s`, `arinit`) comes from the cart to `$4000`, free that early, sets
  everything up and sets `$C8` bit 6. Without an AR nothing changes. Works with the AR's
  fastload mode, which leaves `$DE00` = `$0A` and hooks vectors `xyzzy` puts back.
- **2-bit reads through the AR**: the receive (`asm/tcguard.s` bare, port values fixed
  for `$01` bits 0-2 = `%111` with `TC_F_XOR` taking the read-back bits out through the
  table) lives in the AR's block behind `AR_J_GET` (`$801B`) and `AR_J_PICK` (`$801E`);
  `build_armusic` asserts the driver's and the stage's addresses agree. `tc_host_pick`
  asks `ar_pick`, which reads `$D015` (sprite DMA it cannot dodge) and points tclib's
  `tc_fetch`/`tc_sb_call` at `u5_arget` (2-bit) or back at `tc_getbyte`. `u5_arget`
  sets `$01` = `$27` and `$DE00` = `AR_ON` for each byte, then `AR_OFF` and tclib's
  all-RAM banking before anything is stored, so a load into `$8000-$9FFF` reaches the
  C64's RAM. No `TC_NMI_HOLD` (no room).

Pitfalls the glue handles, each with a test that fails on the naive version:

- `ar_call` sets its self-modified operand after its `SEI`; the play entry's load,
  request and unmute cannot be split by the IRQ's own; the IRQ-time load in the `$0380`
  path runs behind a `SEI` the patch puts in front of the `JSR`, because `$6C03` does a
  `CLI` (`test_an_interrupt_anywhere` injects an interrupt at every possible
  instruction).
- **The KERNAL's serial routines use CIA 1 timer B** as an IEC timeout (`$ED94`,
  `$EE22`), and `startup`'s drive check at `$8417` runs them, stopping the timer:
  `ar_irq` sets `$DC0F` = `$01` on every interrupt (`test_an_interrupt_restarts_timer_b`).
- The play entry's wait (copied from `subs.128` `$7703`) ends in `BCS`, not the original's
  `BNE` after `SBC #$01`, which with no tick coming could spin for ever
  (`test_the_play_entry_returns_without_ticks`). The C128 port keeps the original loop:
  the C128's music never stops ticking.
- Journey Onward's hooks at `$0126-$0146` (the C64 gate above;
  `test_journey_onward_leaves_the_glue_alone`).

## Music on a C64, from the Ultima VI EasyFlash

The same glue with the U6 EasyFlash cart (`make ef`) in the expansion port instead of an
AR: its launcher's **5** starts Ultima V from the tapecart, which stays in the tape port.
The tapecart's image is not changed for it (`build_efmusic` adds nothing to it, and
`tests/test_u5_efmusic.py` checks that `parts()` comes out the same).

- **The bank** (`build.py` `build_efmusic`, `armusic.s` with `EF_MUSIC`): one 16 KiB
  bank of the EasyFlash's flash takes the AR's RAM's place, seen at `$8000-$BFFF` in 16K
  mode (`$DE02` = `$07`) with `$01 | %111`, as the AR's RAM is with its own register.
  The glue writes `$DE02` where it writes the AR's `$DE00`, and off is `$04`. A bank
  holds the player **with all 15 songs after it** (`armusic.py` `relocate(resident=True)`:
  2.2 KiB of code and tables, 9 KiB of songs, the header pointing at them as in `m`), so
  the player's init finds every song itself, a song's end keeps the original's `JMP`
  (`NEXT_SONG` is not changed), nothing is ever loaded: `ensure` is an `RTS`, piece B is
  not there, `ar_ensure` and the cache are not assembled. The jump table at `$8000` is
  the AR's, `AR_J_GET`/`AR_J_PICK` included (the build asserts the driver's), and the
  stage keeps `aplay` and `arestart` where `temp.subs` jumps (asserted against the AR's).
  The player's state goes into the cart's RAM at `$DF00`, always visible on the
  EasyFlash, all 256 bytes free while Ultima V runs. The stage (332 bytes) sits after
  the block in the same bank.
- **The hook** (`efhook.s`, at `$2090` over the AR's): `$01` = `$27`, the music's bank
  into `$DE00`, 16K mode, the stage copied from the bank to `$4000`, the cart off,
  `$01` = `$26`, `JSR $4000` (arinit), `JMP $20D5`. No looking for the cart: only the
  EasyFlash's launcher starts the game this way. Every write of the cart's registers,
  the hook's, the glue's and the driver's, is at `$01` = `$27`.
- **The launcher** (`ultima/ef/efu5.s`; [easyflash.md](easyflash.md)) reads the tapecart's
  own C64 boot segments through U5's descriptor page, as the menu does, so the driver's
  tables are always that cart's. It refuses another build (the descriptor and all four
  segments compared byte for byte with the EasyFlash's copy) and a waiting journal (the
  tapecart's first stage would finish it at power-on, and it does not run here). Then
  three patches in RAM, each checked against the tapecart's bytes at build time
  (`build_efmusic` `patches`): `u5_armap`'s `LDA #AR_ON / STA $DE00` becomes `LDA #$07 /
  STA $DE02`, `u5_arout`'s `LDX #AR_OFF / STX $DE00` becomes `LDX #$04 / STX $DE02`
  (same lengths), and `xyzzy`'s AR hook becomes `efhook.s`. The options byte comes from
  the tapecart's settings page, as the page and `launch128.s` poke it. Nothing reloads
  `xyzzy`, `temp.subs` or `u5siz.o` (no `JSR $6C24` inline name in the 236 files
  resolves to one of them), so the patches stay.
- **The game's own stores to `$DE00-$DFFF`**: a byte scan of the 236 files finds 193
  absolute operands there, most of them in data, but some real code: `main.subs`
  `$5817-$5856` stores twelve bytes to `$DF42-$DF6C` (sprite data in the RAM under the
  I/O). On a C64 without a cart such a store with I/O in goes nowhere; on the EasyFlash
  it would land in the player's state or the cart's registers. So the game must make
  them with I/O out: `tools/vice/u5ef_check.py` traces every store to `$DE00-$DFFF`
  with `$01 & 7` = 5 or 6 (I/O in, the cart's window out) through the title, character
  creation, Journey Onward, Britannia and a save, and finds none. That covers the paths
  played, not combat or dungeons.
- Reads: `u5_arget` through the patched trampolines, as with the AR. Measured in VICE on
  `u5_sweep.py`'s 160 transfers, parked at the main menu: raw blocks 6.73M cycles at
  2 bits against 7.87M at 1 bit on a plain C64 (-15%), named files 14.4M against 17.7M
  (-19%; most are zx02 streams, whose decoding does not get faster).

## C128 mode

Booted from 1A on a C128 the original runs natively: `m` plays from RAM bank 1, and
`subs.128` (at `$7700` over the fastloader) is an overlay cache. The cart keeps its
driver at `$7700` and moves `subs.128`'s code to bank 1:

- **`sub128.s`** at bank 1 `$E000` (free there) does what `subs.128` did, entry for
  entry: fetch overlay A to `$A700` from the eleven cached (C E I M P R S T U V Z) or by
  name, play song X, restart, the mode-root swap (both forms), Journey Onward's preload,
  the VDC map exchange, the KERNAL `$0A00-$0A28` exchange, plus `$7715`, the music setup
  `xyzzy` did with `m` in bank 0. It runs with the MMU at `$7F` (bank 1, all RAM; overlay
  U is cached under the I/O) and banks I/O in only for the VDC, reaching bank 0 through
  the KERNAL's FETCH/STASH (`$02A2`/`$02AF`) as the original reached bank 1. Its tables
  are copied from 1A's `subs.128` at build time (`sub128_data.s`).
- **The C128 driver** (`u5drv.s` with `U5_C128`) starts with eight `JSR C_FAR` at
  `$7700-$7717`; `C_FAR` (`c128far.s`, 31 bytes at common `$0200`) tells them apart by
  the return address, switches to bank 1 and back. `C_B0` (`$0100`) is the way from bank
  1 to bank 0 for a load (`u5_c128_ld`). The driver mutes the music around each
  transfer (`$0126`/`$0129`, as the original's disk code) and runs every transfer at MMU
  `$3F`. `u5_exit` restores the MMU, unmutes, and restores I.
- **2-bit reads from bank 1**: `b1_pick` (reads `$D015` and builds both receives' port
  values and `tcfast.s`'s nibble table from `$01`/`$00` as `tc_enter` left them) and the
  guarded 2-bit and a 1-bit receive live in `sub128.s`; tclib reaches them through
  `c128fast.s` in common RAM (`C_PICK`/`C_GET` at `$0113-$0122`, `C_BACK` at
  `$0297-$029C`), as `tc_host_pick` and `TC_FETCH`. No `$D030` write exists in the 236
  files, so the 1 MHz timing holds.
- **Common RAM used**: `$0100-$0122`, `$0200-$021F`, `$0292-$02A1` (the BASIC input
  buffer). **Not `$0380-$039F`**: `startup` copies `$C000-$CFFF` over `$F000-$FFFF`,
  which puts the C64 path's IRQ vector `$0380` into bank 0's `$FFFE`, and that handler
  runs on a C128 until the next unmute writes `$0220` back.
- **The launcher** (`launch128.s`) is a BASIC program the page writes to disk (C,
  `x_c128` in `asm/page_xfer.s`, scratch then save as `ULTIMA V 128`). Its `SYS` reads
  TXTTAB (DLOAD relocates), copies itself to `$1300`, enters command mode, and reads
  everything from **a fixed flash page, `regions.C128_DESC` (`$000700`)**: a version
  byte (`C128_DESC_VERSION`, checked), the driver's `tc_init`, `u5_dirinit` and
  `pt_opts`, the option caps and the settings byte's offset, `xyzzy`'s entry, and the
  segments with a bank-1 flag: `m` and `sub128.s` into bank 1 (MMU `$7F`, `$D506` = 8 KiB
  common so its own code stays visible), `c128far.s`, the two `c128fast.s` pieces,
  `xyzzy`, and the C128 builds of `temp.subs` and the driver into bank 0. It pokes the
  options byte from the settings page and jumps to `$2000` with MMU `$0E`, as the C128
  boot did. Because it reads that page, a disk written once keeps working after the cart
  is updated.
- **A C128's `$01` bits 0-2 are not banking**: they select the colour RAM bank and the
  VIC's character ROM. The launcher sets tclib's `TC_KEEP_01` = `%11000111` and
  `TC_IO_01` = 0; every game's own tclib keeps the C64 defaults.
- The saved game is the C64's, the same slots. No journal in this build (above).

## Pitfalls

- `$7B00-$7B56` and everything up to `$7FFF` belong to the game; so does the RAM under
  the I/O. New code goes into the holes or the AR/C128 spaces, after a static scan of
  all 236 files *and* memmaps of every mode (town, dungeon, combat, Journey Onward's
  first program, which on a C64 writes `$0126-$0146` and does not show in memmaps of
  play and the attract).
- `$0380-$03FF` is live code (the IRQ handler). A memmap of 120 steps of overworld play,
  a fight included, shows `$0335-$037F` and `$0200-$0276` untouched (the AR glue uses
  them when it is there; the VICE harnesses put their stubs there otherwise).
- Keep `$01` bit 5 set in anything that writes `$01`, and put the caller's I flag back on
  every driver exit.
- Byte scans over U5's files give many false positives (graphics and text decode as
  plausible code; a raw `STA $01` scan finds 57 hits, 6 real). Confirm with a
  disassembly from real entry points.
- `$6C2A`/`$6C09`/`$6C24` signal success with carry clear; a set carry is an endless
  retry, not an error.
- Breaking at the KERNAL's GETIN (`$F142`) catches nothing in play: the game runs at
  `$01` = `$00` with its own RAM copies of the KERNAL routines. U5 moves the party with
  the joystick (`$5BDF` reads `$DC00`); `u5_drive.py` patches around it.
- Hijacking the PC in VICE can land mid-transfer; park at `u5_blk_fetched` first.
