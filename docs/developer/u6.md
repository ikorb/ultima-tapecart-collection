# Ultima VI on the cart: how it works

Code: `ultima/games/u6/` (`build.py`; the drivers `u6res.s`, `u6bulk.s`, `u6core.s`,
`u6io_read.s`, `u6io_sector.s`, `u6io_small.s`, `u6boot.s`, `u6pack.s`, `u6end.s`; the REU
`u6reu.s`, `u6wc.s`; the game fixes `u6exp.s`, `u6key.s`, `u6scan.s`; the speed patches
`u6view.s`, `u6flood.s`, `u6light.s`, `u6walk.s`, `u6clear.s`, `u6chunk.s`; the shared
constants `u6.inc`), `asm/init_u6.s`, the launcher's side in `asm/page.s` (`i_u6`),
`asm/page_u6t.s` (the Avatar transfer), `asm/page_u6x.s` (export and import),
`asm/page_reu.s` (the REU line), and the host model of the write log in
`ultima/launcher/u6log.py`. What the original game does is in
`docs/reversing-notes/u6.md`; this file is about the cart. The EasyFlash build of U6
shares `patched_game()` (below) and is documented in `docs/easyflash.md`.

Disk keys: `u6-1a` (Surface), `u6-1b` (Dungeon), `u6-2a`, `u6-2b`, `u6-3a` (Populace A, B,
C), `u6-3b` (Game). In `build.py` they are the tags `1A`..`3B`; Surface and Dungeon are
disk 0 and 1 of the block maps (`SECTOR_DISKS`).

## Shape

Only the Game disk holds code. The original has two copies of one serial fastloader, and
both speak one command protocol (the reversing notes, "The loader's command protocol"):

| Command | Meaning |
|---|---|
| `^ t s off cnt` | read part of a sector (count 0 = 256) |
| `& t s` | write one sector |
| `!NAME` | a file's first track/sector; the drive frees the file's chain in the BAM |
| `#xx` | disk-ID check (`SU`, `DU`, `CA`, `CB`, `CC`, `GA`) |
| `/NAME`, `%NAME` | load by name, chained (`%` drops the PRG header, `/` keeps it) |

The cart replaces both loaders, one per phase, and keeps the protocol:

| Phase | Seam | Cart code at |
|---|---|---|
| boot (opening, creation, intro) | the resident loader `$C16B` (jump table `$C000-$C009`) | `$C16B-$C3D6` + `$C578-$C7FF` (`u6boot.s`) |
| play | `game`'s loader `$29BE` and the disk check `$2823` | resident: `$2823-$28CD` + `$2989-$2B4D` (`u6res.s`); on demand: 1 KiB in the idle sprite half (`u6bulk.s`) |
| the ending | the ending overlay's own loader `$C8C2` | `$C8C2-$CA8E` in that overlay (`u6end.s`) |

Plus the init segment `asm/init_u6.s` at `$1000` (the log, below) and the relocated
one-time init of `game` at `$4400`. The descriptor's entry is `$1000`; its segments are
the patched `$C000` image (1 KiB, from `u6load`'s payload), the boot driver's second piece
at `$C578`, and the init segment.

## Storage

Everything is in one cart directory (DIR_LOOKUP), 20-byte entries: a 12-byte key -- the
name **as the game sends it, prefix included**, zero padded -- then address (3), length
(2), flags (`F_ZX` a zx02 stream, `F_LINKS` a logged file) and 2 bytes extra.

- **Game-disk files** (`%NAME` and `/NAME`): stored raw, because the boot driver has no
  room for a decoder. `%NAME` points 2 bytes into `/NAME`'s data, so both spellings cost
  one copy.
- **Conversations** (`/T001`..`/T202`, Populace disks) and **chunk files** (`/Saa`..`/Shh`,
  `/Daa`..`/Ded`): zx02 where it shrinks them (`zx.crunch`), raw otherwise. Each chunk file
  also has a `!NAME` entry whose extra field is the file's first track/sector, which is what
  the save asks the drive for; its address and length fields hold the REU write cache's
  slot (`reu_slots`).
- **Surface and Dungeon sectors** read by position: raw, one page each, deduplicated,
  behind a **block map per disk** (21 entries a track, 4 bytes each: page address and a
  mark). Sectors that belong to a file point at one page of zeros: chunk files are never
  read by track and sector (traced over a played session). Marks: `M_LOGGED` (`$FF`) for
  the save area 1A T6 S9-20 (the game writes it; look in the log first), `M_BAM` (`$FE`)
  for both BAMs (T18 S0: always read as the original, writes dropped; see below). The raw
  pages are one contiguous block (`page_base`, 631 pages in the reference build), which
  is what the REU read cache keys on.
- The **patched raw sectors** -- T4 S15 (`exp()`), T24 S16-18 (Rest), T23 S16-18 (the
  ending) -- go in through `overrides`, on both disks; the build asserts each is in no file
  and identical on 1A and 1B where it should be.

Flash: the data region starts at `$0FB000` (612 KiB, `regions.py`); U6's save region,
the write log, is `$197000-$1D6FFF` (256 KiB), the lowest of the save regions, so it can
grow downward without moving anyone else's.

## The resident driver and the on-demand part

`u6res.s` sits in `game`'s own dead disk code: piece A `$2823-$28CD` (the disk check and
swap prompt) and piece B `$2989-$2B4D` (the old loader). `$28CE-$2988` between them is the
keyboard scan (rewritten by `u6scan.s`, but still the scan); `build.py` asserts the gap is
untouched. `$2823` only remembers which disk was asked for (0 Surface, 2 Dungeon; the
Populace and Game disks are read by name) and returns carry clear.

The resident handles the **plain sector read** -- 1680 of 2239 commands in a traced
session -- straight from the block map, and nothing else. Everything rarer (loads by name,
`!`, `&`, reads of `M_LOGGED` sectors) is `u6bulk.s`, fetched from flash into **whichever
half of the sprite double buffer is not on screen** (`$D800-$DBFF` or `$DC00-$DFFF`; `$27`
bit 4 says which is shown) and run there. It is assembled twice, once per origin. A trace
of 521,320 sprite-pointer stores over a game start and a save found none into the idle half
during a loader call. State that must outlive a call (the write session, the log's
position, the directories) lives in the resident.

**Keeping the part in its half.** `u6bulk` sets `u6_keep` to its own half on entry, and
the resident skips the fetch when the idle half is that one. `u6_keep` is dropped (set to
a value that is no half) by a load by name, which can come between any two frames -- except
the first three of `game`'s four object-file loads (`OBJ_CMD` `$243B`; the fourth is
quadrant `$2445`/`$2446` = `$80/$80`), which follow each other with no frame drawn -- by
`$2823` (the save's `#SU` and its closing `$2813`), and by `u6pack` (fetched over it).
`tools/vice/u6_keep_check.py` watches the invariant in VICE: no store into a half while
`u6_keep` names it, from code that is not the driver, over saves, window shifts and a walk;
its control (`u6_keep` poked during play) is hit at `$0946`.

Room is exhausted: piece B ends exactly at `$2B4D`, `u6bulk` has about a byte left.
`$02AE` in `game`'s jump table is `JMP $29B6`, which was a lone `RTS`; `u6io_small.s` is
placed so that an `RTS` of its own falls on `$29B6` (`U6_CB_RTS_AT`, asserted in
`build.py`).

**Interrupts stay on** during transfers (`TC_IRQ_ON`, `TC_NO_C0`): the 1-bit protocol
tolerates any delay, and the game's IRQ drives the keyboard and the sprite multiplexer.
Three IRQ handlers banked I/O in with `LDA #$35 / STA $01`, which clears bit 3, the
cassette write line the protocol clocks on: the resident loader's (`$C135`), `game`'s
(`$1F31`) and `create`'s (`$048C`), plus the ending overlay's. Each becomes `ORA #$05 / STA
$01` (same banking from `$34`, `$35` or the transfer's all-RAM value; bits 3-5 kept).
The opening's, intro's and `end`'s handlers bank nothing, and no load happens under them.
U6 reads at 1 bit everywhere in play (sprites are on in the game view); only the boot's
compaction reads at 2 bits (below).

**The access light**: `u6res.s` sets tclib's `TC_SCREEN_LED` to the frame cell at row 24,
column 23 (`$CFD7`, `LIGHT_CELL` in `u6.inc`): `tc_enter` stores `$81`, `tc_leave` `$89`
-- constants, so an unmatched pair cannot leave it lit. Only the low nibble shows there.
Row 24 is not among the cells `game` writes in play, and no file on the six disks stores
into `$CFC0-$CFE7` by an absolute address (a scan of all files; indirect stores not
covered). Only the game's resident has it, not the boot driver or the ending.

## Saves: the write log

A save (`$3E83`: Shift-S, every window shift `$22C5`, every level change `$25A9`) writes
the four chunk files of the window through `!NAME` and `&`, the BAM, then the 12 sectors of
1A T6 S9-20. On the cart **all world state goes to a write log** in U6's save region:

- pages are appended upward from the half's bottom; one 20-byte directory entry per logged
  unit is written **downward** from the half's top, newest lowest, and the cart's
  DIR_SETPARAMS is pointed at the newest, so a scan meets the newest version of a key
  first. A lookup tries the log's directory, then the static one. No invalidation, no
  erase in play.
- a save's chunk-file writes (`!NAME`, then its sectors with their link bytes) become one
  entry keyed `/NAME` (`F_LINKS`, the page count in its length), the same key the original
  has in the static directory, so a load by name finds the newest; the driver strips the
  link bytes on the way back. A save-area sector is keyed `$01`, disk, track, sector
  (`K_SECTOR`).
- **the BAMs are not logged** (`M_BAM`): the save picks a chunk file's new sectors from the
  BAM it reads after `!NAME`, and the drive's `!` frees the old chain first; the cart's
  cannot, so a logged BAM would lose about 13 of 1A's 74 free sectors per save and run out
  after about five (inferred from the code). On the cart a chunk file's position means
  nothing, so the BAM is always read as the original and its writes are dropped (closing
  the write session, as the save-area write would). Eight saves in a row in VICE: every
  chunk file complete, the same sectors allocated each time. An export to real disks
  therefore writes a BAM of its own.
- **the world reset**: the game never resets its chunk files (the manual asks for fresh
  copies). The boot driver erases the log at character creation's first write of T6 S9,
  once per boot (`u6boot.s`).
- the log relies on **partial-page writes leaving the rest of the page alone**: entries
  are 20 bytes, several to a page. ProgRef calls this undefined; in the tapecart firmware
  only the AT45 prototype driver wipes the rest of the page, and the 2 MiB, 4 KiB-erase
  configurations use the W25Q driver, a plain SPI page program, which does not.

**Two halves, compacted at boot.** The region is two 128 KiB halves. A half's top slot is
its first entry (generation 0) or a header (key `$FE "LOG"`, a 16-bit generation and its
complement); erased or torn means invalid. The active half is the valid one with the
higher generation (half 0 on a fresh cart). `init_u6.s` finds it by probing only each
slot's key byte (0.2-0.4 s a boot), finds the next free page (skipping any page that is not
wholly erased, which a save cut short can leave, starting from the newest entry whose pages
lie inside the half), and below `RESERVE` = 128 free pages **compacts**: the other half
erased, the newest version of every key copied into it, the header written **last**, the
old half erased. A power cut at any point leaves one valid half. Meanwhile a message
("tidying the world of ultima vi") and a 30-cell progress bar, white on black. The
compaction reads at 2 bits with the screen on (`g_read`: tclib's `TC_GUARD` receive from a
bare `tcguard.s`, interrupts off, no sprites); writes are 1-bit, the protocol has no fast
write. Measured in VICE: about 11.6 s typical, 36.3 s in the worst case (every chunk file
live, 221 pages) -- `tools/vice/u6_compact_check.py [worst]`.

The boot driver then hands the log's position to `game`'s driver: `$C071`'s `JMP $0200`
is `JMP ub_handoff`, which writes `u6_logdir`/`u6_logdata` into the resident, reads the
relocated init to `$4400` and jumps there.

**Compaction in play.** A save is about 30 pages, so the 128 the boot leaves last a
session of about four saves. When `b_append` finds no room, the on-demand part fetches
**`u6pack.s` over itself** (same half, through the resident's fetch), which compacts
exactly as the boot does and then fetches the on-demand part back; the command restarts
from its first byte (`b_sp` restores the stack). Safe, because before its first append a
command can only have closed the write session, and closing a closed one does nothing.
There is no live table (no room): an entry is live if DIR_LOOKUP of its key in the old
directory answers with its own address. The open write session's pages move last. Copies
go through a 64-byte buffer. A spinner turns in the cell after the command prompt (row 23,
column 23; bitmap `$E000` and colours `$CC00`, RAM, as this runs under I/O) and the cell is
put back. 1-bit reads, interrupts and sprites on: 15-50 s. Never drop a write to make room:
the player would lose progress without being told.

## The boot

`u6boot.s` replaces the resident loader's body at `$C16B` through `$C3FF` and adds a second
piece at `$C578-$C7FF` (idle in memmaps of the opening, creation and the intro). Of the
original `$C000-$C16A` -- jump table, cold start, machine setup `$C074`, descriptors
`$C0B6`, music IRQ `$C12D` -- three places are patched (`boot_patch`, each asserted):

- `$C00C` `JSR $C2E4` (the drive-code upload) -> three NOPs;
- `$C071` `JMP $0200` -> `JMP ub_handoff`;
- `$C135` the IRQ's `LDA #$35 / STA $01` -> `ORA #$05 / STA $01`.

The boot driver has its own copy of the sector read, the block maps and `u6core.s` (without
the write sessions); interrupts stay on (the theme plays from the IRQ during loads).
`init_u6.s` also blackens background and colour RAM until the opening's first picture (the
cold start blackens only the border, and its loads land in the menu's text screen, still
on show).

**Journey onward** pokes `$C025`/`$C026`: the cold start's `LDA #$00 / BNE $C036` at
`$C023` becomes `BEQ $C054`, the `$C006` path (load `game` and its assets, which reads the
save), after the machine setup and music.

**The Avatar transfer** (`page_u6t.s`, `init_u6.s` `xf_*`): the page pokes eight bytes
(`xf_lvl`, `xf_str`, `xf_dex`, `xf_int`, `xf_hp`, `xf_mp`, `xf_xp`; level 0 = nothing) next
to Journey Onward's pokes, and the boot, after its room check and any compaction, reads the
newest S12 and S13 and appends them patched, through the boot driver's own `b_lookup`,
`b_append` and `b_entry_write` (the world reset is in the command dispatcher, not there).
The page offers T only while the Avatar is as creation left it (level 3, 370 experience).
The fields it reads: U4 block 273 record 0 (+`$13-$15` STR/DEX/INT, +`$1A` the level as the
max HP's high byte, +`$1C/$1D` experience, BCD high first); U5 ROSTER record 0 at +`$80`
(+4-6 STR/DEX/INT, +`$C/$D` experience BCD high first, +`$E` the level, binary). U6 side:
experience `$585B + 2 x slot`, level in the low nibble of `$57BA + slot`, max HP 30 x
level, MP 2 x INT.

## The relocated init

`game`'s one-time init -- `$038F-$03FB` (the machine setup and its calls), `$1302-$13D9`
(the screen frame and its 12-byte table) and `$2077-$208C` (the page-1 and actor-table
fill) -- is named only by the init's own calls and never runs again. `relocate_init` copies
it (350 bytes) into flash, re-points its three call targets and the frame's three table
reads, ends it in a `JMP` to its tail (`JMP $03FC`, the main loop's entry, or the REU's
`reu_init`, which ends so), and zeroes the 347 bytes in `game`. The hand-off reads it to
`$4400` (the chunk index map, idle until the window loads). The speed patches and the REU
code take that room (`INIT_FREED`; `apply_fast` asserts each patch there lands on zeros and
inside one range). About 8 bytes are left.

## The ending

The ending starts from a code overlay (1A/1B T23 S16-18 at `$C800`, overlay `$3C`,
reached through the jump table's `$038C` -> `$2C15`). `end` fills `$0200-$7599`, `game`
and its driver included, so the overlay loads it itself through its own serial loader at
`$C8C2`, called with `%THEME2` -> `$9000`, then `%ICHARS` -> `$8000` + `%END` -> `$0200`.
`u6end.s` replaces that loader in place, same contract (C clear, `$01` = `$34` on
return), looking each name up in the static directory with DIR_LOOKUP; the directory's
position comes from the resident's `u6_sdir` on the first call, before `end` overwrites
it. 460 bytes, to `$CA8E`. The overlay's IRQ gets the `ORA #$05` patch. `end` itself needs
nothing: its `$DD00` code is VIC bank switching.

## Patches to the game

All in `patched_game(disks, irq_ora)`, shared with the EasyFlash build (which passes
`irq_ora=False`: there `LDA #$35` must stay). Every patch checks the original bytes first
and stops the build if they differ.

| What | Where | How |
|---|---|---|
| IRQ bank-in keeps the tape lines | `game` `$1F31`, `create` `$048C`, `$C135`, ending `$C892` | `LDA #$35` -> `ORA #$05` |
| Shift-L's Y/N | `game` `$2EF9` | `BCS` -> `BCC`: `$3E6C` returns C set for Y |
| key queue | `game` `$1F76-$1FB6` (`u6key.s`, `KEY_QUEUE`) | a frame with no key counts `$0197` down |
| keyboard scan, direction latch, Return as fire | `$28CE-$2988`, `$1FB7`, `$046C`, `$2084`, `$27ED` (`u6scan.s`) | below |
| the shrines' level check | T4 S15 (`u6exp.s`) on 1A and 1B; last 8 bytes of T191-T198 (3A) | below |
| Rest | T24 S16-18, `$C93B`, `$C8E1` (`REST_FIXES`) | below |
| copy-protection questions | T005, T033, T064 (2A) (`COMPENDIUM`) | below |
| text-box raster split | OPENING, INTRO, END (`steady_split`) | below |
| "press a key" | OPENING `$0C22`, INTRO `$09ED`, END `$0AFE` (`KEYWAIT`) | below |
| speed patches | `game`, see "Speed" | `apply_fast` |

**Shrines.** The Talk overlay T4 (T4 S9-20 at `$C000`) evaluates scripts in 8 bits; its
`exp()` (opcode `E0`, `$C650`) returned experience's low byte, which the eight shrines
compared with the low bytes of 0/100/.../6400. `u6exp.s` returns experience / 50 (at most
199) in the same 71 bytes, same entry and exits, and each shrine's table becomes `00 02 04
08 10 20 40 80`: every threshold is a multiple of 50, so the check is exactly the PC's.
Only the shrines and T001's debug editor call `exp()` (all 202 conversations decoded); the
editor's "Exp =" shows exp / 50 and its adds lose the 9999 cap (combat's award restores
it).

**Rest** (overlay `$20`): the guard's alarm printed through `$0383`, the inline print that
returns from the caller, so the `JMP $C923` after it never ran; the cart's is `JSR $0380` (print and
go on): hours 0, the party awake, the command ended. The guard prompt refused the last
member (`BCS` on equal); the cart's is `DEX / BMI / CPX $15 / BEQ / BCS` in the same 9 bytes.

**Copy-protection questions.** An answer list is `ASK` (`$F7`), per answer `KEYWORDS`
(`$EF`) words `ANSWER` (`$F6`) statements, then `ENDANSWERS` (`$EE`). The catch-all `*`
answer's first three bytes become a `JUMP` (`$B0`, 16-bit) to wherever the first, correct
answer goes; nothing moves. Each question is found by its text, its structure asserted.

**Raster split.** OPENING, INTRO and END switch `$D011`, `$D018` and `$DD00` at the text
box's first character row from an IRQ two lines earlier and a fixed BIT/NOP delay tuned
for NTSC; on PAL the stores could reach the badline. Now the IRQ comes a line earlier (the
split table less one), the routine waits on `$D012` for the line before the row, then 43
cycles: stores at cycles 59-73 on 63- and 65-cycle lines, whatever the interrupt latency.

**"Press a key".** The three overlays read keyboard column 4 without selecting a row; after
the title menu's scan port A's data register is `$FF`. The cart's routine `ASL`s `$DC00` while
port A drives, one more row each poll (20 of its 21 bytes, X and Y kept).

**Key queue** (`u6key.s`): `game`'s IRQ queued a key (`$D7E4`, count `$45`) when it
differed from the last seen (`$43`) or the repeat count `$0197` ran out; a frame with no
key did nothing, so a second tap of the same key was the first one held. Now a keyless frame
counts `$0197` down too, stopping at zero. Same 65 bytes; the direction-key search knows
Return, the only fire-bit entry of `$206D`, by its index 9 (`build.py` checks the table).

**Keyboard scan and latch** (`u6scan.s`): the scan `$28CE-$2988` is rewritten to do the
same in 140 of its 187 bytes (modifiers masked out of each row, the key's index counted
with the bits, the rows' selects from `game`'s masks at `$0225`). In the room: the
direction latch at the input handler's end (`$1FB7` jumps to it): the first direction
newly pressed since the main loop's last read (`$0449` copies `$47` to `$46` once a pass)
is shown in `$47` while nothing is held; the first IRQ after a read sees `$FC` at 7 and
empties the slot. Fire is not latched. And Return as fire: `$046C` (`STA $44 / RTS`) goes
to `$2084` and `$27ED`, which set fire in `$46` when the popped key is Return, because the
confirms (`$2F45`, `$1D43`) read only the sampled fire bit. Every caller of `$0449` and its
jump-table entry `$032C` reloads A and the flags after it.

## Speed

Profiled in VICE, a step was 74 % the view (`$1631`): its draw loop, the line-of-sight
flood `$178C`, the actors; every eighth step four chunk fetches, each a 64-byte read and a
whole walk of the object pool. The patches (each source's header says how):

- `u6view.s` -- the draw loop `$1697-$178B` (also called from `$25ED`): light level 4 is a
  plain copy, 0 a fill, 1-3 the original masked loop. Its two short loops live in the
  others' spare room (`-Dv_dark`, `-Dv_lit`, with limits; the assembler errors if they do
  not fit).
- `u6flood.s` -- the flood `$17A3-$189E`: a neighbour test is a bit shifted out of one
  valid-directions byte a cell; visit order kept (the first visit decides the marking).
  The original's dark-neighbour special case is dead logic (both paths do the same) and is
  gone.
- `u6light.s` -- the light map `$18E8-$198D`: two table reads instead of two `$30A9`
  calls a cell; the distance table keeps its 46 used bytes.
- `u6walk.s` -- the pool walk `$27CE` in line (89 -> 65 cycles a node). Its old entries
  `$27E3` (jump table `$02BA`, Use overlays `$00`, `$10`) and `$27EA` (`$02D5`, overlays
  `$08` and Look `$18`, and `$338B`'s `JSR`) are re-pointed at the same code.
- `u6clear.s` -- a window in which no tile blocks (`$A600 & $0C`) and none is tile 0 skips
  the flood: `$D600` = the tiles, the party's cell `$3C`. Hooked at the prologue's `STA
  $D63C`.
- `u6chunk.s` -- one pool walk per block of chunks instead of one per chunk: a strip (4
  chunks), a window load (16), and `$3FBD` (16; run after Get, Drop, Move, several Use
  classes, Cast and combat) and `$3399` (one chunk). Objects go straight into planes 2/3;
  first claim wins, as in pool order. What the old code left behind (`$33/$34`, `$80/$81`
  = 8, which Look and `$39E6` read without setting, the row pointers, counters) is left
  the same.

`FAST_ORIGINAL` holds the CRC of every span the patches replace; a disk whose spans differ
is refused. `apply_fast` also asserts TILES' level-4 mask (`$93C0-$93CF` all `$FF`), that a
view cell's lower half is 320 bytes after its upper (`$1E3A`/`$1E4C` tables), that the
kept distance table is the original's, that `$2061` is an `RTS`, and that no two patches
overlap. Measured in VICE: a normal step about 0.31 -> 0.27 s, on open ground 0.31 -> 0.23 s; a
chunk-boundary step about 0.7 -> 0.46 s; `$3FBD` 0.87 -> 0.17 s; a window shift 8.5 s (46
s on a 1541 with true drive emulation, `tools/vice/u6_shift_bench.py`), about 60 % of it
the 1-bit protocol.

## The REU

Optional, found at every launch; no switch. Two parts.

**The read cache** (`u6reu.s`, code at `$132E` and `$03C9`, variables at `$2077`, all in
the init's room). The hook is `tc_read`'s first instruction, `JSR tc_enter`, becomes `JMP
rc_read`. A read of exactly 256 bytes from a page's start inside the raw sector block is
looked up: the REU holds the block (page n at n x 256, banks 0-2) and a flag byte a page
(bank 3). Held: DMA (~100 cycles + 1 a byte, the cart untouched). Not held: from the cart,
then stashed and flagged. Everything else (block map entries, the on-demand code, the log,
the 64-byte chunk reads, loads by name) goes to the cart. Pages of the block never change:
a sector the game also writes is read from the log first by the on-demand part.

**The write cache** (`u6wc.s`). With an REU the on-demand code is two kilobytes: part A
(`U6_PART_A`: `u6core.s` without the writes) and part B (`U6_PART_B`: without the loads by
name, plus `u6wc.s`). `reu_init` points `u6_bulkfl` at part A; a command for the other part
brings it in over this one by DMA (part A stashed first; part B from the REU, or from flash
the first time in each half, `wc_bheld`) and reruns the command, as after `u6pack`. Bank 3
`$0300-$03FF` holds a count per slot (a chunk file's index from its `!NAME` entry, or
`$80` + sector for the save area); the copies are in bank 3 from `$0400` and in bank 2
(`u6.inc`, `reu_slots`). A save sector is compared with its copy by the REU's **verify**
(`$83`, status bit 5); the same: no page, no entry. A chunk file's pages are held back while
each is its copy's; at the first that differs, the held ones are written first from the
copy, through the game's buffer, which waits in the REU's scratch page meanwhile (after a
room check for all of them, since a compaction among them would rerun the command). A copy
counts only once its entry is written; `reu_init` clears every count at each launch, so
only what this launch wrote is trusted. A file the game stops writing short with every
page so far the copy's gets no entry (the old file stays whole, as on a drive; inferred
unreachable). A file that outgrows its slot is written every time. No checksums anywhere:
an exact compare or nothing.

**Detection** (`reu_init`, the relocated init's tail): the address registers hold what is
written, a stash/fetch round trip moves a byte, bank 3 differs from bank 1 (256 KB or more;
128 KB is refused), then the flag table is cleared. An Action Replay's RAM at `$DF00`
answers the registers but moves nothing; an open bus answers itself: both refused. Then
verify is tested on a page of its own code (the same, last byte different, first byte
different); if verify cannot tell them apart the write cache stays off and the plain
`u6bulk` is used. `rc_on` is 1 or 0; with 0 the hook costs an `LDA` and a `BEQ`. The
launcher's page (`asm/page_reu.s`) makes the same tests and prints the result, so the two
agree.

Without an REU the game runs the plain `u6bulk`, as built for that case; parts A and B
are only ever fetched after `reu_init` has found one.

Measured in VICE: Look's overlay 0.467 s first, 0.025 s after; Cast's 12 sectors ~1.08M
cycles -> 16k; a window shift 7.4-8.0 s (read cache only) -> 4.7-5.2 s with the write cache
(29 pages written -> 4-5); a save 5.1-5.3 s -> 2.4-2.8 s (29 -> 3-6). The first save of a
launch writes everything.

## Export, import, reset

`page_u6x.s`. A saved game of U6 is the whole world: 84 chunk files and the save area.
**Export** writes every chunk file (the log's newest, else the original) through fresh
chains from a pool the build worked out (`xfer_world`: the files' own sectors bar the
first, which the directory fixes, then what the BAM has free on tracks 1-17, in the game's
allocator order, track 17 down, sector 0 up -- less 1A T5 S20, free in the BAM but read by
position), then the save area, then a BAM that says exactly that. Any copy of the disks,
played or not, ends up consistent. The disks are recognised by the BAM's disk name and ID,
as the game does (`check_id`). **Import** follows every chain, logs only the chunk files and
save-area sectors that differ from the originals into the log's other half, and makes it
active with a header written last; a failure leaves the log as it was. The file export
(`ULTIMA VI SAVE`) carries the log's live chunk files and save sectors that differ, as
records. **Reset** erases the region; a fresh U6 log is all `$FF`. The page reads the party
from the newest S12/S13 (`i_u6`).

## The pristine state

The base is the reference disks' Surface and Dungeon, unchanged: U6 has no seed in
`ultima/disks/manifest.py` -- every chunk file, the save area (the factory state) and the
block-mapped sectors must match by hash. A played Surface or Dungeon is refused by
`ultima/disks/scan.py` (`HINTS`: "the world differs: this disk has been played and
saved"). The one fixup: a Surface disk with a new character never saved (`CREATE` writes
only the save area) has the fields creation fills in put back to the factory's
(`manifest.RESETS`, [disks.md](disks.md)), so it builds the same cart as an unplayed one. `ultima/disks/importsave.py` takes a played pair whole as a saved game and imports
it through the page's own import on the host. Two played dumps whose changes do not
overlap can complete each other, since every unit is still matched by its pristine hash.

## Pitfalls

- **No code may run from `$D000-$DFFF` while I/O is banked in.** The on-demand parts live
  there; anything that touches I/O (the REU's status) must be resident (`rc_status`).
- **The REU's DMA goes through the C64's banking.** Arm the command (bit 4 clear) and
  start it with `LDA $FF00 / STA $FF00` at `$01` = `$34`, or a fetch into `$D000-$DFFF`
  writes the chips (overlay `$34` at `$D400`, the BAM at `$D500`, buffers at `$D600`). A
  test model must not store a register write with I/O in into the RAM below.
- **`$27F4` (`00 40 80 C0`)** is read by the sprite builder at `$093B` as well as by the
  chunk fetch. **Scan every overlay for absolute operands** into anything a patch
  rewrites: jump-table entries (`$02BA`, `$02D5`) reach "internal" entry points.
- **`tc_read` leaves `tc_dest` alone** (it copies it into a self-modified store), whatever
  its comment in `asm/tclib.s` says.
- **`game`'s variables are not adjacent**: the hand-off writes the log position field by
  field; a block copy across them overwrites the keyboard scan at `$28CE`.
- **A static scan for dead code is not enough**: `$37D4`, with no pointer to it, is actor
  type `$81`'s handler, reached through split low/high byte tables (`$422F`/`$4242`).
- **RAM**: almost none is free (`docs/reversing-notes/u6.md`, "RAM the game leaves
  alone"). `$FFC0`.. is the text line buffer with no fixed end.
