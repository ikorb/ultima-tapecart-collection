# Akalabeth on the cart: how it works

Code: `ultima/games/u0/build.py`, `asm/init_u0.s`, the launcher's side in `asm/page.s`
(`i_u0`, `ow_u0`, the options' words). What the C64 release does is in
`docs/reversing-notes/u0.md`; this file is about the cart.

Disk key: `u0`, Genesis Project's release ("accept no limits"): `AKALABETH+4  /GP` and
`LIB`, the only units the build reads (`ultima/disks/manifest.json`). The pictures'
files are not needed.

## Shape

Akalabeth is a compiled BASIC program with its runtime, `$0801-$7A2E`, and a graphics
library, `LIB` (`$C000-$C8A6`). It reaches the drive only to load `LIB` as it starts and
the three pictures of its instructions; it never saves. So the cart has **no driver**:
both its files are segments, the program is patched not to load, and nothing of the
tapecart is used once the game runs.

| Segment | Destination | Stored |
|---|---|---|
| the program | `$0801-$7A2E` | zx02, 13.1 KiB |
| `LIB` | `$C000-$C8A6` | zx02, 1.4 KiB |
| the init stub, `asm/init_u0.s` | `$0334-$03FF` | raw |

The entry address is the init stub's, `$0334`.

## The unpack

The main file is packed together with Genesis Project's intro. `build.py` `unpack()`
runs the file's own decruncher in py65 from its `SYS 2061` (`$080D`) until it hands over
to the intro at `$3000` -- about 1.9 million instructions, a second or two -- and takes
the program from `$4000`, where the decruncher leaves it for the intro to move to
`$0801`. The model sends writes to `$D000-$DFFF` to the chips while `$01` has I/O in, as
Ultima III Gold's unpack does (`ultima/games/u3/goldunpack.py`). The result is pinned
(`PROGRAM`, 29230 bytes), as are both files (`MAIN`, `LIB`). Checked against VICE: the
program at `$0801-$7A2E` in VICE's RAM as the intro starts it is byte-identical.

The program ends at `$7A2E`: the runtime's own pointers (`$1F93`, which `build.py`
checks) put VARTAB at `$784C` -- the scalar variables' names are compiled in -- and
ARYTAB at `$7A2F`. Arrays and strings are made as it runs, up to `$A000`.

## The patches

Each is a run of `:` (`$3A`), the runtime's empty statement, over whole statements
(`build.py` `FILLS`, each checked by the bytes at its ends and the one after it, and the
whole program by its pin first):

| Range | Was |
|---|---|
| `$20A2-$20A4` | `GOSUB $76E6`: the trainer's questions |
| `$691D-$6932` | `PRINT "LOADING...": FL$="LIB": GOSUB $6261`, the LOAD |
| `$6AE0-$6BE0` | the three pictures: their loads, the bitmap mode, the `LIB` calls that show them |

What stays around the pictures' run: the key before it (`GOSUB $62CB`), `POKE
53265,11`, which blanks the screen for the pictures, and after it the `GOSUB $62A8` that
brings the text screen back, which unblanks it, and the clear screen. The runtime keeps
an operation pending in `$3B` across bytes, and only a statement's end clears it
(`$0EAC`). A run that starts inside a statement leaves one pending, and a later RETURN
fails (`?RETURN WITHOUT GOSUB ERROR IN 25290`): the pictures' run starts after the
blanking POKE's last byte, not at it.

With these, no GOSUB to the LOAD routine is left in the program, and the routine itself
holds the program's only `SYS 65493` (`tests/test_u0_build.py`).

## Boot: `asm/init_u0.s`

The menu leaves interrupts off and BASIC's state as the launcher had it. A player would
LOAD and RUN the program; the stub sets up what RUN would find and starts the runtime as
`SYS 2076` does:

- `$00`/`$01` = `$2F`/`$37`;
- MEMBOT `$0800` and MEMTOP `$A000` (`$0281-$0284`), then the ROM's `$E453` (BASIC's
  vectors) and `$E3BF` (BASIC's zero page: CHRGET, the temporary string stack at `$16`,
  TXTTAB and MEMSIZ from MEMBOT and MEMTOP). A stale `$16` is `?FORMULA TOO COMPLEX` at
  the program's first string;
- the keyboard queue emptied, `$C0` = 1 (the KERNAL's IRQ starts the tape motor while
  `$C0` is zero and sense is low, and the cart would drop out of command mode -- harmless
  here, but there is no reason for it), `CLI`, `JMP $081C`.

The runtime sets the variables' pointers itself and clears them.

## The options: the trainer's flags

The game reads four flags, `PEEK(1020)`-`PEEK(1023)`, which Genesis Project's trainer
sets to 100 for a Y. The stub's segment runs to `$03FF` and ends in the four of them,
zero: the menu loads it, then applies the page's pokes, then runs the stub, which leaves
them alone. So each option is a **poke option** of the page (`p["options"]["pokes"]`),
100 into its flag, and there is no options byte (`addr` 0):

| Key | Bit | Flag | Option |
|---|---|---|---|
| F | `FOOD` | `$03FF` | Food used while walking |
| G | `ITEMS` (its key `oi_key`) | `$03FE` | Gold spent when buying |
| H | bit 7 (`o7_key`) | `$03FD` | Monsters can hurt you |
| A | `AVOID` | `$03FC` | Attacks can miss |

As for every game, "on" is the game as it was (the bit clear, no poke). G's and A's lines
have Akalabeth's own words (`page.s` `ow_u0`), and the items bit's key is G here, not M
(`oi_key`, checked before G's graphics, which Akalabeth does not offer); H is bit 7's
line, whose words and key are per game anyway. The settings keep Akalabeth's options byte at `+$0A` (`4 +` its
descriptor index, 6).

## No saves

There is no save region: `regions.SAVES` has no entry, `save_region("u0")` is empty, and
the launcher builds no reset table for it (`rs_lo`/`rs_hi` 0). The page takes that as
"this game saves nothing": no saved-game line, no R; with no Journey Onward and no
export tables, no J, E or I either.

## Flash and the list

Akalabeth's data region follows Ultima VI's (`regions.DATA`, "u0"). Its descriptor is
the top page of the reserved area, `$007F00`: pages `$000100-$000600` are Ultima I-VI's,
`$000700` is Ultima V's C128 descriptor (pinned: the C128 launcher on a player's disk
reads it), and the first stage follows. The game list's records carry each descriptor's
page, so the menu reads Akalabeth's from there like any other. It is the list's first
game: its key is 0.

## Tests

- `tests/test_u0_build.py`: the unpack against the pin; the segments as the menu decodes
  them; the stub's calls and its zero flags; the program different from the unpack only
  in the three runs, each all `:`, and `:`'s handler (`$0ECB`) from the runtime's table;
  no GOSUB to the LOAD routine or to the trainer left; every flag read by the game
  outside the trainer.
- `tests/test_page.py` `test_akalabeth_s_page`: the page's lines, the keys that do
  nothing there, the pokes for each set of options and the settings remembering them.
- In VICE, `tools/vice/u0_check.py`: from the menu, twice -- options as they were, and
  all four toggled: the flags, no trainer, the instructions' pages as text, a character,
  gold spent or not, a walk to a dungeon with food used or not, its ladder; a breakpoint
  on the KERNAL's LOAD throughout. `make run-menu` starts it from the menu too.
