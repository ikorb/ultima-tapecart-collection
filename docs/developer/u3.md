# Ultima III on the cart: how it works

How the cart version of Ultima III: Exodus is built and how it runs. The original game
is described in `docs/reversing-notes/u3.md`, and the fan version whose changes are
ported in `docs/reversing-notes/u3-gold.md`. What a player sees is in
`docs/changes/u3.md`. Rules that apply to every game (the `$00`/`$01` rules, tclib, the
flash map) are in `docs/developer/README.md`.

## Shape

Ultima III keeps the structure of the Apple II version. Game code never calls a loader.
It prints an Apple DOS 3.3 command (`^D "L MAPA"`) through the DOS module's character
output at `$B815`. The module parses it, looks the four-letter name up in the catalog at
`$B000` (94 entries of 8 bytes: name, start block, length in blocks, destination page),
fills a parameter block at `$BB00` and calls `dos_transfer` at `$BA48`. All 44 call
sites go through that one routine.

The cart replaces `$BA48` and nothing above it:

- `$BA48` in the DOS module becomes `JMP $BC00` (build.py asserts the original first
  bytes, `LDA #$00 / JSR $FF90`, before patching).
- The catalog is rewritten at build time. Each entry's start field (+4/+5) becomes a
  **flash page number** instead of a disk block. The driver reads it as one.
- `catalog_find`, the `^D` parser and all 44 call sites are untouched. No "which disk
  is in the drive" notion is needed: each catalog entry identifies its content, because
  the build resolves which of the two disks it lives on.

Parameter block, as the driver reads it (DOS module, `$BB00`):

| Address | Meaning |
|---|---|
| `$BB00` | 1 = load, 2 = save |
| `$BB01` | destination low byte, always 0 |
| `$BB02` | destination page |
| `$BB03`/`$BB04` | flash page (the catalog's rewritten start field) |
| `$BB05` | block count; bit 7 set = a writable entry |

Two flags ride in the catalog:

- **Writable**: bit 7 of the length byte. Real lengths are 1-87 blocks; 87 (EXOD) already
  has bit 6 set, so bit 7 is the only free one. The dispatcher copies it through to
  `$BB05` unchanged.
- **Stored crunched**: bit 15 of the start page. 2 MiB is 8192 pages, so bits 13-15 of
  a page number are spare. The length byte has no room for it: a flag there truncates
  EXOD from 87 blocks to 23.

## Memory

All addresses are C64 RAM while the game runs.

| Range | What |
|---|---|
| `$0200-` | `init_u3.s`, the init stub (BASIC's input buffer, free once past BASIC) |
| `$0825-$090F` | the boot PRG's credits painter and its text, loaded as a segment (its final `JMP $0910` into the loads made an `RTS`) |
| `$3000-$86FF` | EXOD, the intro (a boot segment and a catalog entry, one unit) |
| `$B000-$B3FF` | the catalog, rewritten |
| `$B800-$BBFF` | the DOS module, `$BA48` patched |
| `$BC00-$BFEE` | the driver: entry table, tclib, `u3_transfer`, save code. Must end below `$C000` (DEMO); acme `!error`s and build.py checks it |
| `$C500-$C9C4` | the decoder segment: `zxdecr.s`, `patch.s` and the options table, `u3_opt_once`, `tcguard.s`, `u3key.s`, `u3step.s`, `u3view.s`, `u3trainer.s`, `u3avoid.s`, `journal.s`. Must end below `$CA00` (UPDT); acme `!error`s |

(End addresses are those of the current build; the limits are what the asserts enforce.)

`$BC00-$BFFF` and `$C500-$C9FF` are the two areas the original's memory map lists as
free. The driver does not fit in `$BC00-$BFFF` with the decoder, so acme assembles one
blob from `$BC00` to the end of the decoder segment, and build.py slices it at
`u3_drv_end` and at `$C500`. The hole between them covers DEMO (`$C000`) and DDAT
(`$C100-$C4FF`). build.py refuses a non-zero hole, which is also the proof that the
driver stayed below `$C000`.

Gold's save cache uses `$E000-$F2FF` under the KERNAL and its animations use
`$0334-$0354`. Neither is used by the driver, the init stub, tclib or the decoders.

**No zero page.** tclib and `zxdecr.s`/`zx02a.s` use no zero page at all: their pointers
are self-modified absolute operands. This is a hard requirement for U3: ULT3 uses `$F7`/
`$F8` (the party's position) and much of the rest, and there is no run of zero page free
across the games. A transfer that clobbers zero page shows up as subtly wrong game state
after a load, such as a new party starting in the ocean.

## Boot

The menu loads seven segments from the descriptor (`regions.desc_offset("u3")`,
`$000200`), then jumps to the init stub:

| Segment | Destination |
|---|---|
| EXOD (shared with its catalog unit, zx02 sized) | `$3000` |
| the DOS module, patched | `$B800` |
| the catalog, rewritten | `$B000` |
| the driver | `$BC00` |
| the decoder segment | `$C500` |
| the init stub | `$0200` |
| the credits painter | `$0825` |

`init_u3.s` repeats the boot PRG's machine set-up (`$0810-$0824`): `$00` = `$2F`, clear
the screen through CHROUT, KERNAL messages off (`$FF90`), `$01` = `$36` (BASIC out,
KERNAL and I/O in, motor bit set), border and background black. Unless the options byte
has JOURNEY, it calls the credits painter and holds about four seconds (200 frames,
counted on raster line `$FB`), ending early on a key read straight from the CIA with
interrupts off (`$DC00` back to `$7F` afterwards). It consumes a pending key as the
original does at `$0910`, calls the driver's `tc_init` (`JSR $BC03`), sets `$C0` = 1,
`CLI`, and jumps to EXOD's entry `$8220`. The original never masked IRQs, and U3 plays
with interrupts on and the KERNAL IRQ live.

EXOD loads `BOOT` itself (`^D "R BOOT"`), and from then on every load is a catalog load
through the driver.

## Storage in flash

**One unit per catalog entry.** The catalog references 606 of the two disks' 1366 blocks
(the highest used is block 284 on disk A and 381 on disk B), and no two entries share a
block. So each entry is stored as its own page-aligned unit, and the rest of the disks is
not stored. Data region: `regions.data_base("u3")`, 68 KiB.

- The ten program files (`EXOD`, `TEXT`, `SHPS`, `DEMO`, `ULT3`, `DDAT`, `BOOT`,
  `SUBS`, `MUSI`, `COPY`) come from disk A, the rest from disk B. Both disks use one
  block-number space, so the disk matters for every block number.
- Each read-only unit is patched (below), then crunched with zx02 in the **sized** form
  (`zx.sized`: the stream starts with its own 16-bit length, because the catalog has only
  a block count). A unit that would not shrink is stored raw (`zx.smaller`). Crunched
  units set bit 15 of the start page.
- EXOD is both a catalog entry and the `$3000` boot segment. `Layout`'s dedup makes them
  one unit, and the menu decrunches the same blob the catalog points at.
- `OUTM` and `DNGM` are replaced by the cart's own (`PEERS`), and their catalog length
  becomes the new length in blocks.

**Loads.** `u3_transfer` (via `$BC00`) lets a footstep's clicks in flight finish
(`st_flush`, [A step on the surface](#a-step-on-the-surface)), saves the caller's status byte, runs the transfer,
calls `pt_apply` (the launcher's options) and `u3_opt_once`, then puts the caller's I flag
back by hand (`CLI` if it was clear) while keeping the transfer's carry. tclib's
`tc_enter` does an `SEI` that nothing else undoes.

- Crunched: `zxd_unpack_sized` with `$01` forced to `ora #%00000110`.
- Raw: one `tc_read` of blocks x 256 bytes, with the same banking.

tclib configuration in `u3drv.s`:

| Symbol | Effect |
|---|---|
| `TC_NO_CMDMODE = 1` | the launcher entered command mode; it is held all session |
| `U3_FAST = 0`, `TC_NO_FAST = 1` | no `READ_FLASH_FAST` and no blanking |
| `TC_GUARD = 1` | 2-bit reads with the screen on, waiting out badlines; 1-bit while a sprite is enabled |
| `TC_NMI_HOLD = 1` | a RESTORE during a transfer is held off, not taken through RAM vectors |
| `TC_GUARD_ELSEWHERE = 1` | `tcguard.s` goes into the decoder segment, because `$BC00-$BFFF` has no room |

U3 does not touch CIA 2's timers or interrupt mask (no absolute `$DD04-$DD0F` operands on
its disks), which `TC_NMI_HOLD` relies on.

## Patches

Every patch asserts the original bytes before writing.

### Fixed patches (build.py)

| Unit | Address | Change | Why |
|---|---|---|---|
| DOS module | `$BA48` | `JMP $BC00` | the seam |
| BOOT | `$103F` | `JSR $1DF4` -> 3 x `NOP` | the copy protection: `$1DF4` reads track 6 sector 8 and hangs at `$1E42` if the read succeeds. On an original the read fails and the routine returns having done nothing, so the NOPs are faithful |
| BOOT | `$1055` | `JSR $46C3` -> `JMP $1079` | skips "INSERT SCENARIO DISK" and its key wait (`$1072-$1078`). The text is inline after the JSR, so the call cannot be NOPed |
| EXOD | `$855E` | `CMP #$C3` -> `CMP #$00` | C at an intro wait ran `COPY`, the disk duplicator, which needs a drive. No key code is `$00` (`$B80C` returns `$FF` for none), so C ends the intro like any key |
| SUBS | `$4EB4` | `JSR $B80C` -> `JSR kb_take` | type-ahead (below) |
| SUBS | `$4EBB` | `JSR $B80F` -> `BIT $B80F` | the flush after a key |
| ULT3 | `$50A9`, `$6F25`, `$72D8`, `$7FFD`, `$8B6D`, `$8F25` | each `JSR $B80C / CMP #$FF / BEQ / JSR $B80F`: the poll to `kb_take`, the flush to `BIT` | type-ahead. `$8198` polls without a flush and is left alone, as are ULT3's flushes before its prompts |
| ULT3 | `$52AF`, `$50E5`, `$801E`, `$61DA` | hooks to `tr_board`, `tr_key`, `tr_fight`, `tr_other` (`TRAINER_HOOKS`) | Gold's trainer keys |
| ULT3 | `$93AF` | `CMP #$64` -> `CMP #$40` | the teleport refuses 64 and above (Gold refused only 100 and above, so 64-99 put the party off the 64 x 64 map) |
| ULT3 | `$762B`, `$7777`, `$6951`; `$9367`, `$9372` | hooks to `tr_pool`, `tr_back`, `tr_xit` (`TRAINER_HOOKS`); `JMP $52D0` -> `JMP $52D4`, `JMP $52B2` -> `JMP $52B6` (`TRAINER_EDITS`) | the map kept whole with the trainer keys ("Trainer stubs", below) |

| ULT3 | `$730D` | `JSR $71D3` -> `BIT $71D3` (`STEP_PANEL`) | `$72EC` drew the party's panel, and each of its three callers (`$6DC0`, `$7F72`, `$8DD0`, asserted) draws it again at once |
| SUBS | `$470E` | `JMP $4D3D` -> `JMP st_fx` (`STEP_FX`) | every effect waits for a footstep's clicks in flight |
| MUSI | `$9A7B` | `JSR $9A86` -> `JSR st_tick` (`STEP_TICK`) | the IRQ plays the footstep's later clicks |

| UPDT | `$CA99` | `JMP vw_los` (`VIEW_LOS`; the original's `$CA99-$CB00` and the step tables `$CBE8-$CBFD` pinned) | the line of sight in one pass |
| OUTM, DNGM | whole unit | `u3outm.s`, `u3dngm.s`; the original unit's SHA-256 prefix is asserted first (`PEERS`) | the peer in colour |

**Type-ahead (`u3key.s`).** The DOS module's `$B80C` (`$B952`) returns the *last* key in the
KERNAL queue without removing it, and the callers then flush the queue, so only one key
of a burst ever counted. `kb_take` returns the *first* key, with bit 7 set, and moves the
rest up. With the queue empty it reads joystick 2 at most every 5 jiffies: directions as
`@ / : ;`, fire as E (`$62` = 0, Sosaria), T (`$62` positive, a town) or A (`$62`
negative, combat and Ambrosia). It returns `$FF` for none, keeps X and the I flag, and
sets Z/N as `CMP #$00`. This follows `ultima/games/u4/u4key.s`, itself from Ultima IV
Remastered's `fixed_getkey`.

**Trainer stubs (`u3trainer.s`).** Gold's trainer code is in the cart's ULT3 already (the
tail `$922F-$93FF` of Gold's image). In Gold, BOOT poked the hooks in only when the
trainer was answered Y. On the cart the hooks are always in. They go to stubs that test
`tr_on` (`$80` = on, a launch poke from the page) and take Gold's path or the
original's:

| Hook | Off (original) | On (Gold) |
|---|---|---|
| `$52AF` Board with nothing to board | `JMP $520F`, "WHAT?" | `JMP $934C`, S/H |
| `$50E5` surface key | `CMP #$A0` / `BNE $50F5` as before | `JMP $9375`: F7 (`$88`) teleports, then the same test |
| `$801E` combat dispatcher | `JMP $80FE` | `JMP $93F1`, X wins |
| `$61DA` Other's `JSR $46C3` "NO EFFECT!" | the print | if the word ends in A and has 8 letters: `JSR $756B` (the whirlpool's trip to Ambrosia), `JMP $6D38` |

**The map kept whole.** ULT3 assumes a frigate stands on water (or the whirlpool) and a
horse on grass: Board writes water (`$52D0`) or grass (`$52B2`) where it took the craft,
and X-it writes the craft's tile on any square below `$05`. The keys put a craft
anywhere, and Gold's versions changed the map (`docs/reversing-notes/u3-gold.md`, "The
ingame keys"). Three hooks and two edits of Gold's tail keep it whole, on or off; in the
original's play each does what the original did:

| Where | Was | Now |
|---|---|---|
| `$762B`, the whirlpool's trip down: `JSR $4708 / LDA #$00 / STA ($7E),Y` | the party's square cleared to water | `tr_pool`: cleared only if it holds the whirlpool (`$30`) |
| `$7777`, the way back: `LDA #$16 / STA $60` | the party on a frigate | `tr_back`: on a frigate if the square is water, else on foot (`$7E`) |
| `$6951`, X-it: `LDA $0E / ASL / STA ($7E),Y` | the craft parked on water or grass | `tr_xit`: a frigate parked on water, a horse on grass; else left behind, the square kept |
| `$9367`, `$9372` in Gold's tail, B's S and H: `JMP $52D0`, `JMP $52B2` | into Board, which writes water or grass | `JMP $52D4`, `JMP $52B6`: past the write (`TRAINER_EDITS`) |

By the whirlpool the square is always `$30`, so water on the way back; a frigate goes
only onto water and the whirlpool (`$71AD`), and a horse X-its on grass only (forest and
the rest are `$05` and up). `tools/vice/u3_map_check.py` plays all of it.

Gold's own Other hook overwrote the 18 bytes of "NO EFFECT!". The cart's is a `JSR` over
the print's `JSR`, and tail-calls `$46C3`, which finds the inline string as before.

**"AVOID?" (`u3avoid.s`).** ULT3 starts a fight the party did not choose in two places:
a monster stepping onto the party (the monsters' turn `$78AF`, X = the monster, then
`$78D5 JMP $5249`, Attack's own entry; surface, towns, Ambrosia), and a dungeon's random
encounter (`$8E01`, after the roll's `BMI`). With bit 6 of `pt_opts` set, `av_ask` prints
"AVOID?" through SUBS' `$46C3` and reads a key with `$4711`, as Gold's "EXIT?" does. Y
continues the monsters' turn at `$78B3` (the monster stays) or the dungeon turn at
`$8B2B`. No RAM patch carries the AVOID bit, so build.py adds it to the page's caps by
hand.

### Ultima III Gold (`gold.py`)

`gold.apply(name, data)` is called on every read-only unit. The Gold disk (key `u3gold`)
is unpacked on the host by `goldunpack.py`:

- the data files are `exomizer raw` streams, decoded by `ultima/sim/exodec.py` (a Python
  port of exomizer's raw decruncher);
- the boot file is an exomizer SFX in two stages, and stage 2's `$BE00` unpacks five
  in-memory streams (SUBS, ULT3, SHPS, TEXT, DEMO, DDAT). These run as Gold's own 6502
  code in py65. The C64's I/O banking has to be modelled: a write to `$D000-$DFFF`
  while `$01` has I/O in goes to the chips, not RAM. The SFX writes `$DBE7` (a colour
  cell) while it works, and stage 2 has packed data in the RAM under it. Written
  through, it corrupts ULT3 from `$6846` on.
- the five save files (PLRS, PRTY, ROST, SOSA, SOSM; stored raw, `$BAD9`'s table) are
  not read (`goldunpack.SAVES`): Gold's copies hold a played state, and nothing of them
  is used, so a played Gold disk builds the same cart;
- the result is the decrunched `boot`, `updt`, `shp3` files and `game`, the 64 KiB
  after `$BE00`. `tests/test_release.py` pins their hashes. The U3 build therefore needs
  py65.

Per unit:

| Unit | What gold.py does | Check |
|---|---|---|
| SHPS | `shps()`: 16 rows of 128 bytes -> `(r>=8)*$400 + t*16 + b*8 + (r&7)` | equals Gold's `$0800-$0FFF` |
| TEXT | `text()`: `r*$80 + c` -> `c*8 + r` | equals Gold's `$B400-` |
| SUBS | Gold's `$4100-` | differs from the original only in `SUBS_CHANGES`; the first `$200` (frames) equal `frames()` of the original |
| UPDT | Gold's file, then the original's bytes past its end | differs only in `UPDT_CHANGES` (`$CB01-$CBE7`, `$CC66-$CC93`) |
| ULT3 | Gold's `$5000-` | differs only in `ULT3_CHANGES` (dispatchers, the twelve "which player?" calls, the save system, the dungeon dispatcher, the tail `$922F-$93FF`) |
| BOOT | the original, with Gold's menu block | see below |
| SHP3 | Gold's file whole, padded with the original's tail | loads at `$9400`, fits the original's blocks, calls out only where the original does plus `$46DE`, `$46EA`, `$B809` (`SHP3_NEW_CALLS`) |

`_only()` raises "an undocumented change" for any byte that differs outside the listed
ranges. So nothing of Gold's that is not wanted (the trainers' BOOT patch lists, the
fastloader, the run-time keyboard remapping) can come along unnoticed. ULT3 carries the
trainers' tail code, but only the cart's hooks reach it.

**BOOT.** Gold's BOOT drops the module loads the cart's driver serves, so it cannot be
used. Gold's BOOT is the original shifted down by `$72` from Gold `$1060` on. The
original BOOT gets Gold's menu block (original `$1369-$14F1`, Gold `$12F7-$147F`: the
title map's blitter and animations in one routine, which the demo view draws with).
`boot()` walks Gold's code to `$1401`, moves every absolute operand into Gold's shifted
BOOT up by `$72` (asserting each one stays inside the block), asserts the tile colour
table in the block equals the original's `$1461-$14A0`, repoints the two callers
`$114B`/`$114E` (`JSR $144B`) to `$1369`, and changes the delete key test at `$1B2E` from
`$AB` (`+`) to `$94` (DEL).

### The launcher's RAM patches (`OPTION_PATCHES`)

Applied by `pt_apply` after every transfer, each only when its option is on and every
original byte is in place. Catalog entries load wherever the caller says, so
`patches.check_floating` proves each signature occurs in nothing else the game loads
(ULT3 at `$5000`, BOOT at `$1000`, every other unit at any page).

| Option | Address | Change |
|---|---|---|
| FOOD | ULT3 `$73D1` | `LDA #$10` -> `#$00` before `JSR $7463` (0.10 food per living member per turn; the routine's only caller) |
| PASS | ULT3 `$5096` | `BEQ $50E9` ("Pass") -> `BEQ +0` |
| PASS | ULT3 `$7FF4` | combat timeout: `JMP $8007` -> `JMP $7FFD` (the key read) |
| PASS | ULT3 `$8B66` | dungeon timeout: `JMP $8BF5` -> `JMP $8B6D` |
| TORCH | ULT3 `$5F86` | `SBC #$01` -> `SBC #$00` in Ignite's BCD decrement of record byte `$0F` |
| ITEMS | ULT3 `$5355` | `JMP $5368`: any class casts |
| ITEMS | ULT3 `$53E3` | `JMP $5418`: no MP check or cost |
| ITEMS | ULT3 `$6823` | `JMP $684C`: doors open without a key |
| ITEMS | ULT3 `$6404`, `$8D94` | `JMP $6419` / `JMP $8DA9`: peer without a gem |
| ITEMS | ULT3 `$51DB`, `$8122` | the N entry of the command letter tables -> `$6122`: no powder needed |
| JOURNEY | BOOT `$1278` | `JSR $4711` -> `JMP $12A9`: the menu's J path at once |
| JOURNEY | BOOT `$116C` | the demo view's `BEQ $1117` -> `NOP NOP`: on to the menu at once |

The ITEMS patches are Gold's trainers, read out of the patch lists in Gold's BOOT
(`$1E36-$1E6D`). The cart's ULT3 is Gold's, so they land exactly as in Gold.

U3's options byte, `pt_opts` (in the decoder segment), uses bit 2 as JOURNEY. So the X
option (`patches.POWERS`) is not an options bit for U3: the page pokes `tr_on` = `$80`
instead (`options["pokes"]`).

### Journey onward

`p["journey"]` pokes `JMP $8570` over EXOD's `$827E` (`LDY #5 / JSR $8545`, the delay before
the "Exodus" scramble-in), after the intro's display set-up, which BOOT needs.
`$8570` is the tail of the "any key" exit `$856E` (`PLA` x4 / `JMP $823F`): `PLA / PLA /
JMP $823F`, `R BOOT`, with the stack as `$856E` leaves it. build.py asserts both
sequences. The JOURNEY bit then patches BOOT's demo view and menu as BOOT loads.
BOOT is loaded again later in a session, so `u3_opt_once` clears the JOURNEY bit once
`$1278` holds the `JMP`.

## The launcher's side

- **The page's saved game**: `U3_PRTY` and `U3_PLRS` (the slots' flash addresses).
  PRTY +1 is the party size (0 = no party). PLRS has four 64-byte records: +0 the name
  (bit 7 set), +`$11` status, +`$1A` hit points, +`$1C` maximum, BCD.
- **Options**: caps from `OPTION_PATCHES` plus POWERS and AVOID. The X line reads
  "Gold's trainer keys".
- **Export/import** (`ultima/launcher/xfer.py`): one disk, asked for as "Scenario",
  recognised by the BAM name of disk B (Trilogy "PLAYER MASTER") or `alt` "ULTIMA
  III-SCEN." (the 1984 edition). Five raw slots (24 sectors in all) at their original
  track/sectors, written with `U1`/`B-P`/`U2`. The game itself never checks the disk's
  identity. The file form is `ULTIMA III SAVE`.

## Saves

Five writable entries, each with its own fixed slot of two erase blocks (8 KiB: SOSA is
16 blocks, and with a header page it does not fit 4 KiB), in this order from
`regions.save_base("u3")` = `$1EC000`:

| Slot | Entry | Blocks | Loads at |
|---|---|---|---|
| `$1EC000` | SOSA | 16 | `$1000` |
| `$1EE000` | SOSM | 1 | `$4F00` |
| `$1F0000` | ROST | 5 | `$9500` |
| `$1F2000` | PLRS | 1 | `$4000` |
| `$1F4000` | PRTY | 1 | `$CD00` |
| `$1F6000-$1F7FFF` | the journal (8 KiB) | | |

A slot is a 4-byte header page (`$A5 $5A`, block count, 0) and the data from the next page.
A load of a writable entry reads the header first. Without the magic, it returns and leaves
memory as it is. With it, it loads the data. A save (`u3_do_save`) goes through
`asm/journal.s`: `jr_begin` points `tc_addr` into the journal, `u3_sv_body` writes there
(erase the blocks the write covers, data, header last), `jr_commit` writes the journal
header ("JN" and the slot's address), `u3_sv_body` writes the slot in place, and `jr_end`
erases the journal's first block. The first stage finishes a committed journal at the
next power-on (`docs/developer/README.md`). A save request for a read-only entry is
ignored.

With Gold's save system, ULT3 writes only on Q (`$647F`: SOSA, SOSM, PLRS, PRTY). Town
visits, deaths and the whirlpool copy the state to `$E000-$F2FF` under the KERNAL. BOOT
writes ROST (`S ROST`).

### The pristine state

The build seeds every slot from disk B (header and data), so a fresh cart looks like a
fresh disk. For the release, the seeds are rules in `ultima/disks/manifest.py` `SEEDS`,
not the bytes of the supplied disk:

| Unit | Disk B blocks | Base |
|---|---|---|
| ROST | 327-331 | all zero |
| PLRS | 332 | all zero |
| PRTY | 333 | zero, but +4 = `$08`, +5 = `$FF` |
| SOSM | 312 | zero, but +`$FC` = `$02` |
| SOSA | 296-311 | **not generatable**: `manifest.WORLD` |

SOSA is the 64 x 64 map of Sosaria without monsters or transports. ULT3 loads it and
writes it back at every save, and nothing resets it: forming a party writes only ROST,
PLRS and PRTY, and the original's model is to copy the Player Master with `COPY`. No copy
of it exists elsewhere on either disk (its rows and 16-byte chunks were searched against
every other catalog unit and both whole images). But what play writes into it is recorded
on the same disk (`docs/reversing-notes/u3.md`, "The pristine state"): each monster's
under-tile in SOSM, a chest's in its low bits, a parked craft and the whirlpool on what
they can only stand on, the moon gate on its eight grass squares. `ultima/disks/world.py`
puts those back and the scanner offers the result as a source for SOSA's sectors, which
must still match the reference hashes. A map changed in a way the disk does not record (a
chest on mountains, `$24`; Gold's trainer keys' water and grass) is refused, and
`ultima/disks/scan.py` `HINTS` says so. A played disk also supplies its saved game, played
map included, through `ultima/disks/importsave.py` (the page's own import, run on the
host). The reference disk B is very likely pristine:
an empty roster and no monsters. That rests on one image: a second disk B dump that
matches is byte-identical to it, so it is not independent evidence.

## A step on the surface

ULT3's command loop prints the prompt (`$508D`), sets the idle count (`$22`), and loops:
`$5096` counts it down (a turn passes at zero), `$509A JSR $74AB`, `$509D JSR $46F3`
(SUBS `$4A68`: the animations and all of UPDT, `$CA00`), the poll at `$50A9`. A
direction key prints its name, checks the square and plays the footstep, and the party
moves (`$6D38`); then the turn's bookkeeping and the party's panel, the wind, the
monsters (`$780B`), the status line and the prompt (`$507E`). The view is drawn by the
idle pass before the next poll, so the moved view appears in the second half of a step,
and a key waiting in the queue is taken at that poll. (The path in the original:
[the reversing notes](../reversing-notes/u3.md#engine-notes), "A move on the surface".)

The cart changes four things. Two are a step's alone:

- **The footstep's later clicks come from the IRQ** (`u3step.s`, `STEP_FOOT`, `STEP_FX`,
  `STEP_TICK`). The footstep was effect `$F6` (a burst of eight toggles of `$D418`, about
  5k cycles), a fixed wait of 41k, `$F6` again, and on a horse another wait and a third.
  Now the first click plays where it did (`$710C`), and `$710F` is `JSR st_foot / LDA
  #$00 / RTS`: `st_foot` sets the clicks still to come (one, two on a horse; none with
  `$20` set, as `$4D3D` tests it). MUSI's IRQ handler calls `st_tick` instead of its
  player (`$9A7B`), which plays a click every `ST_GAP` (3) ticks of the KERNAL's CIA
  timer (16.4k cycles, 60 a second) with its own copy of `$4E7C` (no zero page: the
  original counts in `$15`), then goes on to the player at `$9A86`. Eight toggles leave
  `$B93E`, the speaker's state, as they found it, so a toggle the main program is in the
  middle of is not upset. Every effect (`$470E`, `st_fx`) and every load or save
  (`u3_transfer`) first waits for the clicks in flight (`st_flush`), as the original's
  blocking effects did; with interrupts masked the rest of the footstep is dropped.
- **The party's panel is drawn once a turn** (`STEP_PANEL`): `$72EC` drew it at its end
  (`$730D`), and each of its callers draws it again at once.

Two make the drawing faster everywhere, with the same result to the byte:

- **The message window scrolls a row at a time** (`u3scroll.s`, `SCROLL`, in place of
  SUBS' `$4770-$47FB`, checked to fit). A newline in the window (rows 17-23, columns
  24-39) copied rows 18-23 up one bitmap line at a time through `($7C),Y`, eight bytes
  apart, then cleared row 23 by printing 16 spaces, each through the glyph printer and the
  DOS module's colour hook (`$B895`): 31k cycles. A text row of the window is 128 bytes in
  a row, so the replacement copies the six rows and clears the seventh in one loop over
  the 128 columns, and the screen RAM in another: 9.7k. It leaves `$33/$34`, `$70`,
  `$79/$7A`, `$7C/$7D` and A, X, Y as the original does, and `$7E/$7F` alone; the
  bitmap's place (`$2000`) and screen RAM's (`$0400`) are constants where the original
  read SUBS' line tables and the DOS module's (nothing in any unit writes those tables or
  `$D018`, but the unreachable `COPY`).
- **UPDT's line of sight in one pass** (`u3view.s`, `VIEW_LOS`). UPDT walks from each of
  the 11 x 11 squares toward the party and hides it (`$48`) behind a blocker (`$06`,
  `$08`, `$46`, `$48` in the view buffer at `$9900`): 34-44k cycles on Sosaria, the more
  the more open the land. The walk from a square goes on exactly as its first step's own
  walk, so with the squares taken nearest the party first, a square is hidden when its
  first step is a blocker or hidden: one test a square, about 9k whatever the land.
  `$CA99` jumps to `vw_los`, which leaves the first square to the original's walk at
  `$CAA3`; that ends the pass as it always did, zero page and registers included.

## Pitfalls

- **Keys in VICE must be delivered at a poll.** U3 flushes the queue all over its intro
  and menus, so a key typed at a random moment is usually eaten. Break at the poll and
  put the code in `$0277` with `$C6` = 1 (`u3_drive.py` does this).
- **VICE screenshots**: use VICE's own `screenshot` (`vice_mon.Vice.shot`). A renderer
  that reads `$2000`/`$0400` directly is wrong for U3's intro and menu screens.
- **`$C0` must be re-armed.** U3 plays with the KERNAL IRQ live, which starts the tape
  motor (dropping the cart out of command mode) unless `$C0` is non-zero. tclib's
  `tc_leave` sets it on every exit, and the init stub sets it before the first `CLI`.
- **Force I/O with HIRAM+CHAREN (`ora #%00000110`), never LORAM.** LORAM banks BASIC ROM
  over `$A000-$BFFF`, and the driver lives at `$BC00`.
- **The driver must put the caller's I flag back** (`u3_transfer` does). Without it the
  game keeps running but its interrupt-timed sequences and KERNAL keyboard scan stop.
- **ACME's `^` is the bank-byte operator.** A mask written as `#<(F_WRITABLE ^ $ff)`
  assembles as `and #$00` and makes every load a no-op. Masks are spelled in binary.
- **Units load wherever the caller says.** `L SHP@` and `L CON@` select overlays by
  overwriting the name's last letter at run time, and the overlay window `$9400-$97FF` is
  shared. A RAM patch's signature has to be unique across all units at every page
  (`check_floating`).
- **`SHP0` and `SHP6` contain serial code at `$977F-$97BF`** that calls the DOS module's
  internals (`$BB20`, `$BB93`, `$BBD3`) and the KERNAL's serial routines. It is
  unreachable: the shop code before it ends at the `RTS` at `$977E`, and no absolute
  `JSR`/`JMP`/`JMP ()` into `$977F-$97FF` exists in any of the build's units. It is
  residue (as is OUTM's copy of DOS code), not a disk access the driver misses.
- **The copy protection is in BOOT, not the DOS module.** A scan of the load path alone
  finds none. Disk A's track 6 is unreadable on an original, and `$1DF4` hangs if it
  reads.
- **Gold's BOOT addresses are shifted.** Gold's BOOT is the original shifted down by
  `$72` from `$1060` on. Any BOOT address taken from Gold must be moved up by `$72`.
