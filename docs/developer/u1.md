# Ultima I on the cart: how it works

Code: `ultima/games/u1/` (`build.py`, `u1drv.s`), `asm/init_u1.s`, the standalone
launcher and self-test `asm/boot_u1.s`, the launcher's side in `asm/page.s` (`i_u1`).
Shared pieces it includes: `asm/tclib.s`, `asm/journal.s`, `asm/zxdecr.s` (with
`asm/zx02a.s`), `asm/patch.s`, `asm/tcinit.s`. What the original game does is in
`docs/reversing-notes/u1.md`; this file is about the cart.

Disk key: `u1`, the one Ultima I disk.

## Shape

All of Ultima I's disk I/O is one block of about 1.5 KiB that `HELLO` relocates from
`$8400-$89FB` to `$C000-$C5FB`, reached through three entry points from 13 call sites
(plus a fourth, "save next", from OU). The cart keeps that block and its addresses and
replaces only the dead parts of it, so no call site in the game changes:

| Address | Original | Cart |
|---|---|---|
| `$C480` | load file by index X, with the OU special case | `JMP u1_load_ou` |
| `$C483` | save file by save index X (scratch `S:xx`, KERNAL `SAVE`) | `JMP u1_save` |
| `$C486` | plain load by index X | `JMP u1_load` |
| `$C489` | save next: `LDX $C4F8`, +2, save | the same three instructions, then `JMP u1_save` |

Indices are the game's own: 0-15 the read-only files (`TC MA PL FI GE OU DN TW CA SP TM
ST IN MI LO PR`), 16-21 the writable ones (`DD RO P0 P1 P2 P3`). The save entries take
the save index (0-5), which is file index 16 + X, because the original's save tables are
the load tables from index 16 on. `$C4F8` is the game's current-character number (0-3),
so `$C489` saves that character's `P` file.

`HELLO` itself never runs on the cart. Its machine setup is in the init stub; its drive
prompt, the fastloader install and the command channel have no meaning without a drive.

## Memory

Everything the cart adds sits inside the original driver's image or in RAM the game
does not use before its first load:

| Range (C64) | Cart use |
|---|---|
| `$C000-$C47F` | tclib (`TCLIB_ORG = $C000`), the journal code, the unit table `u1_table`, `u1_load`, `u1_xfer`, `u1_unpack`, `u1_save` -- over the dead fastloader (drive code, M-W uploader, `$DD00` loops, the `$0330` hook) |
| `$C480-$C48D` | the entry table, pinned (`* = $c480`) |
| `$C48E-$C4EE` | `u1_load_ou`, `u1_load_slot`, `u1_done`, the options byte `pt_opts` and the applier's variables; ends at `u1_drv_end` |
| `$C4F8` | original: the current-character variable, kept |
| `$C4FD-$C52B` | original: the OU memcpy (`$E000` -> `$8C9E`, 24 pages, KERNAL banked out), kept and called |
| `$C52C-$C5E2` | the options' applier (`asm/patch.s`) and `u1_sv_tab`, over the original's KERNAL load routine and its name/address tables |
| `$C5E3-$C5FA` | original: the save start/end tables, kept (read by `build.py` and by nothing on the cart) |
| `$C600-$C6EC` | the zx02 decoder (`asm/zxdecr.s`), in the dead fastload receive buffer |
| `$C700-...` | the init stub, run once; MA (the settlements' glyph set, `$C700-$CAFF`) overwrites it later |
| `$CE01-...` | the launcher's X (`u1powers.s`), the outdoor idle wait (`u1idle.s`) and the options' table (`PT_TAB`, generated `u1_patches.s`), a segment of their own; `$CE00` is the NMI's `RTI` |
| `$02A7-$02FF` | the view's animation clock (`u1view.s`), a segment of its own: KERNAL RAM the KERNAL does not use |
| `$0334-$03FF` | the view's hooks and the text window's scroll (`u1view.s`), a segment of their own: the KERNAL's tape buffer and its unused bytes either side |
| `$1F87-$1FFD` | the view's helpers (`u1view.s`), after ST's end, loaded with ST |
| `$3F40-$3FEB`, `$5F40-$5FEB` | the view's record of each bitmap, in the bitmap's tail, which the VIC does not show |

Assertions in `u1drv.s` hold the pieces apart: `u1_pre_end <= $C480` (the code before
the entry table), `u1_drv_end <= $C4FD`, `u1_opt_end <= $C5E3`, `u1_zx_end <= $C700`,
`u1_ext_end <= $D000`.
`build.py` also checks that the zero-filled holes between the pieces of acme's output
are still empty. Room is tight: about two dozen bytes are left before the entry table.

**`$CB00-$CDFF` is not free.** TW and CA copy the current settlement's layout and people
there (three pages, TW `$8CF5`, CA `$8CF7`) as they start. A watchpoint run through the
intro and the outdoors sees nothing there, but the first town entered overwrites it.
`tests/test_u1_build.py` `TestU1Memory` checks the copy loops are where they are and that
no boot segment reaches into `$CB00-$CDFF`.

**`$0334-$03FF`**: only the tapecart's own loader uses the tape buffer, at power-on, before
the launcher. A VICE memmap from power-on through character creation, the outdoors, a town,
a dungeon and a castle sees `$033C-$03FB` written during that boot only and `$0334-$033B`,
`$03FC-$03FF` never, nor `$02A7-$02FF` at all. **`$1F87-$1FFD`**, between ST's end and the CHROUT stub at `$1FFE`:
untouched in the same session. **The bitmaps' tails** (`$3F40-$3FFF`, `$5F40-$5FFF`): in
that session (watchpoints on both) only ST's copy of one bitmap over the other (`$1723`,
32 pages) wrote there; TC, which TW and CA load to `$4000`, ends at `$5DED`. A linear
disassembly of every unit with code names an address in these ranges only in data
(`TestU1Memory` lists the eleven hits).

**`$C600-$C6FF`** was only ever used by the original fastloader; every absolute reference
to it in the game's units is misaligned data (a static scan of the units).

**`$CE01-$CFFF`** is named by no unit: a linear disassembly of every unit with code (all
but TC, MA and FI, which are data) finds no absolute operand there and no immediate
`$CE`/`$CF` that could build a pointer, but for one hit inside a table of DN's (`$AC49`
reads as `CMP $CE01,X`). The original never loaded anything there (`HELLO` copies
`$C000-$C7FF`), so the game cannot rely on its contents. `TestU1Memory` repeats the scan;
`tools/vice/u1_powers_check.py` finds the segment unchanged after the outdoors, a town, a
dungeon and a castle (VICE).

U1 runs with interrupts masked for its whole life (the stub masks both CIAs, as `HELLO`
did, and the NMI vector points at an `RTI` at `$CE00`). So no driver exit needs to put an
I flag back, and the game's own `$01 = $30` all-RAM windows in GE and OU are safe.

## Boot

The game's descriptor (`regions.desc_offset("u1")`, flash `$000100`) has entry `$C700`
and seven segments:

| Segment | C64 | Stored |
|---|---|---|
| the driver image, original with the overlay | `$C000`, 1532 bytes (`$C000-$C5FB`) | raw |
| LO, the title and loader | `$0800` | zx02 with its own length (`zx.sized`), flag bit 0 |
| the decoder | `$C600` | raw |
| the init stub | `$C700` | raw |
| the launcher's X and the options' table | `$CE01` | raw |
| the view's hooks and the scroll (`u1view.s`) | `$0334` | raw |
| the view's animation clock (`u1view.s`) | `$02A7` | raw |

The menu (`asm/menu.s`, at `$8700`, clear of all seven) loads them, applies the page's
poke list (the options byte), and jumps to `$C700`. `asm/init_u1.s` repeats what `HELLO`
did at `$8000-$809D` apart from the drive: `SEI`, `$00 = $2F`, `$01 = $36`, both CIAs
masked, CHROUT pointed at a `CLC/RTS` at `$1FFE`, NMI at an `RTI` at `$CE00`, border and
background black, colour RAM white, the vectors `HELLO` installs (`$0302`, `$028F`),
`$B000 = $02` (the drive-type byte, in the original's terms "no fastloader"), `HELLO`'s
screen registers. Then `JSR tc_init` and `JMP $0C00`, LO's entry.

`tc_init` is the stub's, not the driver's (`TC_INIT_ELSEWHERE`): it runs once, and its
bytes in the driver went to the journal. The stub assembles `asm/tcinit.s` against the
driver's symbols, which `build.py` writes out through `tcsyms.tcinit_include`
(`build/u1_tcinit.s`). The stub is too long for page 2 (whose KERNAL variables start at
`$0281`), which is why it lives at `$C700`: nothing loads there before LO asks for MA.

The driver is assembled with `TC_NO_CMDMODE` (the launcher entered command mode and it
stays entered).

## Storage in flash

Data region: `regions.data_base("u1")`, 60 KiB reserved (about 54 KiB used). Every
present read-only unit is stored page aligned, zx02-crunched unless that would not
shrink it (`zx.smaller`). `build.py` reads the names and load addresses out of the
driver's own tables (`$C597`, `$C5C3`) and refuses to build if the name table differs
from the expected list.

`u1_table` is 22 entries of 8 bytes, filled by `build.py`:

| Byte | |
|---|---|
| +0/+1 | flash address bits 8-23 (units are page aligned) |
| +2/+3 | length (the crunched length for a crunched unit) |
| +4/+5 | C64 address |
| +6 | flags: bit 0 crunched, bit 1 save slot |
| +7 | spare |

Two units have length 0 and so return C set, as the original does when a load fails:
**PL**, which has a table entry but no file on the disk, and **PR**, the copy protection
(its directory entry points at track 6, which is unformatted; see the reversing notes).
The build takes PR as the protection by name, not by its read failing: a copy whose
track 6 was formatted (a dump without an error map can be one) holds a 5 KiB file there.
The game ignores the result of the PR load at MI `$8CA9` and keeps the table already at
`$12C0` in ST. That is the behaviour of an original disk, so nothing is patched.

**OU is two addresses.** LO loads it once with `$C486` into its cache at `$E000` (RAM
under the KERNAL); whenever the game asks `$C480` for index 5, the original memcpy at
`$C4FD` copies it down to the overlay slot at `$8C9E`. `u1_load_ou` sends index 5 there
and everything else to `u1_load`.

### Loads

`u1_load`: an index past 21 or a zero length returns C set; a save slot goes to
`u1_load_slot`; a crunched unit to `u1_unpack` (`zxd_unpack`, streaming from flash), a
raw one to `u1_xfer` (`tc_read`). Both set HIRAM and CHAREN in `$01` around the
transfer (`ORA #%00000110`, never LORAM) and restore it; tclib itself runs the transfer in
all-RAM banking with interrupts off, so a load can land under ROM.

`U1_FAST = 0`, `TC_NO_FAST`, `TC_GUARD`: every load, raw or crunched, is a 2-bit read
with the screen on, which waits out badlines before each byte, and falls back to 1 bit
while any sprite is enabled (`tc_pick`). See [transfer.md](transfer.md).

**No `TC_NMI_HOLD`.** Its code does not fit before the entry table and no hole elsewhere
takes it, so a RESTORE during a transfer goes through whatever RAM holds at `$FFFA`.
Between transfers it hits the game's own `RTI` at `$CE00`.

Both load paths end in `u1_done`, which applies the options (below). Save-slot loads and
the OU memcpy do not go through it.

## The launcher's options (`OPTION_PATCHES`)

RAM patches with a signature (`ultima/launcher/patches.py`, `asm/patch.s`). The page
pokes `pt_opts`; `u1_done` runs `pt_apply` after every unit load, with `$01` set to all
RAM plus I/O (bits 0-2 = `%101`, the motor bit kept) so that it sees OU's cache at
`$E000` under the KERNAL, and puts `$01` and the I flag back. A patch is applied only
where every original byte is in place; `patches.check` proves each signature is unique in
everything the game loads over that address (`OPTION_UNITS`).

| Option | Unit | Address | Original -> patched | Effect |
|---|---|---|---|---|
| FOOD (F) | MI (resident at `$7400`) | `$8657` | `AD 5A 82` (`LDA $825A`) -> `4C 6A 86` (`JMP $866A`) | MI's food routine (`$863A`) takes a whole unit once the fraction borrows; the jump goes to its no-borrow exit, which keeps the time counter. Every move's cost goes through it; the gremlins' halving does not. |
| PASS (P) | DN | `$912C` | `D0 03 CA D0 F8` -> `D0 03 EA F0 F8` | the idle loop: 128 keyboard polls (`LDX #$80 / JSR poll / BNE key / DEX / BNE`), then a turn passes. `DEX / BNE` becomes `NOP / BEQ`, so it polls until a key. Outdoors the wait is `u1idle.s`'s (below), which reads the option itself. |
| PASS | TW | `$8D4A` | the same | |
| PASS | CA | `$8D53` | the same | |
| STEAL (S) | TW | `$A457` | `A9 00 85 4C A2 0F` -> `60 00 85 4C A2 0F` | Iolo the bard, when the party stands in his way, takes one of every weapon but the readied one (`DEC $81F8,X`, X = 15..1); an `RTS` where that starts. |
| STEAL | CA | `$9D88` | the same | the jester's, the same code |
| STEAL | DN | `$9E81` | `4C AF 9E 4C FC 9E` -> `4C F6 9D 4C FC 9E` | a thief's attack that lands goes through the special attacks' jumps (`$9DDA`: type `$17`) to `$9EAF`, which steals one weapon; the jump goes to the ordinary hit (`$9DF6`), where the thief goes when there is nothing to take. |

The OU patch goes into the cache at `$E000` once, when LO loads OU, and travels with
every copy down to `$8C9E`. The options byte's capabilities are FOOD, PASS and STEAL (bit
7, which is U4's BALLOON and U2's CLAMP: the page's line for it has U1's own words and
key); the page offers F, P and S, and X (below). STEAL leaves the gremlins, which halve
the food, and the gelatinous cube, which destroys the worn armour (DN `$9F27`, `$9EFC`).
**No Journey Onward**: U1 has four characters and asks which to play.

### X: F1 tells where, F7 teleports, B brings a transport

`u1powers.s`, in the segment at `$CE01`: hooks always in, built into OU (`build.py`
`POWER_HOOKS`, the original three bytes checked), each testing `pw_on`, which the page's
launch pokes with `$80`; without it every hook does what the original did. Outdoors only:
both hooks are in OU.

- `$8D31` `JSR $85FD` (the command loop: MI turns the key into a command, or says "Huh?"
  and sets C) -> `JSR pw_key`. With `pw_on`, F7 (`$88`, which the game's key routine
  hands over as `$08`) prints `Teleport land-`, ` X-`, ` Y-`, reads a digit 0-3 and two
  of two digits (at most 63; a land is 64 x 64), and sets `$81E4`, `$20`, `$21`; then
  `$983D`, what a step off a land's edge runs (`$9A10` takes the monsters off, `$9840`
  decodes the land's map at `$6400` and puts the vehicles on it). Anything else prints
  "Huh?" on the next line and buzzes (`$8772`). Both return C set, so the loop goes on
  to the monsters' turn as after an unknown key. The square is not checked.
- In the same hook, F1 (`$85`, handed over as `$05`) prints `Position land-0 X-30 Y-31`
  through MI's decimal printer (`$8582`, its fill byte `$85BE` set to none and put back:
  some callers rely on it), a minus first for the sea west and north of the map (the
  coordinates run -10 to 73), and goes to the loop's top (`$8CFB`, which resets the
  stack): no turn passes. The game has no way of its own to show the position. The
  page's line for X has U1's own words, "Locate, teleport, vehicle" (`o_x1`), which U2's
  page shares.
- `$9082` `JSR $83F6` (Board with nothing to board, before "nothing to Board!") ->
  `JSR pw_board`. With the option it drops the return address, prints
  `(H)orse,(C)art,(R)aft,` and `(F)rigate,(A)ircar-` on lines of their own (the message
  window is 29 columns), and for H, C, R, F or A does what Board does after taking a
  vehicle off the map: `$81F1` = 1-5, `$9E0B` (the party's tile), `$166A` (the view), and
  on to Board's end (`$90B2`, which pulls the vehicle: "Mount " for the horse and the
  cart, the vehicle's name). The others get "Board " first, on a new line. Any other key
  buzzes. No shuttle and no time machine: Board launches those at once.
- Keys come from ST's `$1676` (waits; bit 7 clear), text from MI's `$848E` (the inline
  string; `$7E` a new line at column 1) and `$83D7` (A's glyph; U1's font is ASCII).
- The vehicle counts (`$8213`,x, Ztats) are counted again from the map's vehicles and the
  one the party is in whenever a land is entered (`$9916`), so a summoned vehicle counts
  as any other. X-it puts it on the map (`$9CA6`), on water, grass or forest.

## Saves

The save region is `regions.save_region("u1")`: flash `$1F8000-$1FEFFF`, at the top of
flash, never moved by a new build (`tests/test_regions.py`).

| Flash | Content |
|---|---|
| `$1F8000` | DD (1 byte, from `$B000`) |
| `$1F9000` | RO (64 bytes, `$B000-$B03F`) |
| `$1FA000-$1FDFFF` | P0-P3 (458 bytes each, `$81E2-$83AB`) |
| `$1FE000` | the journal |
| `$1FF000` | not U1's: the launcher's settings page (`regions.SETTINGS`) |

One slot per 4 KiB erase block, so a save never disturbs another. A slot is a header
page, `$A5 $5A` and the length word, then the data from `+$100`. The lengths come from
the original's own save tables at `$C5E3`/`$C5EF`.

**Writing** (`u1_save`, by save index): through the journal (`asm/journal.s`).
`jr_begin` points `tc_addr` at the journal's second page; `u1_sv_tab` points the table
entry there and `u1_sv_body` writes the slot as usual -- erase the block, the data at
`+$100`, the header last; `jr_commit` writes the journal header ("JN" and the slot's
address bits 8-23) and points `tc_addr` back at the slot; the body runs again into the
slot itself; `jr_end` erases the journal. A power cut before the journal header leaves
the old save; after it, the first stage (`asm/boot.s`) copies the journal into the slot
at the next power-on. See [saves.md](saves.md).

**Reading** (`u1_load_slot`): the header must be `$A5 $5A`, else C set ("no save", which
is what an erased slot reads as). The length is taken from the header, not the table.

**What play writes**: DD (on the original, `HELLO` `$8118` on every boot; nothing on the
cart writes it), RO (GE `$8EE0`, `$9349`) and P0-P3 (GE `$9353`, OU's save-next call).

### The pristine state

The image covers the whole save region, so the flash tool erases it rather than leaving
stale bytes that could pass the `$A5 $5A` check. `build.py` seeds the slots the disk
has content for -- DD and RO -- and leaves P0-P3 erased. All of it is generatable, so
nothing pristine is needed from the supplied disk image: the manifest's seed rule for RO is 64
zero bytes (four empty roster slots; `+0 = $FF` marks one in use). The reference disk's
RO carries a `$2000` load address where the game writes `$B000`; the cart ignores the
address, and the base keeps the reference's so the build is unchanged.

### The launcher's side

`build.py` hands the page `U1_RO` and `U1_P0` (the others follow at 4 KiB steps). `i_u1`
in `asm/page.s` reads the roster and, for each used seat, the character's slot: a record
starting `$CA $01` shows the name, hit points (`+$59`) and food (`+$78`), 16-bit binary;
otherwise "(no data)". Reset erases the region but the settings page and writes back the
fresh image's pages (DD and RO).

Export and import (`ultima/launcher/xfer.py`, `asm/page_xfer.s`, `asm/page_file.s`): one
disk, recognised by its BAM, five files -- `RO` (64 bytes, `$B000`) and `P0`-`P3`
(458 bytes, `$81E2`, optional) -- written as the game writes them (scratch, then save,
with the game's load address). An empty character slot on the cart is skipped; a
character missing on the disk is erased on the cart by an import. The file format
(`ULTIMA I SAVE`) is the same five slots.

## A step outdoors

OU's command loop waits for a key in `JSR $8DD0` (`$8D1A`): up to 128 polls of ST's
`$1E50`, and every poll draws the view (`$1C8A`) into the hidden bitmap and flips it
(`$1700`). So a step shows only when the poll after it has drawn the view. Measured in
VICE (`tools/vice/u1_step_bench.py`, on grass near the start, the walking sound on; the
original's figures from a `U1_NO_FAST` build):

| | Original | Cart |
|---|---|---|
| key to the moved view | ~158k cycles, 0.16 s | ~97k cycles, 0.098 s (78-116k) |
| ... of which back at the key wait | ~38k | ~34k |
| a poll, nothing moving, grassland | ~120k | ~40k |
| a poll beside water or a castle | ~120k | ~60-80k |
| an idle turn (P on), nothing pressed | 15.32 s | 15.00 s (`u1idle.s`) |

Where a step's CPU cycles go on the cart (the profiler; the rest of the stopwatch's is
presumably the VIC's badlines), the original's in brackets:

| Where | Cycles | |
|---|---|---|
| the view, `$1C8A` | 59k (112k) | 40k the cells drawn or passed over (98.5k: all 171 drawn); 15k the flip, which waits for the raster (7k, 3k: a draw now ends anywhere in the frame) and plays out the queued walking sound (`$171A` -> `$1B72`, 7.5k); 2k the eight key reads, one a tile row |
| the prompt's new line, `$1649` | 15k (20k) | the four-line text window scrolled, on both bitmaps |
| the status, `$86C6` | 11k | hits, food, experience, coin printed again |
| the command, `pw_key` -> MI `$85FD` | 2.6k | the key looked up, its name printed |
| the monsters' turn, `$9A2F` | 1.3k | |
| the move, `$96E2`.. | 0.4k | |

A direction held down repeats by CIA 1's time of day (ST `$1F46`): five tenths after the
first press, then two (`$1637`) after the last repeat, looked for at every key read. The
KERNAL leaves the clock's input at 60 Hz, so on a PAL machine its tenths are 0.12 s: in
VICE the repeats come 0.6 s and then 0.24 s apart. A step takes less than that, so the
repeat sets the pace, the same on the cart as in the original: 0.249 s a step on average
in VICE. The original's repeats come at 0.24-0.30 s (one due between two key reads
waits for the next, up to a poll later), the steps mostly 0.18-0.20 s apart with every
fourth or so at 0.33 s; on the cart the repeats come at 0.240 s and the steps 0.19-0.26 s
apart.

Taps are not held to the repeat. ST puts `$FF` into the KERNAL's last-key byte `$C5` at
every key read (`$1F7A`), so `GETIN` returns a key held down at every read and 0 once it
is up, which clears the last key (`$1F83`) and the repeat (`$1F84`, `$1EF9`); the next
press is a new key, taken at once. Taken keys wait in the game's queue (`$4E-$55`, eight
deep, more dropped, `$1E1F`), and a poll hands one over only after drawing the view. So
taps faster than a step queue up and the party walks on after the last: in VICE (the
original), 15 taps every 0.12 s (0.05 s down) and every 0.08 s (0.03 s down) were all
taken, 0.16-0.185 s apart, the last ~0.7 s and ~1.3 s after the last tap. A release must
last until a key read: there are eight a view drawn, one a tile row.

## The view and the text window (`u1view.s`)

The view is drawn only where it changed, and the text window's usual scroll is one pass.
`build.py` lays it in (`VIEW_*`), after checking the bytes it replaces (ST's renderer by
a pin, the rest quoted); `U1_NO_FAST=1` leaves it out, to compare in VICE (the idle
wait below stays).

- **The renderer** (ST `$1C8A`, in place up to its animation at `$1DB5`) is ST's own --
  the rows read from the map, a key read a row, the party's tile in the middle, the
  cells right to left, the same zero page left but for `$5E` -- with a record per bitmap
  of the tile drawn in each cell: `$3F40` for the bitmap at `$2000` (`$5C` = 0), `$5F40`
  for the one at `$4000`, 19 bytes a row, then a byte that is `$80` while the record
  holds (`$3FEB`, `$5FEB`). A cell whose tile the record has is passed over. ST animates
  tiles 0, 4, 6 and 12 by changing their bytes in place (`$1DB5`), so those are recorded
  as `$FF`, which matches nothing. A record that does not hold is filled with `$FF`
  first. Its helpers (the set-up with ST's own start, the next row, the `$FF` test) are
  after ST's end, `$1F87-$1FFD`, so ST's unit is longer by them. It ends in its own `JSR
  $1700 / JMP $1E08` (the flip, then ST's key read and RTS, as ST's ends).
- **The animation goes by the clock.** ST steps it (`$1DB5`: the water, the castle's and
  the town's flags, tile 12) after every draw, and picks every monster's frame anew at
  every draw (`$178E` on into `$B700`); a draw was six frames, so both went at six frames
  a step. Here CIA 2's timer A runs out once a frame on a PAL machine (`$02A6` = 1), every
  1/50 s on NTSC, and timer B counts it down from `$FFFF` (the init stub sets both up;
  the game leaves CIA 2's timers alone and its interrupts are masked). At a draw's start
  (`anim`, `$02A7-$02FF`) the step is taken -- `JSR $1DB5`, which ends in ST's key read
  and RTS -- when six ticks have passed since the last, once, from now on if twelve or
  more have (the view was away: no burst of steps); otherwise `$178E` is put back to its
  value at the last step's draw, so the monsters keep their frames. In VICE the step
  comes every 6.00 frames standing still, as in the original.
- **The record is dropped** (its byte shifted right: never `$80` after, every register
  kept) by whatever else draws in a bitmap, through hooks at `$0334-$03FF`: ST's jump
  table entries for the screen's set-up (`$163A`), the view's clear (`$1661`), a flip
  that is not the renderer's (`$1664`), points and lines (`$168E`, `$1691`, `$1694`);
  text in rows 0-18 (`$1A78`'s first instructions, so a character from anywhere; the
  scroll `$1649`, the row clears `$164C`/`$164F`, the window's clear `$1652`, each when the
  window's top `$30` or the cursor's row `$33` is there); and OU's start (`$8C9E`'s `LDA
  #$30 / STA $01` become `JSR h_ou / NOP`), since another overlay (SP, TM) may have drawn
  without ST. ST's copy of one bitmap over the other (`$1646` -> `$1723`, all 32 pages)
  carries the record and its byte along; a bitmap cleared whole clears the byte.
- **The scroll** (`$1649` -> `h_scroll`): the usual window, columns 0-29 of rows 20-23
  with both bitmaps in use (`$5D` = `$60`), in one pass of 240 columns -- rows 21-23 up in
  both bitmaps, read from the one at `$2000` as ST does, row 23 filled with `$1F` -- then
  what ST's leaves (the colour bytes it sets, `$32`, `$33`, `$43`, `$5F`, X, Y) and its
  closing key read. Any other window goes to ST's own (`$1910`). ~15k cycles for ~20k.

What stays as it was: the status lines are printed again every turn (11k), and the
walking sound is played out before the flip returns.

## The idle turn outdoors (`u1idle.s`)

OU's key wait let a turn pass after 128 polls without a key. A poll is a draw and a flip
on the frame: six frames in the original, so a turn every 15.32 s idle (PAL, VICE),
while with the view drawn only where it changed it is two frames on grass and three or
four by water, a turn every 5-10 s. So the wait is timed instead: OU `$8DD0` (`LDX #$80 /
JSR $167C`) is a `JMP` to `idle` in the segment at `$CE01` (`IDLE_HOOK`), which sets CIA
2's time of day to 0.0 s, polls as before, and lets the turn pass at 15 s (15.00 s in
VICE); with the page's P it polls until a key, as OU's PASS patch did. CIA 2's time of day
and timers (the animation's, above) are named by no unit and by no code of U1's driver
(U1 has no `TC_NMI_HOLD`, which would take timer A over during a load); the init stub
sets the time of day's 50 Hz input on a PAL machine (`$02A6` = 1), so the 15 s are
seconds on both. DN's, TW's and CA's idle waits
draw nothing and keep their loops (and the option's patches).

## Pitfalls

- **Slice the assembler output, do not copy it.** acme emits one blob from `$C000` with
  the holes zero-filled. `build.py` takes `$C000` up to `u1_drv_end`, the options
  segment, and the decoder separately. Copying the whole 1532 bytes over the original
  image zero-fills the save tables at `$C5E3`/`$C5EF`, and every save then writes zero
  bytes to offset zero.
- **The entry table is pinned.** acme only warns when `* = $c480` lands inside code
  already emitted, and the build carries on. The `u1_pre_end` assertion is what stops
  code from running into the table; keep it in front of any pinned `* =`.
- **`$C4F8` is a live game variable**, between the driver's code and the OU memcpy.
  `u1_drv_end` must stay below it (the build checks the original byte is unchanged).
- **The options sit over the original name and load-address tables.** `build.py` reads
  those tables from the disk's `HELLO` before overlaying them; nothing on the cart reads
  them at run time.
- **Memory that looks free.** `$C700-$CAFF` (MA) and `$CB00-$CDFF` (the settlement) are
  written only when a town or castle is entered. Before calling any RAM free, scan every
  unit statically and play every mode: outdoors, a town, a castle, a dungeon, space.
- **PRG headers lie.** Every file is loaded with secondary address 0, so its header is
  discarded; `build.py` uses `payload()` (header stripped) and the driver's address table.
