# Ultima II on the cart: how it works

Code: `ultima/games/u2/` (`build.py`, `u2drv.s`, `u2log.s`, `u2powers.s`,
`u2clamp.s`), `asm/init_u2.s`, the launcher's side in `asm/page.s` (`i_u2`) and
`asm/page_u2l.s`, the host model of the save log in `ultima/launcher/u2log.py`. What the
original game does is in `docs/reversing-notes/u2.md`; this file is about the cart.

Disk keys: `u2a` (side A, "Program + Galactic", the Origin / Ultima Trilogy edition) and
`u2b` (side B, "Player Master", either edition). In `build.py` they are disk numbers 1
(Galactic) and 2 (Player).

## Shape

Ultima II reaches the drive only through four entries of the jump table at the start of
`SUBS` (`$4000`); `ULTIMA` (`$5000-$8A8F`) has no KERNAL references at all. Everything is
addressed **by name**, so the driver is a name -> flash page table. Those four vectors
are the whole seam:

| Vector | Original target | Cart | What |
|---|---|---|---|
| `$408D` | `$4B1C` | `u2_load` | LOAD "name" -> address (inline parameters) |
| `$4090` | `$4B55` | `u2_save` | SAVE "name" <- start..end |
| `$40AB` | `$4E6A` | `u2_block` | raw `U1`/`U2` block read/write |
| `$40AE` | `$4F2D` | `u2_cmdchan` | OPEN 15,8,15 -- an `RTS` |

`build.py` checks that each vector is the original `JMP` before repointing it.
**Nothing else in `SUBS` changes but two jumps for the footstep** (`SUBS_HOOKS`,
[A step on the surface](#a-step-on-the-surface)) **and the launcher's X in the dead block
I/O** (`u2powers.s`, [below](#hooks-that-are-always-in-tested-at-run-time);
`test_nothing_else_in_subs_changed`). The disk code
in `SUBS` is not one free block: the ten sound effects (`$4CBC-$4E68`) and the RNG
(`$4F79`) sit between the dead load/save code (`$4B1C-$4CBB`) and the dead block I/O
(`$4E6A-$4F78`). Leaving the load/save code intact lets the driver call its helpers
instead of reimplementing the inline-parameter convention:

| `SUBS` | Used for |
|---|---|
| `$4BF0` | the caller's return address -> `$2B/$2C`, the inline block |
| `$4C05` | length of the inline name -> `$0E` |
| `$4C1C` | step the return address past the parameters (A = bytes after the name) and return |
| `$4C32` | restore the raster split from its table at `$47C6-$47CF` |
| `$4C47` | print "ONE MOMENT PLEASE!" |

## Memory

| Range | Cart use |
|---|---|
| `$0200-$0285` | init stub (`asm/init_u2.s`), run once; the test checks it ends below `$0286` |
| `$4000-$4FFF` | `SUBS`, a boot segment, four vectors repointed, two jumps for the footstep; the launcher's X (`u2powers.s`) at `$4E6A-$4F77`, in the block I/O the vectors left dead, 1 byte left before the RNG |
| `$A000-$B0FF` | the game's map cache (untouched) |
| `$B100-$BFFF` | the driver: entry points, the name table, tclib, the zx02 decoder, the options code (`patch.s`, `pw_on`, `u2clamp.s`), the footstep (`u2step.s`); `u2drv.s` errors if it passes `$C000`, and 223 bytes are left |
| `$C000-$CFFF` | `INTRO`, a boot segment (patched) |
| `$D000-$DEFF` | the save log's code (`u2log.s`), in the RAM under I/O |
| `$DF00-$DFFF` | the log's page buffer for compaction (`LG_BUF`) |

Why these places:

- **`$B100-$BFFF` is free because the map cache is exactly `$A000-$B0FF`**: `$6809`
  and `$685F` in `ULTIMA` copy `$1000-$1FFF` and `$8F00-$8FFF` to and from it and stop
  at `$B0FF`. It is RAM only with `$01 = $36`. The original boots with `$37` (BASIC ROM
  over `$A000-$BFFF`) and reaches `$36` only at its first map-cache copy, so **the init
  stub sets `$01 = $36` itself**. The game writes `$01` four times, always `$36`, and
  never puts `$37` back.
- **`$2000-$2FFF` is not free**: `$7BA5` fills `$2000-$21FF` with `$FF` as a new game
  starts. What owns `$2200-$2FFF` is not traced; nothing is put there.
- **The RAM under I/O is the log's home** because the game only ever sets `$01 = $36` and
  nothing it loads goes above `$CFFD` (`INTRO`'s end), so the game can never reach
  `$D000-$DFFF` RAM. The log's code is too big for what is left in `$B100-$BFFF`.
  `lg_run` in the driver banks it in (`$01 = $34`; interrupts are already off inside the
  driver) around each call and restores `$01`. No code may run from there with I/O
  banked in.
- tclib and the decoder (`asm/zxdecr.s` around `asm/zx02a.s`) use **no zero page**: the
  game's own `$2B/$2C`, `$0E`, `$0A/$0B`, `$3D/$3E` and `$FB-$FF` are live. The driver's
  name-table cursor (`u2_e`) is a self-modified absolute operand for the same reason.

## Boot

The descriptor (`regions.desc_offset("u2")`, `$000300`) lists five raw segments: `SUBS`
at `$4000`, `INTRO` at `$C000`, the driver at `$B100`, the log at `$D000`, the init stub
at `$0200`; the entry is the init stub. The menu loads them and applies the page's poke
list before jumping to `$0200`.

`init_u2.s` replaces `ULT` (the boot PRG at `$02DA`) and `INTRO`'s first 37 bytes (its
KERNAL load of `SUBS`):

- `$00 = $2F`, `$01 = $36` (BASIC out for the driver, KERNAL and I/O in, motor bit set);
- `$D011 = 0` (as `ULT`), `SETMSG(0)` and a clear screen (as `INTRO`), the keyboard
  queue emptied;
- `$0291 = $80`: MODE bit 7 locks Shift+C=. Without it the KERNAL flips `$D018` until the
  raster split puts it back, a visible glitch. Nothing in U2 calls CINT or writes `$0291`
  (every file scanned), so it holds all game long (`test_init_stub_locks_shift_commodore`);
- `$C0 = 1` before the first `CLI` (the KERNAL IRQ starts the tape motor otherwise);
- `JSR $B100` (`u2_boot`: `tc_init`, then the log's `lg_init`);
- `CLI`, `JMP $C025`, where `INTRO`'s own work starts.

`INTRO` then loads `SHAPES`, `DNGNDRAW`, `STARS` and `ULTIMA` by name through the driver.
Its `JMP $5000` at `$CED3`, the hand-over to `ULTIMA`, goes to the driver's `u2_go`,
which runs `pt_apply` (the launcher's RAM patches, once `ULTIMA` is in memory) and
jumps to `$5000`. `ULTIMA` is loaded only once, so this is the one place options are
applied.

## Storage in flash

Data region: `regions.data_base("u2")` (`$028000`), 68 KiB reserved.

- **Files are stored individually and deduplicated**: every directory entry of both
  disks gets a table entry (121), pointing at 70 distinct blobs (the `MONX`/`MOBX`
  templates are copies of each other, several `MON` files are identical, `SHAPES` and
  `MONSTERS` are on both disks). The PRG header is dropped: the loader uses `SETLFS` with
  secondary address 0, so the header's address never mattered.
- **zx02 per unit**, kept raw where it would not shrink (`zx.smaller`).
- **Writable files are seeded raw**: `MOB xx` and `MON xx` on the Player disk, each at
  most a page, so the log can copy and write whole pages. The player record (raw T35/S16,
  no directory entry) is one more raw page, `u2_recpage`.

The name table (`u2_table`, 124 entries of capacity; `build.py` refuses more) has
13-byte entries:

| Bytes | |
|---|---|
| 0-7 | the name, NUL-padded |
| 8-9 | flash page (address bits 8-23) |
| 10-11 | stored length (the crunched length for a crunched unit: the stream ends itself, so the decrunched size is never recorded) |
| 12 | disk number in bits 0-1 (1 Galactic, 2 Player); bit 6 `F_COMP` crunched; bit 7 `F_WRITE` writable |

### Which disk

Twelve names exist on both disks with different contents (`MAP 10`, `MAP 15`, `MAP 20`,
`MAP 30`, `MAP 32`, `MAP 40`, `MAP 41`, `MAP 45`, `MON 32`, `MON 41`, `TLK 32`,
`TLK 41`). The selector is `$8E37`, the planet number in the player record: 0 means
Earth and the Player disk, anything else a planet and the Galactic disk (the game's own
wrong-disk check at `$7B42` encodes exactly that). `u2_find` runs the scan twice: first
demanding the disk `$8E37` asks for, then accepting either -- what a player with both
disks in two drives would get. Both entries of each colliding name must stay in the table
(`test_colliding_names_keep_one_entry_per_disk`).

### Loads

`u2_load` prints "ONE MOMENT PLEASE!" (before masking interrupts: it wants the raster
split), saves the caller's flags and masks interrupts, finds the name, takes the
destination from the two bytes after the name's NUL, and either streams a crunched unit
through `zxd_unpack` or reads a raw one with `tc_read`. Then `$4C32` puts the raster split
back, the caller's I flag is restored (`u2_leave`), and `$4C1C` returns past the
parameters. An unknown name leaves memory alone.

The driver is assembled with `TC_GUARD` and `TC_NO_FAST` (`U2_FAST = 0`): every load,
raw or crunched, uses the 2-bit read with the screen on, waiting out badlines before each
byte, and falls back to 1 bit while a sprite is enabled. `TC_NMI_HOLD` holds the NMI line
during transfers, so a RESTORE is lost rather than jumping through RAM at `$FFFA` (U2 does
not touch CIA 2's timers or interrupt mask). `TC_NO_CMDMODE`: the menu entered command
mode and it persists.

## Patches

All are checked before they are applied: the expected original bytes must be in place,
or the build stops. `test_the_patches_are_applied_and_nothing_else` compares every unit
in flash with the disk's plus exactly these changes.

### Build-time patches (`build.py` `PATCHES`)

| File | At | Original | Cart | Why |
|---|---|---|---|---|
| `INTRO` | `$CED6` | `LDA #$12 / STA $FB / STA $FC` | `LDA #$32 / RTS` | copy protection: the routine reads T18/S18 and `$C034` wants ASCII `'2'` (a read error); return it directly |
| `INTRO` | `$C9C0` | `LDX #$04 / LDY #$0C / JSR $4045` | `JMP $C9F2` | "INSERT PLAYER DISK" prompt |
| `INTRO` | `$CE89` | `LDY #$0D / LDX #$03 / JSR $4045` | `JMP $CEBC` | "INSERT PROGRAM DISK" prompt after character creation |
| `INTRO` | `$CAB9` | `JMP $C9B4` | `JMP $C093` | "THIS DISK HAS A PLAYER NAMED ...": stopping goes to the title sequence (after the `STARS` load) |
| `ULTIMA` | `$7B42` | `JSR $40AB / LDA $10FF` | `JMP $7BA5` | "WRONG DISK!!" check: take the success path |
| `ULTIMA` | `$501A` | `JSR $4006 / CMP #$CE` | `JMP $5048` | `ULTIMA`'s entry asks for the Player disk: skip the message and wait, keep the screen setup at `$5000-$5019` |
| `ULTIMA` | `$6B04` | the footstep's loop (`LDX #$FF / LDY #$20` ..), `JSR $4021` | `JMP $6B11` | on foot: the pause between the clicks and the second click, which the IRQ plays ([A step on the surface](#a-step-on-the-surface)) |
| `ULTIMA` | `$6AF4` | the same loop, `JMP $6B94` | `JMP $6B94` | on a horse: the pause after its first click |

Plus `INTRO` `$CED3`: `JMP $5000` -> `JMP u2_go` (checked to be `JMP $5000` first).

Two of these depend on each other:

- **`$C9C0` is also the retry target** of the "is this a player disk" loop at `$C9F8`.
  With the prompt gone the loop would spin forever on a record whose `$FF` byte is not 0,
  so `build.py` refuses a seed record that is not marked as a player disk
  (`test_the_player_record_is_seeded_as_an_empty_player_disk`).
- **`$CAB9`**: on the original, declining the found player went back to the
  insert-player-disk prompt so another disk could go in. With that prompt patched out it
  would find the same player and ask again forever; the title sequence at `$C093` offers
  play or create instead.

The copy-protection read never reaches the driver. `build.py` checks that side A's error
map flags exactly T18/S18 (error 5) when the image has an error map; release images
usually have none.

### The launcher's RAM patches (`OPTION_PATCHES`)

Applied by `pt_apply` (`asm/patch.s`) at `u2_go`, each only when its option bit is set and
every original byte is in place; `patches.check` proves each signature appears nowhere
else in `ULTIMA`.

| Option | At (`ULTIMA`) | Change | What |
|---|---|---|---|
| FOOD | `$5165` | `SBC #$0A` -> `#$00` | food for a pass |
| FOOD | `$5948` | `LDA #$10` -> `#$00` (before `JSR $5953`) | food for a dungeon turn |
| FOOD | `$6B13`, `$6B96` | `SBC #$19` -> `#$00` | food for a move (two paths) |
| PASS | `$5151` | `INC $22` -> `LDA #$01` | overworld round counter: wait for a key |
| PASS | `$6D11` | `DEY / BNE` -> `JMP $6CFE` | dungeon countdown |
| PASS | `$692B` | `INC $20` -> `LDA #$01` | direction prompt timeout |
| TORCH | `$79AF` | `SBC #$01` -> `#$00` | Ignite keeps the torch (`$8E2E`, BCD) |

The food subtractions are BCD on `$8E1D-$8E1F`; food lost to other causes is untouched.

### Hooks that are always in, tested at run time

The options byte is full, so X and V are launch pokes of `$80` into a flag in the driver
(`pw_on`, `cl_on`), and their hooks are built into `ULTIMA` unconditionally; without the
flag every hook does what the original did. `build.py` checks the original three bytes at
each hook.

**X: F1 tells where, F7 teleports, B brings a transport** (`u2powers.s`, `POWER_HOOKS`).
The code is not in the driver but in `SUBS`' block I/O (`$4E6A-$4F78`), dead since its
vectors `$40AB` and `$40AE` go to the driver (scanned: every file on both disks for
absolute `JSR`/`JMP`/load/store operands into the range, `SUBS` for branches into it, the
driver's sources for its addresses -- found only the two vectors, the dead load code at
`$4B86` and the block code itself). `build.py` assembles it on its own, passes `pw_on`'s
address in the driver (`acme -D`), checks it ends before the RNG at `$4F79`, and writes it
into `SUBS`; its symbols are in `build/u2powers.sym`.

- `$5233` `JMP $6702` (a non-letter key that is no command: "ILLEGAL COMMAND!") ->
  `JMP pw_key`. With `pw_on` and on the surface (`$8E14 = 0`):
  - F1 (`$85`) prints `POSITION X-30 Y-31` (`$02`/`$03`, two digits each), a carriage
    return as `$52C0` would, and goes to `$50E7`, the prompt, where the turn's end goes
    after the monsters: no turn passes.
  - F7 (`$88`) prints `TELEPORT X-` / ` Y-`, reads two digits each (at most 63; the map
    is 64 x 64 at `$1000`) and stores `$02`/`$03`; anything else prints ` WHAT?`. Both
    end at `$52C0`, the command's end. X waits on the stack until Y is good.
- `$72CD` `JSR $4006` (Board's " WHAT?" with nothing to board) -> `JSR pw_board`. With
  the option on the surface it drops the return address, prints
  `(H)ORSE,(F)RIGATE,(P)LANE-` on its own line (the text area is 29 columns), and puts
  `$22`, `$24` or `$26` into `$13`, the transport Board keeps; otherwise it tail-calls
  `$4006`, which finds its inline string after the original `JSR` as before.
- Keys come from `$38` (bit 7 set while a key waits; `$4075` takes it and keeps A and
  the flags), characters go out through `$4057` (A and Y kept). The tiles around the
  party (`$14-$18`) are redrawn by the view after every command, so a teleport leaves
  none of them stale. No rocket: launching is the
  game's way between Earth and the planets. U2 has every letter in use, hence F1 and F7.

**V: counts stop at 99 and 9999** (`u2clamp.s`, `CLAMP_HOOKS`): every add to the player
record is `SED / ADC / STA` with the carry out of the top digit dropped. Each add's last
`STA` becomes a `JSR` into the driver: 23 of them, for coins (`$8E22/$8E23`), experience
(`$8E20/$8E21`), food (`$8E1D/$8E1E`, whole rations; the hundredths stay), weapons
(`$8E40,X`), armour (`$8E60,X`), spells (`$8E80,X`), items (`$8EA0,X`), torches
(`$8E2E`), keys (`$8E2F`), tools (`$8E30`), helms (`$8EA5`) and tri-lithium (`$8EAF`).
The attribute add (`$7F6C`, `LDA $8E15,X` and four `ADC $28`, "ALAKAZAM!") is a `JMP`
to `cl_att`, which tests each `ADC`'s carry and returns to `$7F7A`. With `cl_on` a
carry out stores `$99` (both bytes for a four-digit value). The flags after every hooked
`STA` are dead (`CLD`, then `JMP`, `JSR` or `LDX`), and the carry is left as the add made
it. Hit points are not hooked: their one add (the king's, `$8426`) gives nothing from
9900 on. The full list of adds, with the game action of each, is in `u2clamp.s` and
`build.py`.

**The footstep from the raster IRQ** (`u2step.s`, `STEP_HOOKS`, `SUBS_HOOKS`), always on:

- `ULTIMA` `$6B01` `JSR $4021` (on foot, and the walk of a horse and a plane) ->
  `JSR st_foot`; `$6AF1` `JSR $4021` (a horse) -> `JSR st_horse`. Each waits until
  `ST_FLOOR` ticks (20, 0.2 s) have passed since the last move's click (`st_since`; not
  with interrupts masked), writes the click's registers as `SUBS` `$4DD9` does, from its
  own blocks (`$4DDE`: `$D415-$D41B`; `$4DEA`: `$D40E-$D414`, seven bytes each, as `$40A2`
  copies them; `$D414 = 0` matters, the other effects leave sustain `$F` and a long
  release there), gate off first, and starts
  the IRQ's sequence: `st_tab`, (tick, `$D412`) pairs. `st_horse` plays the original's
  three clicks and sets `st_skip`, so `$6BB4`'s `JSR $6B01` that follows neither clicks
  nor waits.
- `SUBS` `$47A9` `INC $2D / BNE $47AF` -> `JMP st_tick`: both raster handlers end there,
  so it runs twice a frame (9.2k and 10.5k cycles apart). It counts the frame as before,
  counts `st_since` up to `$FF`, plays the sequence's next event when its tick comes, and
  goes on at `$47AF`.
- `SUBS` `$40A2` `JMP $4CBC` (the SID block writer, which every effect starts with) ->
  `JMP st_fx`, and `u2_enter` (every load and save) calls `st_flush`: a click in flight is
  waited for, as the original's blocking effects were, or cut with interrupts masked.
  Nothing else writes voice 3 but the SID clear `$401B` (`$43BF`), at `ULTIMA` `$7C06`
  and `$7D72`, never right after a step; at worst it would silence the rest of a click.
  (Scanned: `ULTIMA`, `SUBS`, `INTRO`, `STARS` and `DNGNDRAW` for absolute stores to
  `$D400-$D41C` and for calls of every effect vector.)

`build.py` checks `$4021` is `JMP $4DD9`, the two blocks' `JSR $40A2` and targets, the
gate off at `$4DF1-$4DFB` and the bytes after the hooked `INC $2D`.

### Journey onward

`p["journey"]` pokes `JMP $CEBC` over `$C093` (the start of the title sequence, after the
`STARS` load): `$CEBC` is the title menu's `<P>` path, which loads `ULTIMA`, and `ULTIMA`
reads the player record itself. `build.py` asserts the bytes at both addresses.

## Saves: a write log

The game writes 256-byte units: the record (raw T35/S16) at a save, and a map's `MOB` and
`MON` files each time the party leaves it on Earth (`$68AE` skips the write when `$8E37`
is not 0). 26 files are writable (`F_WRITE`); the game ever writes 12 of them.

Region: `regions.save_base("u2")` = `$1E4000`, 32 KiB, two halves of 16 KiB
(`u2log.HALF`). The address is pinned (`tests/test_regions.py`): a moved save is a lost
save.

### Layout

Each half is 64 pages: pages 0-62 hold one unit version each, page 63 is the directory.
Directory byte k is the unit in page k (`$FF` free, `$FE` dead); bytes `$FE`/`$FF` are
the half's generation and its complement. Unit 0 is the record, unit n the name table's
entry n-1. A unit the log does not hold reads as its seed in the game data. The active
half is the valid one (header and complement agree); of two valid halves, the one whose
generation is the other's plus one (mod 256).

### Operation (`u2log.s`)

- **`lg_init`** (from `u2_boot`, at every launch) reads both headers, picks the active
  half, walks its directory and points each unit's table entry (`u2_recpage` for the
  record) at its newest page, so **loads go through the ordinary name table** and never
  look at the log. The page after the last recorded one must be erased; if a power cut
  left it written, it is marked dead and the next one checked.
- **`lg_append`** (`u2_save` for a writable file, `u2_block` writing T35/S16): writes the
  data into the next free page, then its directory byte, then repoints the table entry.
  A half without a header is erased and given one first.
- **Compaction**, when the half is full: the other half is erased, each unit's newest page
  is copied over through `$DF00` with its directory byte (the unit about to be written is
  skipped), the header with the next generation is written last, then the old half's
  directory block is erased.

A power cut at any point leaves one valid half holding every unit's last complete
version. The one case not covered, as in U6's log: a directory byte whose programming is
cut could read as another unit's number.

`u2_save` drops a write to any name that is not writable rather than touch read-only
flash. The original would scratch and create such a file, but the only names it can make
are `MOB xy` with y not 0, which nothing loads back (`$67F1` skips the `MOB` load unless
`$8E14` and `$8E37` are both 0). `u2_block` ignores any sector but T35/S16 and always
leaves `'0'` (OK) in `$FD`, as `$4F5C` would.

A read-modify-write of a packed 4 KiB block would take half the code and a quarter of the
flash, but every 256-byte write would become a 4 KiB read, erase and 1-bit write (two or
three seconds, twice per town exit), and a cut mid-rewrite would lose 16 units at once,
the record included. The log avoids both.

### The pristine state

A fresh cart's log region is erased (no valid half), so every unit is its seed. Play only
changes the record and `MOB`/`MON` 00-40, and none of the seeds needs data from a played
disk:

- the record is 256 bytes of `$00` (a valid player disk with no character);
- each `MOB nn`/`MON nn` is a byte-for-byte copy of its `MOBXnn`/`MONXnn` template on the
  same disk, which the game never writes (`INTRO`'s new-game initialisation copies
  `MOBX00`/`MONX00` onto `MOB 00`/`MON 00`).

`ultima/disks/manifest.py` (`SEEDS`) encodes exactly this, so a played side B builds the
same cart as a fresh one. Its saved game can be imported on top
(`ultima/disks/importsave.py`: a disk holds a game when the record's first byte is a
letter with bit 7 set).

### The launcher's side

`asm/page_u2l.s` reads the same layout: `lg_find` resolves a unit to its newest page (or
its seed) for the info line (`i_u2` in `asm/page.s`: name, hit points `$1B/$1C`, food
`$1D/$1E`, BCD; a record counts as a game when its first byte is `$C1-$DA` and its `$FF`
is 0) and for export, through `xfer.LOG | unit` slots. An import writes all units into the
other half as a fresh half, header last. The export's Player disk is recognised by the
BAM name, the Trilogy's or Sierra's (`"U II-PLAYER DISK"`, `alt` in `build.py`). Export
writes `MOB 00-40`, `MON 00`, `MON 03`, `MON 10-40` (each scratched and saved, with the
game's own load address, `$3000` or `$8F00`) and then the record with a block write.
Reset erases the region: a fresh image's log is all `$FF`.

## A step on the surface

`ULTIMA`'s command loop prints "CMD:" (`$50F1`), rotates the water's character rows
(`$69A5` three times, `$6981`) and polls `$38` at `$512C`. Every 256 polls an idle pass
draws the view again (`$4087`) and rotates the water; 24 idle passes let a turn go by
(`$5151`). A direction key (`$5186`) prints its name and checks the square (`$69F1`); on
a free one the party moves and the footstep plays (`$6AD6` on: the transports' paths are
in [the reversing notes](../reversing-notes/u2.md#a-move-and-its-footstep)). Then the
turn: the monsters (`$52C0`), the view drawn and attacks and food (`$53DD`), the status
(`$543E`), and back to the prompt (`$5469` `JMP $50E7`).

In the original more than half of a step is the footstep's waits. The cart plays the

## Pitfalls

- **Keys in a VICE script go straight into `$38`**, one at a time once the game has taken
  the last (`$4075` clears bit 7). Through the KERNAL's queue keys are lost at random, and
  a lost Y in character creation leaves no player. Idle turns pass while a script waits:
  left in warp, the player starves. They also scroll a command's text off the four text
  rows, so check what a command did with a breakpoint or in RAM.
- **PRG headers lie**: files load where the inline parameters say (`SUBS` `$4000`,
  `INTRO` `$C000`, `ULTIMA` `$5000`, `STARS` `$9000`, `DNGNDRAW` `$9680`), not at their
  header addresses.
- **Bytes after a `JSR` to `$408D`, `$4090`, `$4006` or `$40A2` are parameters**, not
  code. A patch near one must keep the inline block intact (`pw_board` relies on it).
- **Forcing I/O visible must not touch LORAM**: BASIC ROM would cover the driver.
  `u2_fetch` only sets CHAREN.
- **Sierra's 1984 side A** has a different `INTRO` (packed into its boot program, code
  above `$C600` shifted by up to `$220`): every `INTRO` patch site moves (`$CED6` is at
  `$CCB6`, `$C9C0` at `$C85C`, `$CE89` at `$CC69`, `$CED3` at `$CCB3`) and what else
  differs has not been examined. The build supports only the Origin side A;
  `ultima/disks/scan.py` names Sierra's in its diagnosis.
