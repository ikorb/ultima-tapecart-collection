# Ultima IV: how the cart version works

This covers the build (`ultima/games/u4/`), the driver and its segments, how the four disks
are stored in flash, every patch, saves, and the tests. For the original game itself (disk
layout, the resident kernel, chunk and record tables, the save format) see
`docs/reversing-notes/u4.md`; for what Ultima IV Remastered changes and how, see
`docs/reversing-notes/u4-remastered.md`.

Ultima IV Remastered is by Per Olofsson (MagerValp): code (c) 2006-2015 Per Olofsson,
Apache 2.0; new graphics (c) 2015 Vanja Utne. It enters the build as the git submodule
`external/u4remastered` (github.com/MagerValp/u4remastered, v2.2.1). Everything the cart
takes from it is assembled or generated from that submodule and the supplied disk A at build
time; nothing derived from it is checked in.

## The seam

Every disk access in Ultima IV goes through one routine of the resident kernel
(`$A100-$A6FF`, copied there by the boot PRG): LOADBLK at `$A45E`, reached through the jump
table's `$A103` and from the chunk/record dispatcher's retry loop at `$A1C0`. Its contract
is the parameter block at `$A000` (op 1 read / 2 write, block count, address, linear block
number from T1/S0) and C clear on success.

**The driver is assembled at `$A45E`**, so the kernel needs no patch to reach it: the jump
table, the dispatcher, the chunk and record tables and the boot routine `$A429` are the
original's. The track/sector conversion `$A48F`, the geometry table `$A4E4` and the KERNAL
serial code up to `$A673` are dead and are the driver's room.

Because block numbering is kept exactly, every caller works, including the one that does
not use the tables: SUBS' `$0A7F` (chunk `$4F`) computes a block number by hand,
`(($60 << 4) | $61) + 1` with both nibbles 0-15, i.e. blocks 1-256, and reads one
overworld block through `$A103` into `$E800-$EBFF`. Its op byte `$62` is only ever set to
1 on any of the four disks, so it is read-only. (The other three "copies" of that routine,
in chunks `$40`, `$6C` and `$89`, `JSR $0A7F`; they are relocated residue.) A request is
therefore always `(current disk, block, count)`.

## The driver (`u4drv.s`)

Built with `TC_NO_CMDMODE` (the menu entered command mode), `TC_IRQ_ON`, `TC_NO_FAST`
(no blanking, no `READ_FLASH_FAST`), `TC_GUARD` with `TC_GUARD_ELSEWHERE`, and `ZX_ZP =
$FB` for `asm/zx02s.s`.

**Two pieces.** acme emits one blob from `$A45E` to the end of the second piece with the
hole zero-filled; `build.py` (`build_driver`) slices it and **refuses a non-empty hole**,
which is what proves the resident part never reached `$A674` (BANKOUT/BANKIN and the
IRQ/NMI trampolines, which stay live). `u4drv.s` also asserts `u4_glue_end <= $A674`.

- **Resident, `$A45E-u4_glue_end`**: `u4_transfer` (LOADBLK), `u4_init` (the init stub
  calls it: `tc_init` with the second piece banked in), `u4_in`/`u4_out`, the disk-swap
  hook `u4_setdisk` **pinned at `$A500`** (asserted: the code before it must end there),
  the four-entry block-map table `u4_map_lo/mid/hi`, `u4_savepage`, `pt_opts`, the IRQ
  pieces (`u4_irqs`, `u4_irq`, `u4_kirq`) and `asm/tcguard.s`, whose receive banks I/O in
  to read the raster and so cannot run from under it. Everything the launcher pokes is
  here.
- **Under I/O, `$D000-u4_lib_end`**: the read and write bodies, `asm/patch.s` (with
  `PT_LONG`, a 16-bit table pointer: the options table is over a page), `asm/tclib.s`,
  `asm/zx02s.s` with `zx_getbyte = tc_stream_byte`, the 64-byte block-map buffer, the
  generated `PT_TAB` (`build/u4_patches.s`) and `asm/journal.s`. Asserted below `$DF00`,
  where the temporary map's copy lives.

The RAM under I/O is safe because every write to `$01` on the four disks is `$35` or `$36`
(a scan of every chunk and the kernel; `$A3CB`'s hit is a word table), no chunk or record
loads into `$D000-$DFFF`, and the VIC works in bank 0. `u4_in` runs a call at `$01 = $34`.
Meanwhile the NMI vector at `$FFFA` points at an RTI (`u4_rti`): the kernel's NMI
trampoline would come back with `$01 = $35`, under code that is then not there.

**The pinned `$A500`.** `build.py` writes `JMP u4_setdisk` over each swap overlay's
`STA $5E`; at two of the three sites its last byte lands on the body's first, the original
`$A5`. The bodies are dead, but their bytes stay the original's that way, and the build and
the tests find the overlays by them (`SWAP_BODY`).

### Read

`u4_transfer` saves P, sets up interrupts (`u4_irqs`, below), `u4_in`, `u4_run`, then
`pt_apply` (the launcher's options, after every LOADBLK), `u4_out`, `u4_irqs_out`, and
puts the caller's I flag back by hand: PLP would clobber the carry, which is cleared on
return (flash never fails a read).

A read takes up to `MAP_BATCH` = 16 entries of the current disk's block map into
`u4_map` (one `tc_read` from `map[disk] + block * 4`), then for each block either decodes
its zx02 stream straight out of flash (`tc_stream_open`, `zx_unpack`,
`tc_stream_close`) or, for a length of 0, reads a raw page with `tc_read`. A batch
boundary only costs another map read.

**Speed.** Every read is 2-bit with the screen on (`TC_GUARD`: each byte starts clear of
badlines), and 1-bit while a sprite is enabled -- Remastered's creation moongate. See
`docs/developer/transfer.md` for `TC_GUARD`. Measured with `tools/vice/u4_check.py --time` (VICE
cycles, not cycle exact): game main (chunk `$5B`, 80 blocks, the load behind Journey
Onward) 3.62M cycles, about 3.7 s; module `$41` (32 blocks) 1.36M; one overworld block
from `$0A7F` 24-27k; the whole 453-request sweep 31.2k cycles a block with interrupts
masked, 34.8k with the music's interrupts taken. The original's stock-KERNAL reads take
about 640 ms a block.

### Write

Writes only land in the five save slots (disk 2, blocks 271-275). `u4_setaddr` maps a
block of the save disk in that range to its slot, `u4_savepage + index * 16` pages;
anything else is dropped (there is no such call in the game). Each slot is written
through the journal (`u4_jwrite`: `jr_begin`, the body, `jr_commit`, the body again,
`jr_end`; the body erases the slot's 4 KiB block and writes the page). Reads need no
special case: disk 2's map points those five entries at the slots with length 0.

**The temporary map (chunk `$7E`, block 271).** The game writes it at every entry into a
town, castle, keep or dungeon and reads it back at the exit. The driver keeps it at
`$DF00` instead (`TMAP`): a write of block 271 goes into the copy (`u4_tmv`, `u4_tmd`
set), a read of it comes from the copy once there is one, and **the next write of block
272 (chunk `$7F`, every Quit & save) first flushes a changed copy into slot 271**
(`u4_tflush`), so a saved game holds the map it needs. This follows Remastered's
`tempmap.s` cache, with the driver's own flush.

### Interrupts: the music through a load

U4 plays with interrupts on; its music handler (`$EC89`, from chunk `$55`) is hooked into
the kernel's IRQ vector `$A116`. Three things in that path would break a load running with
interrupts on, and all three are handled:

1. **`$0314`.** The KERNAL IRQ (`$EA31`) has the cassette code, which starts the motor
   while the cart is busy (rule 3 of tclib). `u4_irqs`: if `$0314` is `$EA31`, it points
   it for the load at `u4_kirq` (`JSR $FFEA / JMP $EA7B`, the KERNAL's IRQ without the
   cursor and tape code) and lets interrupts run as the caller had them; with anything
   else there -- character creation's raster split, the only store to `$0314` on the four
   disks -- the load runs masked. `u4_irqs_out` restores `$EA31`.
2. **The kernel's IRQ entry `$A696`** (BANKOUT's RAM `$FFFE`) is `JMP u4_irq`
   (`build.py` patches `48 8A 48`). `u4_irq` keeps the interrupted `$01` for the way out
   (a frame the KERNAL's RTI returns through) and sets `($01 & $38) | $05`: I/O in for
   the music's SID and CIA writes, the cassette bits kept.
3. **The way on to the KERNAL, `$A6AC`**, is `LDA $01 / AND #$38 / ORA #$06 / STA $01 /
   JMP ($FFFE)` (11 bytes over the original's `LDA #$36 / STA $01 / JMP ($FFFE) / LDA #$35 / STA $01`;
   the original exit at `$A6B3` is only reached through `$A696`'s pushed frame, which
   `u4_irq` replaces).

The six `LDA #$00 / JSR $AF20` that stop the song before a load (Descend `$4F94`, Klimb
`$55FC`, Mix `$56B5`, Quit & save `$5831`, Search `$59B7`, Use `$5AFF`) are `BIT`
(Remastered's `patch_music`): the `LDA #$01 / JSR $AF20` after each finds the song playing
and does nothing. `zx02s`' four zero-page bytes `$FB-$FE` are safe with the IRQ on: the
music driver uses `$02-$07`, `$2F-$3B`, `$4D` (a walk of its code from `$EC00`/`$EC03`/
`$EC06`/`$EC89`), the KERNAL's clock and keyboard scan their usual ones.

### No NMI while the cart talks

RESTORE's NMI inside a timed 2-bit byte would corrupt it. An NMI cannot be masked but is
edge triggered: `u4_in` lets CIA 2's timer A run out once with its NMI enabled and leaves
it unacknowledged, so the line stays low and a RESTORE pulse makes no edge; `u4_out`
reads `$DD0D` and lets it go. Nothing on U4's four disks touches CIA 2 but `$DD00` (a scan
for absolute `$DD0x` operands: one hit, in graphics). `tools/vice/u4_nmi_check.py` drives
CIA 2's timer B as an NMI source on the same line, one shot inside each of 46 LOADBLK
calls: all byte-exact; with `--nohold` (the hold poked out) some come back corrupt. Note
that an NMI every 2000 cycles proves nothing: the first lands among the 1-bit command
bytes, and since `u4_rti` acknowledges nothing the line then stays low anyway.

## Disk identity

The swap overlay (`STA $5E` = wanted disk, prompt, then load record `$00` -- block 0, one
byte, to `$0050` -- and compare with `$5E`) is replaced at its entry by `u4_setdisk`,
which stores the number in `$5E` and `u4_disk`, sets `$5F` = 1 (one drive) and `$52`
(`$51 + drive`, the "disk in drive N" cache), and returns. The block router uses
`u4_disk`; it starts at 1 on every launch (the segment is reloaded from flash).

The game's numbers are 1 = A, **2 = C** (Britannia), **3 = B** (Towne), 4 = D, a
different numbering from the BAM IDs (`01`..`04` for A..D). `build.py` takes each disk's
number from block 0 byte 0 and refuses a disk that disagrees. The game's own record-`$00`
check still runs whenever an overlay asks for it, so a wrong block mapping shows up as a
prompt rather than silent garbage.

## Storage: deduplicated zx02 pages behind block maps

The four disks are 4 x 683 = 2732 blocks but only 1579 distinct pages: code, music,
templates and filler recur. `build.py` stores **each distinct page once, zx02-crunched on
its own** (`ultima/flash/zx.py`), packed end to end in one blob, and writes **a block map
per disk**: 683 four-byte entries, the stream's 24-bit flash address and its length; length
0 is a raw page (the save slots, and the few Remastered picture pages zx02 cannot shrink
below 256 bytes). Without the Remastered variant this is 686 KiB of disk in about 224 KiB
(403 KiB from dedup alone, 210 KiB of streams, 11 KiB of maps).

**Five maps.** Maps 1-4 are the disks; map 5 (`TILESET`) is disk A with the Remastered tile
set and creation (below). Pages both share are stored once. The driver's table holds four
entries; the launcher's G option pokes entry 1 with map 5's address. The U4 data region is
292 KiB (`ultima/flash/regions.py`).

Why per page: any block must be fetchable alone, which `$0A7F` needs; per chunk is also
larger (every (chunk, disk) pair stored: 245 KiB against 210). Why zx02: 210 KiB against
exomizer's 231, a 117-byte decoder with no table, and room in the driver only with
`TC_NO_FAST`.

## The descriptor's segments

`build.py` writes seven segments, loaded by the menu before the init stub runs:

| Address | Contents |
|---|---|
| `$A006-$A9FF` | `u4a0.s` (to `$A0E7`, zero-filled to `$A0FF`), the patched kernel `$A100-$A6FF` with the driver's resident part spliced in, and colour tables 1-3 of the Remastered tile set at `$A700-$A9FF` (only its renderer reads them) |
| `$D000-` | the driver's second piece |
| `$0200` | the init stub (asserted under `$86` bytes, clear of `$0286`) |
| `$FF00` | `u4ff.s` |
| `$0839-$095A` | the boot PRG's credits painter and text, its final `JMP $095B` an RTS |
| `$02A7-` and `$0334-` | `u4pw.s`, cut in two around the KERNAL vectors `$0314-$0333` (asserted empty) |

**The init stub** (`asm/init_u4.s`) reproduces the boot PRG's `$0810-$0838`: `$00 =
$2F`, `$01 = $36`, stack at `$C0`, black screen, SID cleared, volume `$0F` (also the
kernel's mirror `$A126`), text colour `$0E`, clear screen. Unless the options byte has
JOURNEY it calls the credits painter and holds about four seconds (200 frames on raster
line `$FB`; a key read straight off CIA 1 ends it, `$DC00` back to `$7F`). Then `$C6 = 0`,
`$C0 = 1` (before BANKOUT's CLI), `JSR u4_init`, `JMP $A429` -- the kernel's own boot,
which banks out, loads the resident set and runs chunk `$50`.

## Patches to the disks

Everything is patched in the disk images before layout, each with its original bytes
asserted (`build.py patch()`), **on every disk that carries the bytes** (dedup stores a
page once by content, so a patch on one copy would leave the other disks' original).

### The build's own (disk A)

- **Copy protection.** Chunk `$50` `$6C8C` (`JSR $A103 / BCS $6C96`, the read of block 115
  that must fail) becomes `JMP $6C96 / NOP / NOP`, which also skips the read.
- **Swap overlays.** `SWAP_BODY` finds the shared body, `build.py` walks back to `STA $5E`
  and writes `JMP u4_setdisk`. Exactly three sites on disk A (chunks `$4F`, `$51`, and a
  block shared by `$50` and `$9A`); none on disks B-D (asserted).
- **The main menu's "Number of drives" line** (found by its bytes, exactly once):
  `$680F` jumps past it, "Return to the view" (`$67F5`) moves a row down into the gap, and
  the N key (`$688D`) goes back to the key poll `$6858` instead of the drives prompt.
- **Journey Onward** (the page's J, option bit `JOURNEY`): `$6031` (`JSR $6092`, the
  logo's first step) becomes `JMP $71E0`. At `$71E0`, in chunk `$50`'s residue (source
  text, nothing points there), `build.py` writes: display off, the title's own
  `$676C-$67A1` (state, the view's tables, load and start the music; asserted byte for
  byte), colour RAM `$0400-$07FF` cleared, display on, `JMP $6954` (the menu's J). Game
  main never turns the display on itself. About 20 s of logo waits are skipped.

### From Ultima IV Remastered (`remastered.py`)

`code_fixes()`. Disk numbers there are the game's (A = 1, C = 2, B = 3, D = 4).

  asserted to fold to the original.

  sets, so the dungeon uses table 0 only.

at `$B000`, Lord British's music-stop removal, the loaders, SuperCPU code.

### From Sean Gugler's continuation (`fork_fixes()`, `MAP_FIXES`, `HUMILITY`)

Sean Gugler continued the kit (github.com/sean-gugler/u4remastered, 2.3.0-2.4.1, Apache
2.0 as the kit); its wiki's `Version_2_3_0.md` analyses the 2.3.0 fixes. The build does
not use that repository: each fix was found in the original, checked against its
disassembly (`docs/reversing-notes/u4.md`, "Bugs in the original") and is written here
as a patch of the original bytes, named in `fork_fixes()` like `code_fixes()`.

- **The command level's stack, `fx_top`** (`u4fix.s`): `LDX #CMD_SP / TXS / JMP $621E`,
  `CMD_SP` = `$BE`, the stack at the main loop's key read, `cmd_done` and combat's
  command read (`tools/vice/u4_stack_check.py` measures it). The party dead (`$83E1`)
  and a moongate jump (`$86CB`) go through it; a moongate into a shrine (`$8699`) through
  `fx_gate_shrine`'s `PLA / PLA`. The fork's own moongate fix (`Trammel * 2 + Felucca ==
  12`, room for the PLAs in place) relies on phase pairs the game never produces; the
  helper is exact. Its party-dead fix resets to `$FF`; ours to the measured level.

### The town step (the cart's own)

Three SUBS routines, each the original's byte count and refused unless the original's CRC
matches:

- **`u4scroll.s`** (`$160E-$1686`, 121 bytes): the text window's scroll, the eleven
  bitmap row copies unrolled in one loop over 128 columns (absolute,X, fixed addresses
  `$2000 + 320 * row + 192`), row 23 zeroed in the same loop, the screen rows from the
  game's tables `$E180/$E198` (X counting `$F5..$FF`), row 23's colour by `u4scrollc.s`
  at `$19A3`. The build checks the tables on disk A are the standard ones (bitmap line n
  at `$2000 + 320 * (n / 8) + n % 8`, screen row n at `$0400 + 40 * n`), since the code
  hardcodes them. 30,104 -> 17,766 cycles a scroll on the host.
- **`u4view.s`** (`$0C0B-$0C71`, 103): the 11 x 11 buffer at `$AE80` with a map pointer
  once a row, not once a cell; columns wrap as 8-bit numbers as they did.
- **`u4los.s`** (`$0D65-$0E6B`, 263): line of sight. Pass 1 visits cells nearest the
  party first and looks only at each cell's next cell (a walk from a cell's next cell on
  is that cell's own walk, so this is exact); pass 2 is the original's walk for the cells
  pass 1 left blank.

Zero page the originals leave set and these do not (`$3D/$3E`, `$7C/$7D`, `$44/$45`) is
scratch that the following code sets before reading. Measured in VICE in Britain: 321,690 -> 260,323 cycles
a step with the original graphics, 302,542 -> 241,511 with Remastered's.

### The tile set and creation (`tileset.py`)

`variant()` makes a second disk A from the patched one:

- chunk `$41` (`$B000-$CFFF`) the kit's tile bitmap, chunk `$42` its font, chunk `$4C`
  colour table 0 at `$E1B0` and the font colours at `$E2B0`, all generated from the kit's
  `tiles.png` and `font.png` by `tiles.py`;
- the kit's five renderer routines, assembled by ca65/ld65 into their slots with
  `tilecolors0 = $E1B0` and tables 1-3 at `$A700`/`$A800`/`$A900`: SUBS `DRAWVIEW $0E6C`,
  `GETTILEADDR $148B`, `FILLRAND $14CC`, `ANIMATEFLAGS $1504`, and chunk `$50`'s
  `DRAWVIEWTITLE $6B83`; each slot is asserted unpatched before;
- character creation (`creation()`, `kit_creation()`): the kit's units built as its
  Makefile builds them -- the seven `.koa` pictures for `$45-$4B`, `gen_cards` for `$52`
  and `$9F`, `charcreate.s` over disk A's chunk `$51` with `151.binpatch` -- then merged
  three ways: where the kit left the original's byte, the cart's stays (the swap hook at
  `$692D`); where both changed, they must agree (the CLI fix, the JMPs). Chunk `$9F` is
  one block longer (disk A block 296, which no chunk or record uses, loading at
  `$9D00-$9DFF`, which nothing loads over during creation); the G option also pokes the
  kernel's count for `$9F` (`$A2A9 + $5F`) from 5 to 6;
- the title picture's view (`title_view()`): the dissolve copies a picture (bitmap chunk
  `$43`, colours `$9E`) whose rows 13-22 are the view pre-rendered in the original tiles,
  a second before the renderer draws it. `view_map()` recovers the view's tile map from
  the original picture (water through its vertical scroll, one flag tile by nearness) and
  it is rendered the renderer's way into both chunks, every cell's background black (the
  colours are on screen before the dissolve puts bitmap there, and an empty cell shows
  its background).

Colour tables 1-3 cannot go where the kit puts them: `$A800`/`$A900` are kit loader RAM,
and **`$F300` is read during play by the original game** (a VICE memmap: 209 reads in
`$F302-$F3FD` across Britannia, a town, a dungeon fight and a peer). `$F200`, the same
filler, is not trusted either. Hence the boot segment at `$A700-$A9FF`, which the driver
leaves free by living under I/O.

## The launcher's options

`OPTION_PATCHES` in `build.py` (format: `ultima/launcher/patches.py`; applier
`asm/patch.s` with `PT_LONG`). Applied after every LOADBLK when the option is on **and
every original byte is in place**. `check_options()` proves each signature appears in no
other block of any disk at that page offset (every block can be loaded to any page),
both for the classic and the tile-set disk A; `OPTION_BLOCKS` names the block each one is
in.

| Bit | Page key | Patches |
|---|---|---|
| FOOD `$01` | F | `$6273` (`LDA $1F / JSR $6500`, end of turn) jumped over: walking only |
| PASS `$02` | P | `$4094` and `$70EE` (main loop, combat): back to the key read instead of "Pass" |
| JOURNEY `$04` | J | `$6031` -> `$71E0`, see above; never stored |
| TILES `$08` | G | no RAM patch: launch pokes of `u4_map_lo/mid/hi` (entry 1 = map 5) and the `$9F` count |
| TORCH `$10` | U | `$5516` `JSR $8450` -> `SEC / NOP / NOP` |
| ITEMS `$20` | M | Cast `$48A1` -> `JMP $48DD`; Jimmy `$5551` branch past "use up a key"; Peer `$57CD` -> `JMP $57D7` |
| AVOID `$40` | A | `$66FB`, `$62D7`, `$6D14` -> `fx_avoid*` (`u4fix.s`) |
| BALLOON `$80` | W | the four "DRIFT ONLY!" JMPs -> `fx_balloon_*`; SUBS `$0B15` an RTS |
| POWERS (settings only) | X | a launch poke `pw_on = 1` (`$02A7`) |

The options byte is full, so POWERS has JOURNEY's value but lives only in the settings and
the page's caps; the page pokes the options byte through a mask without it. The BALLOON
south hook's signature is 29 bytes because two stale near-copies of its block (disk A
256, chunk `$9B` at `$4100`; a save slot's seed) agree up to page offset `$69`.

## Saves

- **Slots**: five 4 KiB erase blocks from `regions.save_base("u4")` (`$1DE000`), then
  the journal block (`$1E3000`): block 271 (chunk `$7E`, temporary map), 272 (`$7F`), 273-274
  (`$80`, the roster at `$AA00`), 275 (record `$1A`, 32 bytes of zero page from `$0010`;
  byte `$0F` is `$1F`, the party size and "game present" flag). Fixed addresses: a save
  moved is a save lost (`tests/test_regions.py`).
- **Pristine base.** The game writes only disk C 271-275; each has a template on disk A
  that the game never writes. The release manifest (`ultima/disks/manifest.py SEEDS`)
  rebuilds them, so a supplied Britannia disk may be a played one: 271-272 all zero (= chunk
  `$53`, disk A block 253), 273-274 = disk A 254-255 (chunk `$54`), 275 = disk A 256 with
  byte `$0F` = 0. A fresh cart says "NO ACTIVE GAME!" as the factory disks do.
- **The page** reads the roster and zero-page slots (`U4_ROSTER`, `U4_ZP`) to show the
  party. Its export notes when the save is in a dungeon (`BUF+$0B` = 3): the original
  game would start it on the surface at the dungeon's coordinates.
- **Export and import** (`xfer.Disk("Britannia", ...)`): the five blocks as raw sectors on
  the Britannia disk, recognised by the BAM's disk name (the Trilogy's, or "BRITANNIA",
  the 1986 disk's) and by T1/S0 byte 0 = 2, which also tells it from U5's Britannia. The
  file export is 6 blocks.
- **Other readers**: Ultima V's "Transfer from Ultima IV" and Ultima VI's Avatar transfer
  read these slots (`tests/test_u5_build.py`, `tests/test_u6_transfer.py`).

## Pitfalls

- **Patch every copy.** Many pages exist on several disks (camp on C and D, mix on B/C/D,
  peer on B/C, the swap overlay in three chunks). Dedup stores by content, so a patch on
  one copy silently creates a second page and leaves the others original.
- **A stale copy of live code can hold a signature.** That is why `$5B`'s tail is
  cleared, and why the balloon's south signature is 29 bytes. `check_options()` is what
  catches it.
- **The resident part must not reach `$A674`**, and `u4_setdisk` must stay at `$A500`.
  Both are asserted; any new pinned `* =` needs an assertion in front of it.
- **`CMD_SP` is measured**, not derived: a change to the boot or the kernel's start can
  move the command level's stack. `u4_stack_check.py` is the check.
- **Do not run code from `$D000-$DFFF` with I/O in.** Anything that runs with I/O
  visible (the guarded receive, the IRQ entry) is resident.
- **`$F200-$F3FF` is not free**, whatever a static scan says. `$A006-$A0FF`, `$FF00-$FFF9`,
  `$02A7-$0313`, `$0334-$03FF`, `$9D00-$9DFF` (during creation), `$86EF-$87FF` (while
  `$5B` is in) and SUBS' dead swap prompt are the places used; a new home needs a static
  scan of all four disks and a VICE memmap across every mode (town, dungeon, combat,
  balloon, peer, the shrines, the ending).
- **Route by the game's disk number** (block 0 byte 0), never the BAM ID.
- **Character creation installs its own `$0314`**: loads there run masked, by design.
- **The animated tiles are rewritten in the shared tile bitmap**, not chosen at draw time
  (water rolled, fields randomised, flags swapped, from the end of `$0F90` on every view
  draw). A draw-only-what-changed cache would have to redraw those ids always and be
  invalidated by anything else drawing into the view (peer, dungeon, combat share
  `$0E6C`).
