# Updates and saves

How a flashed cart is updated without losing its saves, how the cart starts (the first
stage and the layout stamp), and how a save survives a power cut. The save regions'
addresses are in the [overview](README.md)'s flash map (`ultima/flash/regions.py`); U2's
and U6's write logs are described in [u2.md](u2.md) and [u6.md](u6.md); export and import
in [launcher.md](launcher.md).

## Updating a flashed cart

`make` writes two images:

- `build/ultima-collection.tcrt`: everything, for a fresh cart;
- `build/ultima-collection-update.bin`: the flash from `$000000` to the end of the game
  data (rounded up to an erase block), below the save area.

Flash the update with the tapecart flash tool's **advanced "Write data file" at offset
0**, which erases only the blocks it writes. Its "Write TCRT" erases everything after the
image, saves included.

"Write data file" does not touch the cart's loadinfo, so **the loadinfo never changes**:
it always loads the **first stage**, `asm/boot.s`, `regions.BOOT_LEN` (2 KiB) from flash
`$000800`, called at `$1000` (the launcher's staging buffers, where nothing of the
launcher loads). The first stage then loads the launcher through the locator at
`$0000F8` (its flash address and length), at whatever length the build gave it, with the
2-bit guarded read, and jumps to the menu at `$8700` (`JMP start`). The menu enters
command mode again itself, which is harmless: `tc_cmdmode` drops the cart to streaming
mode first. So an update needs a full flash only when the save layout changes.

`ultima/build.py` checks that the menu's PRG still starts with `JMP start` at `$8700`;
`tests/test_regions.py` pins the first stage's place and length.

A cart whose loadinfo is not this one (a build without a first stage) cannot be updated
this way: it needs the full `.tcrt` once.

## The first stage

It blanks the screen before anything else (black border and background, cleared, white
text for any message). Then, before it loads the launcher and so before anything runs
that reads a save:

- **It checks the layout stamp.** The settings page (`regions.SETTINGS`, `$1FF000`) must
  start "UCFG" (`regions.SET_MAGIC`) and carry `regions.LAYOUT` at `+$0C`
  (`regions.SET_LAYOUT`); the build seeds that page in the full image. If it does not --
  an update image flashed over a cart whose saves are laid out for another build, or a
  cart with no stamp -- the first stage prints why ("flash this build's full .tcrt image
  ... or the build that made them again, to export them first") and stops. **Raise
  `regions.LAYOUT` whenever a save moves or changes format.**
- **It finishes any journal** a power cut left (below).

Its tables (each journal's place and its region) are generated by `ultima/build.py`
(`first_stage()`, `build/boot_tab.s`).

Tested: `tests/test_journal.py` (the stamp's three wrong cases, the launcher load). In
VICE: `tools/vice/first_stage_check.py` (a power-on to the list; a wrong stamp's message
and no menu; a planted journal copied into its slot and erased before the menu starts).

## Saves that survive a power cut

U2's and U6's saves are **write logs**: new versions are appended and a half becomes
active only by a header written last (see their documents). U1, U3, U4 and U5 have fixed
slots, and each slot is written through a **journal** (`asm/journal.s`,
`regions.journal`), so that a power cut leaves either the old save or the new one, whole.

The journal is one erase block (U3's two: its `SOSA` slot is 17 pages) at the top of each
fixed-slot region, below the settings block:

| Game | Journal |
|---|---|
| U1 | `$1FE000`, 4 KiB |
| U3 | `$1F6000`, 8 KiB |
| U4 | `$1E3000`, 4 KiB |
| U5 | `$1DD000`, 4 KiB |

A slot is written twice:

```
        (tc_addr = the slot: page aligned, the start of its erase block)
        jsr jr_begin    ; tc_addr <- the journal's second page
        <write the slot exactly as before, relative to tc_addr, erase included>
        jsr jr_commit   ; the journal's header, last; tc_addr <- the slot
        <write the slot again>
        jsr jr_end      ; the journal's first block erased
```

The header (`jr_commit`) is 4 bytes on the journal's first page: "JN"
(`regions.JOURNAL_MAGIC`) and bits 8-23 of the slot's flash address.

- A cut **before the header** leaves the slot holding the old save; the journal is an
  unfinished copy.
- A cut **after the header** leaves a whole new save in the journal: at the next
  power-on the first stage copies the journal's pages into the slot (skipping erased
  pages) and erases the journal. A cut after both writes, before `jr_end`, makes the
  first stage copy the same save again.
- A header that was begun but is not whole, or names no slot of that region (not block
  aligned, below the region, at or above the journal), only gets the journal erased.

Every slot keeps its address, so nothing that reads saves needs to know about the
journal: the page, export, U5's Ultima IV transfer, U6's Avatar transfer, the C128
launcher. A save takes about twice as long (~0.3 s more a slot).

**Not in U5's C128 build**: it has no room (5 bytes free), so it writes in place; a journal
the C64 build left is finished at the next C64 power-on only.

### Where the code lives

- U4: under the I/O (81 bytes); U3: in its decoder segment.
- **U1 and U5 make room from `tc_init`**, which runs once at launch: tclib's
  `TC_INIT_ELSEWHERE` leaves it out of the driver, and the init stub assembles
  `asm/tcinit.s` against the driver's symbols (`ultima/flash/tcsyms.py` writes them out:
  the `tc_v_*`/`tc_d_*` operands, `BIT_*`, `TC_KEEP_01`, `TC_IO_01`, `TC_FAST2`,
  `TC_GUARD`). U1's stub is too long for page 2 (its KERNAL variables from `$0281`) and
  sits at **`$C700`**, where `MA` goes later; `asm/boot_u1.s` calls its `tc_init` too
  (`build/u1_init.s`). U5's C64 stub also does the directory setup, and U5's driver
  includes `journal.s` in two parts (`JR_PART` 1 and 2), the first in the main segment,
  the second in hole C.

### Tested

`tests/test_journal.py` runs each driver's real save from the built cart on the model
cart and cuts the power at every flash operation's edges and a sample of the bytes
between, then runs the first stage's own repair: the slot is always the old save or the
new one, whole. In VICE: `make run-u1test` and `make run-u3test` (their round trips),
`tools/vice/u4_check.py --saved ...` with a Quit-and-save (the blocks in their slots),
`tools/vice/u5_save_check.py` (a `ROSTER` save through `$6C2D`: header, data, journal
erased; Journey Onward through the stub).
